# src/components/dictionary — Gotchas

## `sortDictionaryEntries` Bulk-Op Constraint

**`sortDictionaryEntries` bulk ops:** pass `null` as `changedKey` when modifying >1 entry — `IncrementalDictionarySorter.incrementalSort` only repositions ONE key per call; a non-null anchor silently drops the other N-1 entries from the persisted dict.

## `DictionaryContext.tsx` CRUD Audit Checklist

After touching any CRUD function or `addToHistory`, audit for:

1. Stale-closure ref-mirror (`currentHistoryIndexRef`)
2. Typed error throws (`ValidationError`/`SaveError`) including pre-`try` existence checks
3. Dep-array correctness
4. `isValidationError`/`isSaveError` double-toast guards — applies to `addEntry`/`updateEntry`/`deleteEntry`/`bulkDeleteEntries` only. `moveEntry`/`bulkMoveEntries` have no internal catch/toast at all, by design — `MoveDialog.tsx` owns error display for move ops via its own inline error banner (`handleMove`'s `catch` → `setError(...)`), not a toast. Tested as invariant I4 in `useDictionaryCRUD.test.ts` (`src/hooks/__tests__/`) — the move-op cases assert the inverse: zero toast calls on failure, so a future "helpful" toast added here doesn't double up with `MoveDialog`'s banner.
5. Metadata coverage (`allowAsPatternVariable`, `semanticType`, `allowedVariableTypes` for `phrases|patterns|properNouns-*`)
6. `prepareMutationEntry` called at the top of `addEntry`/`updateEntry` — owns sanitize + validate + typed value construction. Throws `ValidationError` (no toast); catch block handles the toast via `isValidationError(error)` branch. Validation is `validatePersistEntry(dictionaryId, source, translation)` from `utils/dictionary/PersistTimeValidator` — NOT the form-time `validateDictionaryEntry` in `DictionaryEntryValidator.ts` (different signature, different return type).
7. Cache invalidation called after successful save via `invokeEngineInvalidator(engineInvalidatorRef, id)` — required in every CRUD success branch. `engineInvalidatorRef` is registered by `Translator.jsx` at engine-ready time. Undo/redo paths handle invalidation via `invalidateEngine` injected into `useDictionaryHistory`.

**Single-dict CRUD protocol**: `addEntry`, `updateEntry`, `deleteEntry`, `bulkDeleteEntries` all go through `persistDictionaryMutation(dictionaryId, oldData, sortedEntries) → Promise<boolean>`. Defined in `useDictionaryPersistence.ts` (not inline in Provider). Owns optimistic `setDictionaries` → `saveDictionary` → rollback on failure. Move ops use `commitMoveOp` from the same hook — two-dict partial revert (if one save succeeds and the other fails, the successful write is reverted to disk). Callers own: diff computation, `sortDictionaryEntries`, `addToHistory`, toast, `invokeEngineInvalidator`.

**Load protocol**: Both `loadInitialState` (startup) and `loadDictionary` (single reload) delegate to `loadAllDictionaries()` in `src/utils/dictionary/DictionaryBackend.ts` (parallel batch + serial retry). Do NOT call `window.electronAPI.loadDictionary` directly — that path has no retry. Failure outcome classification lives in `classifyLoadResult` in `DictionaryLoadClassifier.ts`. See ADR-014.

`undo`/`redo` live in `src/components/dictionary/useDictionaryHistory.ts`. Diff-reversal delegates to `computeUndoMutation`/`computeRedoMutation` in `src/utils/dictionary/DictionaryOperationReverter.ts` — pure, no React. Dep arrays: `[history, currentHistoryIndex, commitMutation, invalidateEngine]` — `dictionariesRef` intentionally excluded (stable ref).

## Error Handling

**The double-toast guard depends on throwing the right typed error class every time.** If a code path shows a toast then `throw new SaveError(...)`, the outer `catch` must guard with `!isValidationError(error) && !isSaveError(error)` before showing its own toast. Same failure mode from the other direction: pre-`try` existence checks (e.g. dict-not-found) that use bare `throw new Error(msg)` bypass the `!isValidationError` guard entirely — always `throw new ValidationError(msg)` there instead.

## Dictionary JSON Format: Two Tiers

**Pure lookup tables** (`characters`, `conversion`, `punctuation`): string values only, no metadata. The string branch in `DictionaryManager.js` is intentional — do NOT convert these to objects.

**Complex entry dicts** (`phrases`, `patterns`, `properNouns*`): values MUST be `DictionaryEntryValue` objects. `addEntry`/`updateEntry` always write objects (never strings). Any code iterating `DictionaryData` must guard: `typeof value === 'string' ? value : value.translation`.

## `VirtualRowComponent` Is at Module Scope

Lives in `VirtualRowComponent.tsx` (sibling file), imported by `EnhancedVirtualizedDictionaryTable`. Do NOT wrap in `useMemo` or move inside any render function — any dep change creates a new React component _type_, unmounting all rows and destroying inline edit state (`sourceEdit`/`translEdit` from `useInlineFieldEdit`). `ITEM_HEIGHT` is exported from `TableBuildingBlocks.tsx` (moved there 2026-09-09, architecture review grilling — its real owner is `RowShell`, which lives there too) — import it from there, not redeclared locally.

## `SemanticType` Canonical Values

Canonical values: `'character'`, `'location'`, `'organization'`, `'concept'`, `'object'` (UI abbreviations: CHA/LOC/ORG/CON/OBJ). Dictionary JSON stores these strings directly — a stale value (e.g. old `'person'`/`'place'`) displays no badge and fails filter matching silently. Bulk-migrate with `scripts/migrate-semantic-types.py`.

- `SEMANTIC_TYPE_ABBREVIATIONS` and `SEMANTIC_TYPE_LIST` (from `src/constants/SemanticTypes.ts`) are the canonical exports for toggle cells in `EnhancedVirtualizedDictionaryTable.tsx` — do NOT redeclare local lists.
- `classifyVariableType` in `SemanticPatternProcessor.js` returns canonical values when `metadata.semanticType` is set, but falls back to internal discriminators (`'proper_noun'`, `'character_unit'`, `'unknown'`) that are NOT canonical — `'proper_noun'` is special-cased to `null` (always include); `'character_unit'` and `'unknown'` fail `allowedVariableTypes` constraints intentionally.

## `$X`/`$Y` Variable-Derived Semantic Types (Patterns Only)

Pattern `semanticType` accepts `"$X"` or `"$Y"` — resolved at WASM match time from the variable's cache `var_type`. Constants in `src/constants/SemanticTypes.ts`: `PATTERN_SEMANTIC_TYPE_REF_LIST`. UI: `SemanticTypePicker.tsx` (via `DictionaryEntry.tsx`) and `SemanticTypeToggleCell` in `EnhancedVirtualizedDictionaryTable.tsx` (inline column, patterns branch only — NOT phrases/properNouns branches).

Resolution edge cases: `$-ref` to non-existent variable (e.g. `"$Z"` in an X-only pattern) → `None` silently, no error. `$X` where var has `var_type: Some("proper_noun")` (JS non-canonical sentinel for untyped proper-noun entries) → `Some("proper_noun")`, NOT `None` — canonical `allowedVariableTypes` constraints (e.g. `["character"]`) won't match it.

## Pattern Variable Contract

X = optional 1st variable (0 or 1 — a 0-variable pattern is a literal, no-variable entry); Y = optional 2nd, but only meaningful alongside X. Y-only patterns (Y present, X absent) are intentionally invalid. Form-time (`DictionaryEntryValidator.ts`) and persist-time (`PersistTimeValidator.ts`) enforce **identical** rules as of 2026-09-07 — both delegate to `PatternEntryRules.ts`: no variable may repeat in source; variables must be introduced in order (Y requires X, Z requires Y); translation and source variable sets must match exactly, both directions. Before 2026-09-07 persist-time was looser (no ordering check, X/Y-only) — that asymmetry let a Z-variable or Y-without-X pattern pass the Quick-Add form's live check, then get rejected only at save. A 0-variable pattern is a deliberate, supported shape: it lets a literal pattern entry outrank a same-length variable pattern via `find_best_pattern_match`'s "fewer variables wins" tie-break (`wasm-core/src/pattern_processor/matcher.rs`) — see the 这种马上-vs-这X上 case (2026-08-29). Existing-entry suggestion (`handleTranslationFocus` → `checkForExistingEntry`) applies to patterns too (re-enabled 2026-08-10) — was previously suppressed via an `activeDictionary.startsWith('patterns')` guard with no recorded rationale; removed since it left same-dict pattern overwrites completely silent, unlike every other dict type.

## Dictionary Type Classification

Use `classifyDictionaryId(id)` from `DictionaryIdClassifier.ts` for all UI-layer type checks. `isPatterns` is true for both `'patterns'` and `'patterns-f_*'`; raw equality misses fiction variants and silently breaks on every dict-type extension, with no error anywhere — the UI just treats a fiction dict as some other type. Same reasoning for the fiction-prefix checks `isFictionProperNounsId(id)`/`isFictionPatternsId(id)`, for the ADR-027 pairing derivations `toPatternsId(properNounsId)`/`toProperNounsId(patternsId)`, and for `toProperNounsDictionaryId(rawName)` (create/rename forms; added 2026-08-28 architecture review candidate #4 grilling). All are pure transforms — the Rust side (`validate_dictionary_id`) is the real authority on ID safety.

You no longer have to remember any of that: `SourceConventionScan.test.js` fails on raw `=== 'patterns'`, on a hand-rolled `startsWith('properNouns-f_')`/`'patterns-f_'`, and on a hand-rolled `'patterns-' + …` / `` `properNouns-${…}` ``, repo-wide, with `DictionaryIdClassifier.ts` itself as the only exemption. The class was real — found duplicated at 10 call sites across 5 files (2026-07-28) — and stood at zero when the gate went in, so it is a zero-tolerance ceiling rather than a baseline.

**`=== 'phrases'` is deliberately not covered** — ruled out 2026-08-31. Fiction dicts exist only as `properNouns-f_*` and `patterns-f_*`, so `'phrases'` has no variant to miss and the nine live comparisons across `src/` are correct. Widening the detector to it would be nine false positives on day one. Reverse this only if a `phrases-f_*` dictionary type is ever introduced.

## Fiction Pattern Merge Order Is Load-Bearing

`FictionDictionaryFilter.ts`'s conflict merge must spread global `patterns` FIRST, fiction entries LAST (`{ ...global, ...fiction }`) so fiction wins on a same-template conflict (ADR-027). The reverse order was a live bug until 2026-07-16 — silently let global patterns override fiction-specific ones with no error. Verify with a same-key conflict test before touching this line again.

## `DictionaryInfo` Name Collision

`DictionaryTypes.ts` has a LOCAL `interface DictionaryInfo { label, description }` — display-only type for dictionary type metadata. NOT the same as `ComponentTypes.d.ts::DictionaryInfo { id, name, path, isActive, ... }` which is the API/IPC type used by `ElectronTypes.d.ts`. Do not re-export the local one, do not merge the two. Import `DictionaryInfo` from `../../types/ComponentTypes` for the API type.

## Hook Tests — jsdom Gotchas (Dictionary-Specific)

General jsdom/RTL testing techniques (RAF mocking, event-bubbling for context menus, closure-mocking hook arguments, ref-callback event capture) live in `docs/guides/gotchas.md`'s jsdom section — the two below are dictionary-specific.

`useVirtualScrollRange`'s `containerHeight` state defaults to `600` (not `0`) — small test datasets (EVDT and siblings) render fully with no ResizeObserver-firing needed; still stub `ResizeObserver` as a class so `new ResizeObserver()` doesn't throw "not defined" in jsdom.

**Patterns-dict source text is not a single text node** — `VirtualRowComponent` renders it through `highlightPatternVariables(source)`, which splits it into styled spans per X/Y variable. `screen.getByText(sourceString)` will fail to match; assert on the (plain-text) translation string instead.

## Reusable Row/Badge Building Blocks — `TableBuildingBlocks.tsx`

`RowShell` (fixed-`ITEM_HEIGHT` flex row wrapper — takes an optional `backgroundColor` override for the unselected state, added for `DuplicateDictionaryTableView`'s alternating group-background color; `isSelected`'s own highlight still takes priority), `CheckboxCell` (row-selection checkbox — exported 2026-08-28, `ariaLabel` prop overrides the default static title/accessible-name for callers with per-row labels), `MetadataBadge` (VAR toggle chip), `SemanticTypeToggleCell` (per-row single-active-type selector), `SemanticTypeFilterChips` (filter-bar multi-select toggle group — NOT the same shape as `SemanticTypeToggleCell`, don't conflate them), and `FilterChipButton` (generic active/inactive toggle-chip button — takes `active`, `activeColor`, optional `inactiveColor`/`ariaLabel`/`style`) are exported from `TableBuildingBlocks.tsx` (split out of `VirtualRowComponent.tsx` 2026-09-09, architecture review grilling — the row renderer's own module now holds only the row; these 6 symbols plus `ITEM_HEIGHT` moved because every external importer only ever wanted them, never `VirtualRowComponent` itself) specifically for reuse by other table-shaped views (e.g. `src/components/rules/RulesManager.tsx`, `RuleMatchesModal.tsx`, `DuplicateDictionaryTableView.tsx`) — import and reuse them rather than re-deriving the same padding/font-size/color values, which drift silently (found twice in one session: a copied semantic-chip badge missing `alignItems: 'center'`, and missing `fontSize`/`padding` overrides that fell back to the shared class's different defaults; found a third time 2026-08-12, `RulesManager.tsx` hand-copying the whole cell instead of importing it — see CLAUDE.md's Deleted Symbols entry for `SemanticTypeToggles`; found a 4th time 2026-08-14, the filter-bar chip group duplicated between `RulesManager.tsx` and `EnhancedVirtualizedDictionaryTable.tsx`, closed by extracting `SemanticTypeFilterChips`; found a 5th time 2026-08-24 — `SemanticTypeFilterChips`'s own per-chip button AND `EnhancedVirtualizedDictionaryTable`'s FilterPanel's 5 filter buttons were independently hand-rolling the identical 8-property inline style object, closed by extracting `FilterChipButton` and routing both through it, architecture review candidate #3 grilling); found a 6th time 2026-08-28, one level up at the column-schema layer — see `DictionaryColumnSchema` in `CONTEXT.md`. Any new active/inactive filter-chip button should use `FilterChipButton` directly rather than hand-rolling a 7th copy.

**A mechanized gate against the 8th recurrence was investigated and rejected (2026-09-08, architecture review candidate #2 grilling).** `fallow find_dupes` in `weak` (structural) mode — the shape-correct tool for near-duplicate JSX, already used in this repo for dead-code analysis — was tested against a deliberately-constructed near-copy of `MetadataBadge` (same onClick/stopPropagation shape, same ternary style pattern, different literal values) planted as a scratch file. Zero hits, even at `top: 200`. Its clone detector doesn't fire at the scale of a single small React component. A `SourceConventionScan.test.js`-style regex gate was also ruled out: it only catches literal-string patterns, and 6 of these 7 confirmed drifts were either an absent property or a near-duplicate object, neither of which a regex can detect (absence isn't a pattern to match; near-duplicates don't share a literal string). No cheap mechanized gate exists for this failure class — the discipline documented in this section (review + this file) is the real, and only, lever. Do not re-propose a fallow/regex gate here without a new detection approach — the ones tried are ruled out, not merely undone.

**The recipe itself was finally extracted 2026-09-09** (architecture review candidate #1 grilling), closing the 8th and 9th instances: `BadgeChip` (`TableBuildingBlocks.tsx`) is now the single owner of the active/inactive style — `TypeToggleCell` (`VirtualRowComponent.tsx`), `SemanticTypeToggleCell`'s per-type badge loop, and the Rules tab's `MatchKindToggle`/`MoveModeToggle` (deleted; replaced by one generic `BinaryToggleChips<T>` built on `BadgeChip`) all render it instead of hand-rolling the style object. Deliberately NOT folded in: `MetadataBadge` (own single-purpose identity, out of this round's scope) and `SemanticTypeToggleCell`'s dashed `$X`/`$Y` reference chips (a different visual language — dashed border signals "inherited," not a selection state — not a drift instance of this recipe). A 9th/10th recurrence there is still possible; this section's discipline note still applies.

`SemanticTypeToggleCell` also takes `clearable` (default `true` — `false` makes the active chip's click a no-op instead of firing `onSelect('')`, for required/non-clearable fields like Transform Rules' `semanticType`), `size` (`'table' | 'form'`, controls chip scale), `align` (`'center' | 'left'`), and `rowLabel` (per-row `aria-label` text — required whenever a view renders many rows of this cell at once, or every row's same-type chip is indistinguishable to `getByLabelText`/assistive tech).

**A real `<table>`'s `<tr>` `height` is a minimum, not a cap** — content padding/line-height can still force it taller. To match Dictionary's exact row density, don't build a `<table>`; use `RowShell`'s fixed-height flex-div technique instead (same mechanism `EnhancedVirtualizedDictionaryTable` itself uses). Setting `height: 40px` on a `<tr>` and expecting Dictionary-identical row height is a no-op if the cell content needs more room.

**Testing a `RowShell`-based row directly** (not through its parent table): `RowShell` renders a plain `<div role="row">`, not a real `<tr>` — render the component directly, don't wrap it in `<table><tbody>`. That wrapping is invalid DOM nesting (div inside tbody) and buys nothing; `role="row"`/`role="cell"` ARIA attributes work with `getByRole` without real table markup. Found writing `RuleRow.test.tsx` (2026-08-12).

## WASM Wrapper Methods

**Must check `initialize()` return value**: `if (!this.initialized) { const ok = await this.initialize(); if (!ok) return false; }` — skipping `if (!ok)` causes `this.processor.*` to throw TypeError when `this.processor` is null after failed init.
