# src/components/dictionary — Gotchas

## `sortDictionaryEntries` Bulk-Op Constraint

**`sortDictionaryEntries` bulk ops:** pass `null` as `changedKey` when modifying >1 entry — `IncrementalDictionarySorter.incrementalSort` only repositions ONE key per call; a non-null anchor silently drops the other N-1 entries from the persisted dict.

## `DictionaryContext.tsx` CRUD Audit Checklist

After touching any CRUD function or `useDictionaryHistory`, audit for:

1. Plans read dictionaries only through the plan's own `dicts` argument, inside the commit turn — never from a closure or `dictionariesRef` (`patchEntry`'s current value is the case that matters)
2. Typed error throws (`ValidationError`/`SaveError`) — an invalid plan becomes a `ValidationError` in `commitOrThrow`
3. Dep-array correctness
4. `isValidationError`/`isSaveError` double-toast guards — applies to `addEntry`/`updateEntry`/`patchEntry`/`deleteEntry`/`bulkDeleteEntries` only. `moveEntry`/`bulkMoveEntries` have no internal catch/toast at all, by design — `MoveDialog.tsx` owns error display for move ops via its own inline error banner (`handleMove`'s `catch` → `setError(...)`), not a toast. Tested as invariant I4 in `useDictionaryCRUD.test.ts` (`src/hooks/__tests__/`) — the move-op cases assert the inverse: zero toast calls on failure, so a future "helpful" toast added here doesn't double up with `MoveDialog`'s banner.
5. Metadata coverage (`allowAsPatternVariable`, `semanticType`, `allowedVariableTypes` for `phrases|patterns|properNouns-*`)
6. `prepareMutationEntry` called at the top of `addEntry`/`updateEntry` (inside the plan for `patchEntry`, which needs the current value first) — owns sanitize + validate + typed value construction. Throws `ValidationError` (no toast); catch block handles the toast via `isValidationError(error)` branch. Validation is `validatePersistEntry(dictionaryId, source, translation)` from `utils/dictionary/PersistTimeValidator` — NOT the form-time `validateDictionaryEntry` in `DictionaryEntryValidator.ts` (different signature, different return type).
7. Cache invalidation is `EditCommitter`'s, once per touched dictionary after a successful save, for CRUD and undo/redo alike — never call `invokeEngineInvalidator` from a CRUD method. `engineInvalidatorRef` is registered by `Translator.jsx` at engine-ready time.

**Guard helpers `requireDictionaryExists`/`failSave` deleted 2026-09-29**: the plans check that a dictionary exists (`{invalid}`), and `commitOrThrow` (`useDictionaryCRUD.ts`) types every outcome — `ValidationError` for an invalid plan (toasted there only for delete/bulkDelete, whose catch does not toast validation errors), `SaveError` for a failed save (toasted there unless the op is a move).

**The catch-guard asymmetry above was investigated as a follow-up and rejected (2026-09-09, same grilling).** Two unification directions exist, both worse than leaving it: (1) make the catch the single toast site — requires dropping `deleteEntry`'s `toast.warning(msg)` at its throw site in favor of catch-side `toast.error(error.message)`, silently changing the "entry not found" toast's severity styling from warning to error, since `ValidationError` carries no severity field to preserve the distinction; (2) make the throw site the single toast site — requires `prepareMutationEntry` itself to call `toast.error` before throwing, coupling a function whose own doc comment says "no toast — caller's catch block handles UI feedback" directly to the `toast` module, a real testability regression for the one function in this file that's currently pure-ish. (Since 2026-09-29 `bulkDeleteEntries`'s `!isValidationError` catch branch is live: `commitOrThrow` throws its invalid-plan `ValidationError` inside the `try`, after toasting it.) Do not re-propose unifying these two catch shapes without a way to resolve the severity/coupling trade-off first.

**One save protocol**: every CRUD method and undo/redo commits a Dictionary Edit through `EditCommitter` (`EditCommitter.ts`, built once by the provider; CONTEXT.md "Dictionary Edit", ADR-052) — one global queue, memory first, rollback plus write-back of saved dictionaries on a failed save. Callers own: input clean-up (`prepareMutationEntry`), the plan, and the toast.

**Load protocol**: Both `loadInitialState` (startup) and `loadDictionary` (single reload) delegate to `loadAllDictionaries()` in `src/utils/dictionary/DictionaryBackend.ts` (parallel batch + serial retry). Do NOT call `window.electronAPI.loadDictionary` directly — that path has no retry. Failure outcome classification lives in `classifyLoadResult` in `DictionaryLoadClassifier.ts`. See ADR-014.

`undo`/`redo` live in `src/components/dictionary/useDictionaryHistory.ts`: undo commits `invert(edit)`, redo the edit itself, through the same `EditCommitter`, which refuses one whose keys changed since. History is a ref (plus a version counter for `canUndo`/`canRedo`), so the cursor moves inside the commit turn.

## Error Handling

**The double-toast guard depends on throwing the right typed error class every time.** If a code path shows a toast then `throw new SaveError(...)`, the outer `catch` must guard with `!isValidationError(error) && !isSaveError(error)` before showing its own toast. Same failure mode from the other direction: pre-`try` existence checks (e.g. dict-not-found) that use bare `throw new Error(msg)` bypass the `!isValidationError` guard entirely — always `throw new ValidationError(msg)` there instead.

## Dictionary JSON Format: Two Tiers

**Pure lookup tables** (`characters`, `conversion`, `punctuation`): string values only, no metadata. The string branch in `DictionaryManager.js` is intentional — do NOT convert these to objects.

**Complex entry dicts** (`phrases`, `patterns`, `properNouns*`): values MUST be `DictionaryEntryValue` objects. `addEntry`/`updateEntry` always write objects (never strings). Any code iterating `DictionaryData` must guard: `typeof value === 'string' ? value : value.translation`.

## `VirtualRowComponent` Is at Module Scope

Lives in `VirtualRowComponent.tsx` (sibling file), imported by `EnhancedVirtualizedDictionaryTable`. Do NOT wrap in `useMemo` or move inside any render function — any dep change creates a new React component _type_, unmounting all rows and destroying inline edit state (`sourceEdit`/`translEdit` from `useInlineFieldEdit`). `ITEM_HEIGHT` is exported from `TableBuildingBlocks.tsx` (moved there 2026-09-09, architecture review grilling — its real owner is `RowShell`, which lives there too) — import it from there, not redeclared locally.

## Moving Entries — One Rule, Three Enforcement Points

`canMoveBetween(sourceId, targetId)` / `getMoveFamily(id)` (`DictionaryIdClassifier.ts`) is the only move rule: `patterns`/`patterns-f_*`/`patterns-_*` move among themselves; `phrases`/`properNouns*` move among themselves; `characters`/`conversion`/`punctuation` don't move at all (string-only tier — an object value moved in breaks the two-tier format above). Enforced in `useMoveTargetDictionaries` (dialog target list), EVDT's context menu (Move item disabled) plus `DictionaryManager`'s bulk Move button, and `moveEntry`/`bulkMoveEntries` (throws `ValidationError`, no disk write). Since every allowed move stays inside one value tier, the value is copied verbatim — there is no metadata loss to warn about. `MoveDialog` calls `loadDictionary` on a selected target that isn't in memory yet (fiction dicts load lazily), or the move throws "does not exist".

Context-menu actions carry the row's own `dictionaryId` (`ContextMenuEntry`) — never `selectedDictionary`, which is wrong for every duplicate-view row from another dictionary.

**One right-click menu, three views.** `EntryContextMenu.tsx` renders the `useContextMenu` result for the Dictionary tab's normal view, its duplicate view, and the Rules tab's Matches view (`showEdit={false}` there — fields edit inline). Delete is two-click (`confirmingDelete`). Any new view listing entries should render this component rather than a fourth copy of the menu markup.

What an entry can carry — the VAR toggle, a semantic type, X/Y variable types — is `entryCapabilities(id)` / `showsSemanticType(id, allowAsPatternVariable)` (`DictionaryIdClassifier.ts`; CONTEXT.md "Entry capabilities"). Every surface reads those: table rows and headers, filters (`availableFiltersFor`), the Duplicate view, the Add form's picker, Rule Matches. Kind checks (`isPatternsDict`, …) stay for layout — column classes, labels — but never decide a capability; a new "does this kind have X?" answer goes in the record, not in a component.

## `SemanticType` Canonical Values

Canonical values, in `SEMANTIC_TYPE_LIST` order: `'character'`, `'creature'`, `'location'`, `'organization'`, `'concept'`, `'object'` (UI abbreviations: CHA/CRE/LOC/ORG/CON/OBJ). That order is also the Add form's digit keys (`SemanticTypePicker`: 1-6, 0 None, then 7/8 `$X`/`$Y`) — inserting a type renumbers them. Dictionary JSON stores these strings directly — a stale value (e.g. old `'person'`/`'place'`) displays no badge and fails filter matching silently. Bulk-migrate with `scripts/migrate-semantic-types.py`.

- `SEMANTIC_TYPE_ABBREVIATIONS` and `SEMANTIC_TYPE_LIST` (from `src/constants/SemanticTypes.ts`) are the canonical exports for toggle cells in `EnhancedVirtualizedDictionaryTable.tsx` — do NOT redeclare local lists.
- `classifyVariableType` in `SemanticPatternProcessor.js` returns canonical values when `metadata.semanticType` is set, but falls back to internal discriminators (`'proper_noun'`, `'character_unit'`, `'unknown'`) that are NOT canonical — `'proper_noun'` is special-cased to `null` (always include); `'character_unit'` and `'unknown'` fail `allowedVariableTypes` constraints intentionally.

## `$X`/`$Y` Variable-Derived Semantic Types (Patterns Only)

Pattern `semanticType` accepts `"$X"` or `"$Y"` — resolved at WASM match time from the variable's cache `var_type`. Constants in `src/constants/SemanticTypes.ts`: `PATTERN_SEMANTIC_TYPE_REF_LIST`. UI: `SemanticTypePicker.tsx` (via `DictionaryEntry.tsx`) and `SemanticTypeToggleCell` in `EnhancedVirtualizedDictionaryTable.tsx` (inline column, patterns branch only — NOT phrases/properNouns branches).

Resolution edge cases: `$-ref` to non-existent variable (e.g. `"$Z"` in an X-only pattern) → `None` silently, no error. `$X` where var has `var_type: Some("proper_noun")` (JS non-canonical sentinel for untyped proper-noun entries) → `Some("proper_noun")`, NOT `None` — canonical `allowedVariableTypes` constraints (e.g. `["character"]`) won't match it.

## Pattern Variable Contract

X = optional 1st variable (0 or 1 — a 0-variable pattern is a literal, no-variable entry); Y = optional 2nd, but only meaningful alongside X. Y-only patterns (Y present, X absent) are intentionally invalid. Form-time (`DictionaryEntryValidator.ts`) and persist-time (`PersistTimeValidator.ts`) enforce **identical** rules as of 2026-09-07 — both delegate to `PatternEntryRules.ts`: no variable may repeat in source; variables must be introduced in order (Y requires X, Z requires Y); translation and source variable sets must match exactly, both directions. Before 2026-09-07 persist-time was looser (no ordering check, X/Y-only) — that asymmetry let a Z-variable or Y-without-X pattern pass the Quick-Add form's live check, then get rejected only at save. A 0-variable pattern is a deliberate, supported shape: it lets a literal pattern entry outrank a same-length variable pattern via `find_best_pattern_match`'s "fewer variables wins" tie-break (`wasm-core/src/pattern_processor/matcher.rs`) — see the 这种马上-vs-这X上 case (2026-08-29). Existing-entry suggestion (`handleTranslationFocus` → `checkForExistingEntry`) applies to patterns too (re-enabled 2026-08-10) — was previously suppressed via an `activeDictionary.startsWith('patterns')` guard with no recorded rationale; removed since it left same-dict pattern overwrites completely silent, unlike every other dict type.

**`checkVariableSymmetry`'s `extractPatternVariables` is `isVariableChar`-based**, so a variable letter fused into fixed text (e.g. `X` inside `Xích`) never counts toward either side's set — a translation whose only occurrence of a declared variable is fused (e.g. a missing-space typo) already fails symmetry and is blocked today. Confirm this doesn't already cover a proposed new template-safety check before building one (confirmed redundant 2026-09-10).

## Dictionary Type Classification

Use the kind predicates (`isPatternsDict`/`isPhrasesDict`/`isProperNounsDict`/`isLookupTableDict`) and `tierOf(id)` from `DictionaryIdClassifier.ts` for every kind or tier question (vocabulary in `CONTEXT.md` "Dictionary Kind / Dictionary Tier"). Never compare `kindOf(id)` to a literal at a call site — `kindOf(id) === 'patterns'` reads the same as a raw id check. `isPatternsDict` is true for both `'patterns'` and `'patterns-f_*'`; raw equality misses fiction variants and silently breaks on every dict-type extension, with no error anywhere — the UI just treats a fiction dict as some other type. Same reasoning for the fiction-prefix checks `isFictionProperNounsId(id)`/`isFictionPatternsId(id)`, for the pairing checks `hasPairedPatterns(id)`/`isPairedPatternsId(id)` (fiction or generic tier, ADR-048), for the ADR-027 pairing derivations `toPatternsId(properNounsId)`/`toProperNounsId(patternsId)`, and for `toProperNounsDictionaryId(rawName)` (create/rename forms; added 2026-08-28 architecture review candidate #4 grilling). All are pure transforms — the Rust side (`validate_dictionary_id`) is the real authority on ID safety.

You no longer have to remember any of that: `SourceConventionScan.test.js` fails on raw `=== 'patterns'`, on a raw kind-prefix check `startsWith('patterns…')`/`startsWith('properNouns…')` (added 2026-09-26 after migrating 20 of them), on a hand-rolled `startsWith('properNouns-f_')`/`'patterns-f_'`, and on a hand-rolled `'patterns-' + …` / `` `properNouns-${…}` ``, repo-wide, with `DictionaryIdClassifier.ts` itself as the only exemption. The class was real — found duplicated at 10 call sites across 5 files (2026-07-28) — and stood at zero when the gate went in, so it is a zero-tolerance ceiling rather than a baseline.

**`=== 'phrases'` is deliberately not covered** — ruled out 2026-08-31. Fiction dicts exist only as `properNouns-f_*` and `patterns-f_*`, so `'phrases'` has no variant to miss and the nine live comparisons across `src/` are correct. Widening the detector to it would be nine false positives on day one. Reverse this only if a `phrases-f_*` dictionary type is ever introduced.

## Fiction Pattern Merge Order Is Load-Bearing

`FictionDictionaryFilter.ts`'s conflict merge must spread global `patterns` FIRST, generic entries next, fiction entries LAST (`{ ...global, ...generic, ...fiction }`) so fiction wins on a same-template conflict (ADR-027, ADR-048). The reverse order was a live bug until 2026-07-16 — silently let global patterns override fiction-specific ones with no error. Verify with a same-key conflict test before touching this line again.

**A real `<table>`'s `<tr>` `height` is a minimum, not a cap** — content padding/line-height can still force it taller. To match Dictionary's exact row density, don't build a `<table>`; use `RowShell`'s fixed-height flex-div technique instead (same mechanism `EnhancedVirtualizedDictionaryTable` itself uses). Setting `height: 40px` on a `<tr>` and expecting Dictionary-identical row height is a no-op if the cell content needs more room.

**Testing a `RowShell`-based row directly** (not through its parent table): `RowShell` renders a plain `<div role="row">`, not a real `<tr>` — render the component directly, don't wrap it in `<table><tbody>`. That wrapping is invalid DOM nesting (div inside tbody) and buys nothing; `role="row"`/`role="cell"` ARIA attributes work with `getByRole` without real table markup. Found writing `RuleRow.test.tsx` (2026-08-12).

## WASM Wrapper Methods

**Must check `initialize()` return value**: `if (!this.initialized) { const ok = await this.initialize(); if (!ok) return false; }` — skipping `if (!ok)` causes `this.processor.*` to throw TypeError when `this.processor` is null after failed init.
