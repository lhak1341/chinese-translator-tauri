# src/components/dictionary — Gotchas

## `sortDictionaryEntries` is stateless

**`sortDictionaryEntries(dictionary)`** is one full sort with no cache and no hint. Do not give it a per-dictionary memory of the last result: a failed save rolls a dictionary back outside the sorter, so a cache would hand the failed value to the next commit (see `docs/guides/deleted-symbols.md`, `IncrementalDictionarySorter`).

## `DictionaryContext.tsx` CRUD Audit Checklist

After touching any CRUD function or `useDictionaryHistory`, audit for:

1. Plans read dictionaries only through the plan's own `dicts` argument, inside the commit turn — never from a closure or the provider's `dictionaries` (`patchEntry`'s and `renameEntry`'s current value is the case that matters)
2. Typed error throws (`ValidationError`/`SaveError`) — an invalid plan becomes a `ValidationError` in `commitOrThrow`
3. Dep-array correctness
4. The `fail` catch (see `CommitFeedback.ts` below) — applies to `addEntry`/`updateEntry`/`patchEntry`/`renameEntry`/`bulkDeleteEntries` only. `moveEntries` has no internal catch/toast on failure at all, by design — `MoveDialog.tsx` owns error display for move ops via its own inline error banner (`handleMove`'s `catch` → `setError(...)`), not a toast. Tested as invariant I4 in `useDictionaryCRUD.test.ts` (`src/hooks/__tests__/`) — the move-op cases assert the inverse: zero toast calls on failure, so a future "helpful" toast added here doesn't double up with `MoveDialog`'s banner.
5. Metadata coverage (`allowAsPatternVariable`, `semanticType`, `allowedVariableTypes` for `phrases|patterns|properNouns-*`)
6. Sanitize + validate + typed value construction live in `planAdd`/`planUpdate` (`DictionaryEdit.ts`), so `addEntry`, `updateEntry`, `patchEntry` and `renameEntry` pass raw fields and an invalid entry comes back as an invalid plan, which `commitOrThrow` throws as a `ValidationError` (no toast; the `fail` catch toasts it). Validation is `validatePersistEntry(dictionaryId, source, translation)` from `utils/dictionary/PersistTimeValidator` — the same `checkEntry` the Add/Edit form calls (`DictionaryEntryValidator.ts` was deleted 2026-10-03), so the character rule holds on add, update, patch and rename. Moves write no new value: `planMove` is gated by `canMoveBetween`, which refuses a move into a lookup table, so nothing validates there.
7. No engine call. An edit never reaches the running engine; it shows in translations after a rebuild (Cmd/Ctrl-R or a binding change). Do not re-add a per-dictionary cache invalidation after a commit: the engine's lookups are fixed at `initialize`, so it has nothing to clear (ADR-106).

**Guard helpers `requireDictionaryExists`/`failSave` deleted 2026-09-29**: the plans check that a dictionary exists (`{invalid}`), and `commitOrThrow` (`useDictionaryCRUD.ts`) types every outcome — `ValidationError` for an invalid plan, `SaveError` for a failed save (toasted there unless the op is a move).

**Who toasts what is `CommitFeedback.ts`'s, decided 2026-10-03 (architecture review candidate #2 grilling).** It is pure — `describeFreshFailure` (a CRUD commit), `describeReplayFailure` (undo/redo), `describeOperationError` (a thrown error) each return a `Feedback` (`{ level, message }`) or `null`, and the caller toasts it. Every CRUD catch is `fail(error, verb, logMessage)`: a `ValidationError` is toasted once, at its own `severity`; a `SaveError` says nothing (`commitOrThrow` already toasted it); anything else is `Could not <verb>: …`. `commitOrThrow` no longer toasts an invalid plan (the `toastInvalid` flag is gone). The half-applied advice is one sentence shared by CRUD and history. Undo/redo with nothing to undo is silent on purpose (`canUndo` gates the UI). `refused` keeps two wordings because it means two things: a fresh plan's is a bug, a replayed one's is a stale edit.

**The 2026-09-09 rejection of unifying the two catch shapes is superseded by this.** Its two objections were severity (a delete's "not found" is a warning, a `ValidationError` carried no severity) and coupling (the entry preparation would have had to toast). `ValidationError` now carries `severity` (default `'error'`; a delete's miss is `'warning'`), and the plans stay free of `toast` — only the catch toasts.

**One save protocol**: every CRUD method and undo/redo commits a Dictionary Edit through the `EditCommitter` interface, which the Dictionary Store satisfies (GLOSSARY.md "Dictionary Edit", "Dictionary Store"; ADR-052, ADR-055) — memory first, rollback plus write-back of saved dictionaries on a failed save. Callers own: input clean-up (`prepareMutationEntry`), the plan, and the toast. One user action is one commit: a plan may span dictionaries (`planMove`, `planDelete` over `EntryRef`s), so never loop commits per dictionary — that splits undo and leaves part of the action on disk (ADR-052 addendum 2026-10-21).

**One queue for every write to the dictionaries in memory** (`DictionaryStore.ts`, ADR-055): commits, the startup load, reloads, renames, force reload and import (including the import IPC itself: `importAll`, via the `importFiles` dep — a component never calls `importDictionaries` and then reloads). Never write the provider's dictionaries any other way — no `setState` beside the store, no second loader. A new IPC command that changes dictionary files becomes a store operation. Memory is the source of truth: do not re-read a dictionary from disk on selection.

**After awaiting a store operation, read the store, not the render.** `dictionaries` from `useDictionary()` (and any ref mirroring it) is the last render's snapshot; a rename or load that just resolved is in `getDictionaries()` (the store's own snapshot) before React re-renders. Engine rebuilds in async sequences use it — `moveDictionaryTier` rebuilt the promoted pair under its old id and fiction priority otherwise.

**Load protocol**: every Dictionary Store load (startup, reload, rename, force reload, import) goes through `loadAllDictionaries()` in `src/utils/dictionary/DictionaryBackend.ts` (parallel batch + one batched retry), injected as the store's `load`. Do NOT call `window.electronAPI.loadDictionariesParallel` directly — that path has no retry. Failure outcome classification lives in `classifyLoadResult` in `DictionaryLoadClassifier.ts`. See ADR-014. The store runs it on every full load and keeps the result as the snapshot's `lastLoad`; `loadError` and the load-failure toast are rendered from that, never set by a caller (ADR-072 addendum 2026-10-21).

**A dictionary that fails to load is absent, never `{}`** (GLOSSARY.md "Unread dictionary", ADR-053). It is listed in the provider's `unreadDictionaryIds`, and every plan refuses it because it is not in memory. Do not add a `dictionaries[id] ?? {}` fallback on any path that can reach a save: that rebuilds the placeholder that let an Add save a one-entry file over an unread one. A missing file is not a failure; the parallel loader returns `{}` for it.

`undo`/`redo` live in `src/components/dictionary/useDictionaryHistory.ts`: undo commits `invert(edit)`, redo the edit itself, through the same store queue, which refuses one whose keys changed since. History is a ref (plus a version counter for `canUndo`/`canRedo`), so the cursor moves inside the commit turn.

**The Dictionary tab's selector filters with `quickAddChoices`, over `loadQuickAddView()`** (GLOSSARY.md "Quick-add choices"). Do not re-add a filter over `loadAppConfig().engine.activeProperNouns`: config is only a cache of what the open book's binding implies, and the old copy of the rule hid the selected dictionary whenever it was not active in config, so the `<select>` showed a different dictionary from the table.

## Error Handling

**The single-toast rule depends on throwing the right typed error class every time.** A `SaveError` is toasted where it is thrown, and `fail` skips it; a `ValidationError` is never toasted where it is thrown, and `fail` shows it. Same failure mode from the other direction: pre-`try` existence checks (e.g. dict-not-found) that use bare `throw new Error(msg)` land in `fail`'s `Could not <verb>: …` branch instead of showing the message as a validation error — always `throw new ValidationError(msg)` there instead.

## Dictionary JSON Format: Two Tiers

**Pure lookup tables** (`characters`, `conversion`, `punctuation`): string values only, no metadata. The string branch in `DictionaryManager.js` is intentional — do NOT convert these to objects.

**Complex entry dicts** (`phrases`, `patterns`, `properNouns*`): values MUST be `DictionaryEntryValue` objects. `addEntry`/`updateEntry` always write objects (never strings). Any code iterating `DictionaryData` must guard: `typeof value === 'string' ? value : value.translation`.

## `VirtualRowComponent` Is at Module Scope

Lives in `VirtualRowComponent.tsx` (sibling file), imported by `DictionaryTableView` (the per-dictionary view inside `EnhancedVirtualizedDictionaryTable`). Do NOT wrap in `useMemo` or move inside any render function — any dep change creates a new React component _type_, unmounting all rows and destroying inline edit state (`sourceEdit`/`translEdit` from `useInlineFieldEdit`). `ITEM_HEIGHT` is exported from `TableBuildingBlocks.tsx` (moved there 2026-09-09, architecture review grilling — its real owner is `RowShell`, which lives there too) — import it from there, not redeclared locally.

## Moving Entries — One Rule, Three Enforcement Points

`canMoveBetween(sourceId, targetId)` / `getMoveFamily(id)` (`DictionaryIdClassifier.ts`) is the only move rule: `patterns`/`patterns-f_*`/`patterns-_*` move among themselves; `phrases`/`properNouns*` move among themselves; `characters`/`conversion`/`punctuation` don't move at all (string-only tier — an object value moved in breaks the two-tier format above). Enforced in `useMoveTargetDictionaries` (dialog target list), EVDT's context menu (Move item disabled) plus `DictionaryManager`'s bulk Move button, and `moveEntries` (throws `ValidationError`, no disk write). Since every allowed move stays inside one value tier, the value is copied verbatim — there is no metadata loss to warn about. `MoveDialog` calls `loadDictionary` on a selected target that isn't in memory (an unread one — every other is loaded at startup), or the move throws "does not exist".

Context-menu actions carry the row's own `dictionaryId` (`ContextMenuEntry`) — never `selectedDictionary`, which is wrong for every duplicate-view row from another dictionary.

**One right-click menu, three views.** `EntryContextMenu.tsx` renders the `useContextMenu` result for the Dictionary tab's normal view, its duplicate view, and the Rules tab's Matches view (`showEdit={false}` there — fields edit inline). Delete is two-click (`confirmingDelete`). Any new view listing entries should render this component rather than a fourth copy of the menu markup.

What an entry can carry — the VAR toggle, a semantic type, X/Y variable types — is `entryCapabilities(id)` / `showsSemanticType(id, allowAsPatternVariable)` (`DictionaryIdClassifier.ts`; GLOSSARY.md "Entry capabilities"). Every surface reads those: table rows and headers, filters (`availableFiltersFor`), the Duplicate view, the Add form's picker, Rule Matches. Kind checks (`isPatternsDict`, …) stay for layout — column classes, labels — but never decide a capability; a new "does this kind have X?" answer goes in the record, not in a component. A row renders what an entry can carry through `EntryCells.tsx` (`EntryVarCell`, `EntrySemanticCell`, `EntryTypeCells`, `entryPatcher`), never a hand-rolled badge or `patchEntry(...).catch` — GLOSSARY.md "Entry cells". A new view listing entries uses them; pass `mixedKinds` when its rows can come from dictionaries of different kinds.

## `SemanticType` Canonical Values

Canonical values, in `SEMANTIC_TYPE_LIST` order: `'character'`, `'creature'`, `'location'`, `'organization'`, `'concept'`, `'object'` (UI abbreviations: CHA/CRE/LOC/ORG/CON/OBJ). That order is also the Add form's digit keys (`SemanticTypePicker`: 1-6, 0 None, then 7/8 `$X`/`$Y`) — inserting a type renumbers them. Dictionary JSON stores these strings directly — a stale value (e.g. old `'person'`/`'place'`) displays no badge and fails filter matching silently. Bulk-migrate with `scripts/migrate-semantic-types.py`.

- `SEMANTIC_TYPE_ABBREVIATIONS` and `SEMANTIC_TYPE_LIST` (from `src/constants/SemanticTypes.ts`) are the canonical exports for toggle cells in `EnhancedVirtualizedDictionaryTable.tsx` — do NOT redeclare local lists.
- `classifyVariableType` in `VariableTypeClassifier.ts` returns canonical values when `metadata.semanticType` is set, but falls back to internal discriminators (`'proper_noun'`, `'character_unit'`, `'unknown'`) that are NOT canonical — `'proper_noun'` is special-cased to `null` (always include); `'character_unit'` and `'unknown'` fail `allowedVariableTypes` constraints intentionally.

## `$X`/`$Y` Variable-Derived Semantic Types (Patterns Only)

Pattern `semanticType` accepts `"$X"` or `"$Y"` — resolved at WASM match time from the variable's cache `var_type`. Constants in `src/constants/SemanticTypes.ts`: `PATTERN_SEMANTIC_TYPE_REF_LIST`. UI: `SemanticTypePicker.tsx` (via `DictionaryEntry.tsx`) and `SemanticTypeToggleCell` in `EnhancedVirtualizedDictionaryTable.tsx` (inline column, patterns branch only — NOT phrases/properNouns branches).

Resolution edge cases: `$-ref` to non-existent variable (e.g. `"$Z"` in an X-only pattern) → `None` silently, no error. `$X` where var has `var_type: Some("proper_noun")` (JS non-canonical sentinel for untyped proper-noun entries) → `Some("proper_noun")`, NOT `None` — canonical `allowedVariableTypes` constraints (e.g. `["character"]`) won't match it.

## Pattern Variable Contract

X = optional 1st variable (0 or 1 — a 0-variable pattern is a literal, no-variable entry); Y = optional 2nd, but only meaningful alongside X. Y-only patterns (Y present, X absent) are intentionally invalid. The form and every write share one validator (`PersistTimeValidator.ts`'s `checkEntry`, as of 2026-10-03), which delegates to `PatternEntryRules.ts`: no variable may repeat in source; variables must be introduced in order (Y requires X, Z requires Y); translation and source variable sets must match exactly, both directions. Before 2026-09-07 persist-time was looser (no ordering check, X/Y-only) — that asymmetry let a Z-variable or Y-without-X pattern pass the Quick-Add form's live check, then get rejected only at save. A 0-variable pattern is a deliberate, supported shape: it lets a literal pattern entry outrank a same-length variable pattern via `find_best_pattern_match`'s "fewer variables wins" tie-break (`wasm-core/src/pattern_processor/matcher.rs`) — see the 这种马上-vs-这X上 case (2026-08-29). Existing-entry suggestion (`handleTranslationFocus` → `checkForExistingEntry`) applies to patterns too (re-enabled 2026-08-10) — was previously suppressed via an `activeDictionary.startsWith('patterns')` guard with no recorded rationale; removed since it left same-dict pattern overwrites completely silent, unlike every other dict type.

**`#o` is a translation-only spelling.** The source side writes `#` (`第#章`); the translation writes `#` for the cardinal or `#o` for the ordinal (`nhất`/`tư` for 1/4, else the cardinal), e.g. `thứ #o`. Putting `#o` in the source makes `o` a literal letter that never matches. Mechanism: `wasm-core/CLAUDE.md`.

**`checkVariableSymmetry`'s `extractPatternVariables` is `isVariableChar`-based**, so a variable letter fused into fixed text (e.g. `X` inside `Xích`) never counts toward either side's set — a translation whose only occurrence of a declared variable is fused (e.g. a missing-space typo) already fails symmetry and is blocked today. Confirm this doesn't already cover a proposed new template-safety check before building one (confirmed redundant 2026-09-10).

## Dictionary Type Classification

Use the kind predicates (`isPatternsDict`/`isPhrasesDict`/`isProperNounsDict`/`isLookupTableDict`) and `tierOf(id)` from `DictionaryIdClassifier.ts` for every kind or tier question (vocabulary in `GLOSSARY.md` "Dictionary Kind / Dictionary Tier"). Never compare `kindOf(id)` to a literal at a call site — `kindOf(id) === 'patterns'` reads the same as a raw id check. `isPatternsDict` is true for both `'patterns'` and `'patterns-f_*'`; raw equality misses fiction variants and silently breaks on every dict-type extension, with no error anywhere — the UI just treats a fiction dict as some other type. Same reasoning for the fiction-prefix checks `isFictionProperNounsId(id)`/`isFictionPatternsId(id)`, for the pairing checks `hasPairedPatterns(id)`/`isPairedPatternsId(id)` (fiction or generic tier, ADR-048), for the ADR-027 pairing derivations `toPatternsId(properNounsId)`/`toProperNounsId(patternsId)`, and for `toProperNounsDictionaryId(rawName)` (create/rename forms; added 2026-08-28 architecture review candidate #4 grilling). All are pure transforms — the Rust side (`validate_dictionary_id`) is the real authority on ID _safety_; what an id may _be_ is `isValidDictionaryId` (ASCII letters, digits, `_ . -`, at most 100), which every IPC wrapper and the create/rename forms (`dictionaryNameProblem`) ask. Rust is looser on purpose and must not tighten (ADR-060 addendum 2026-10-03).

You no longer have to remember any of that: `SourceConventionScan.test.js` fails on raw `=== 'patterns'`, on a raw kind-prefix check `startsWith('patterns…')`/`startsWith('properNouns…')` (added 2026-09-26 after migrating 20 of them), on a hand-rolled `startsWith('properNouns-f_')`/`'patterns-f_'`, and on a hand-rolled `'patterns-' + …` / `` `properNouns-${…}` ``, repo-wide, with `DictionaryIdClassifier.ts` itself as the only exemption. The class was real — found duplicated at 10 call sites across 5 files (2026-07-28) — and stood at zero when the gate went in, so it is a zero-tolerance ceiling rather than a baseline.

**`=== 'phrases'` is deliberately not covered** — ruled out 2026-08-31. Fiction dicts exist only as `properNouns-f_*` and `patterns-f_*`, so `'phrases'` has no variant to miss and the nine live comparisons across `src/` are correct. Widening the detector to it would be nine false positives on day one. Reverse this only if a `phrases-f_*` dictionary type is ever introduced.

## Fiction Pattern Merge Order Is Load-Bearing

`FictionDictionaryFilter.ts`'s conflict merge must spread global `patterns` FIRST, generic entries next, fiction entries LAST (`{ ...global, ...generic, ...fiction }`) so fiction wins on a same-template conflict (ADR-027, ADR-048). The reverse order was a live bug until 2026-07-16 — silently let global patterns override fiction-specific ones with no error. Verify with a same-key conflict test before touching this line again.

## `DictionaryInfo` Name Collision

`DictionaryTypes.ts` has a LOCAL `interface DictionaryInfo { label, description }` — display-only type for dictionary type metadata. NOT the same as `ComponentTypes.d.ts::DictionaryInfo { id, name, path, isActive, ... }` which is the API/IPC type used by `ElectronTypes.d.ts`. Do not re-export the local one, do not merge the two. Import `DictionaryInfo` from `../../types/ComponentTypes` for the API type.

Zero hits, even at `top: 200`. Its clone detector doesn't fire at the scale of a single small React component. No cheap mechanized gate exists for this failure class — the discipline documented in this section (review + this file) is the real, and only, lever. Do not re-propose a fallow/regex gate here without a new detection approach — the ones tried are ruled out, not merely undone.

**A real `<table>`'s `<tr>` `height` is a minimum, not a cap** — content padding/line-height can still force it taller. To match Dictionary's exact row density, don't build a `<table>`; use `RowShell`'s fixed-height flex-div technique instead (same mechanism `EnhancedVirtualizedDictionaryTable` itself uses). Setting `height: 40px` on a `<tr>` and expecting Dictionary-identical row height is a no-op if the cell content needs more room.

**Testing a `RowShell`-based row directly** (not through its parent table): `RowShell` renders a plain `<div role="row">`, not a real `<tr>` — render the component directly, don't wrap it in `<table><tbody>`. That wrapping is invalid DOM nesting (div inside tbody) and buys nothing; `role="row"`/`role="cell"` ARIA attributes work with `getByRole` without real table markup.
