# src/components — Gotchas

## Every tab is mounted at once

`TabbedInterface` toggles tabs with CSS `visibility`, never conditional render, and everything below follows from that.

**Anything listening globally must be gated by tab identity.** `useHotkeyHandler` has three call sites — `TabbedInterface.tsx` (tab switching + Dictionary-tab shortcuts), and `Translator.jsx` and `reader/BookReader.tsx` via `<HotkeyHandler>` — and all three listen at once. Each passes its own tab id (`undefined` while it is the background tab); a handler registered without that gate fires from a hidden tab. Add Dictionary-tab hotkeys to `TabbedInterface`, per-tab ones to that tab's `HotkeyHandler` props.

**One action, one call site.** `Cmd+B` (`bindDictionaries`) is registered in `TabbedInterface`, so also passing `onBindDictionaries` to `BookReader`'s `<HotkeyHandler>` fires `openDialog` twice on one press — grep the action name before wiring a handler prop.

**A hidden tab is still reachable, but its modals are not.** A hotkey can drive another mounted tab's component imperatively via `forwardRef`/`useImperativeHandle` (`RulesManagerHandle`, following the older `dictionarySearchRef` precedent) without a second instance of its state hooks. Any modal opened that way must render via `createPortal(..., document.body)` — a nested overlay inherits `visibility: hidden` from the still-hidden tab-panel ancestor despite `position: fixed`.

**Bindings live in one table and are copied nowhere.** Key→action dispatch is `src/utils/ui/HotkeyDispatchTable.ts` (`matchHotkey`) — change shortcuts there, not in the hook body. The hook keeps only _which tabs a quick-add-shaped action is allowed on_ (`QUICK_ADD_TABS`/`NEW_RULE_TABS`), because `matchHotkey` is pure and cannot know whether a callback is wired. Tab shortcuts are the exception: `src/constants/tabs.ts`'s `TAB_ORDER` is their single source — nav bar and `Option/Alt+digit` both derive from it by index. Anything that _displays_ a binding (the Reader's palette hints, `docs/HOTKEYS.md`) is a second copy of the table: assert it against `matchHotkey` (`PaletteCommands.test.ts` parses each hint back into its keypress), or the UI advertises a dead key. Bindings stay pinned literally in `HotkeyDispatchTable.test.ts` on purpose — they live in muscle memory, so a reorder must fail a test rather than silently follow the array.

**Option/Alt-modified digit hotkeys must match `event.code` (`'Digit1'`…), never `event.key`** — macOS remaps Option+digit per keyboard layout (Option+1 → `¡` on US), so `.key` matching silently breaks for most users.

## One owner per concern

Every entry below is the same rule: a concern has exactly one owner, and a second copy — a re-declared type, a re-derived style, an inlined helper, a caller reaching past the owner's API — drifts from it silently. Use the named ops; never reach into an owner's internal state or refs.

## The JS↔TS boundary is unchecked in both directions

`checkJs: false`, so nothing verifies a TypeScript declaration against the JavaScript it describes. Three shapes of the same silent drift:

- **Imports.** `Translator.jsx` is JavaScript, so `type-check` will not catch a stale import there — grep it after renaming any exported utility. Known renames: `validateApiResult` (was `validateElectronResult`) and `validateRawDictionaryEntry` (was `validateDictionaryEntry`), both in `configValidation.ts`; the second was renamed to avoid colliding with the same-named function in `DictionaryTypes.ts`, so do NOT revert it.
- **Prop types.** A `.tsx` file's prop type for a value that is really a `.jsx` function (`Translator.jsx`'s handlers) is checked against nothing, and drifts until something removes the permissive type tolerating it — narrowing a union, typically. After narrowing any handler type, run `bun run type-check` and expect stale declarations in `.tsx` callers, not just at the type's own definition.
- **Hand-written `.d.ts` files.** `EngineContext.d.ts` exists because `createContext(undefined)` makes `useEngine()` destructure `never` in a `.tsx` file; nothing checks it against the provider, so a key added to the provider's `value` must be added there by hand. And an `as any` at the first consumer hides a wrong declaration from the second: `TranslationResult.prebuiltSegments` is declared `TranslationSegment[]`, but what fills it is `matchWordSegments`, whose output is `WordSegment[]` (offsets plus a unit index, no `originalStart`) — `TranslatorDisplayPanels.tsx` casts it away, so the Reader had to assert the real shape. Trace the producer, don't trust the declaration.

TypeScript's own narrowing has two traps here: an optional property accessed through an `&&` spread widens (`SemanticType` → `string`) — extract a local or assign imperatively (`if (metadata.semanticType) entry.semanticType = metadata.semanticType`); and an inline array literal passed to a generic component's prop (`<Foo<T> options={[{value:'x',…}]} />`) widens narrow-union `value` fields to their base type unless the array carries `as const`, compiling standalone and failing only at the generic call site.

## Frequently-updating values travel by ref, not by dep array

Never list frequently-updating state or callback props in a `useEffect` dep array that creates a `setInterval` or `addEventListener` — the subscription is torn down and rebuilt on every update. Use `const ref = useRef(value); ref.current = value;` and read `ref.current` inside the callback (`wasmStatus`'s interval in `Translator.jsx`; `useHotkeyHandler.ts`'s keydown listener, whose props are all mirrored into one `optionsRef` rather than per-prop refs).

**The same refs are invisible to `React.memo`, so a memoized child needs every input it renders from as an actual prop.** A getter that is stable by design (`useCallback(…, [])` reading through a ref) cannot signal that its data changed, and state read off a stable object inside the child — `virtualizer.getVirtualItems()` — is not in the props comparison at all, so the child stops re-rendering on scroll. Both bit `ReaderPanel` in one change: the rendered range and total size became props, and an explicit `contentVersion` counter (`useWindowedTranslation`'s `version`) is what tells it a chunk landed. Before memoizing, list what the component reads that no prop describes. The inverse also defeats it: a prop that changes on every scroll step (a slice-local index, an `isScrolling` flag) re-renders every memoized row per step — `VirtualRowComponent` carried both, unused, until 2026-09-25.

**A ref mirror of the listener's props is not enough when the mirrored callback closes over state itself.** `goToChapter` in `BookReader.tsx` asks `useReadingAnchor`'s `readLine()` rather than using the `anchorLine` it closed over, because a key-repeated `]` can fire before React re-renders from the first press, and `optionsRef` would hand the listener that stale closure.

**The same applies to `useCallback` with a mutable state dep**: a `Set` in state is a new reference on every `setState`, so the callback recreates on every update. Ref mirror, dep array `[]`.

**State set inside a `useEffect` must not appear in its deps** — a flag reset in the effect body and listed as a dep re-triggers the effect.

**Two async fetches keyed by the same identifier can race.** A same-key check cannot tell which one _started_ more recently. Guard with a shared `requestIdRef` counter incremented per fetch and applied only if it still matches on resolution — `useChapterOutline.ts`'s mount fetch and `setOverride` fetch both write `headers` for one fingerprint, and without it a slow mount fetch silently clobbers the user's choice.

**eslint's `exhaustive-deps` only sees a dependency it can read syntactically at the call site** — a ref from a custom hook, or a callback built by a factory function, are both invisible to it. A ref returned by a custom hook (not `useRef` in the same component) needs listing in the dep array by hand — it's as stable as any other ref (`useReaderPanel`'s `scrollRef`, consumed by `useReaderPanels.ts`). `useCallback(factoryCall(...), deps)` warns "pass an inline function instead" even with a correct deps array, because the first arg isn't a literal — `useMemo(() => factoryCall(...), deps)` keeps the same identity while giving the linter a literal to scan. For a factory whose result never needs rebuilding, `useState(() => factoryCall(...))` sidesteps the dep array entirely (`useReaderEngine`).

## React state updater rules

**Never `throw` inside a state updater** (`setState(prev => { throw … })`): React 18 Concurrent Mode may call updaters more than once, and throws bypass the `await` chain. Do existence checks on the closed-over variable before `setState`.

**Never assign a `let` inside an updater for use outside it** — it may run twice. Compute from the closed-over snapshot first. For undo/redo-style history read a ref's `.current` directly instead of a closure variable (dictionary undo/redo uses `dictionariesRef.current`; `bulkDeleteEntries` computes `oldData`/`sortedDictionary` before calling `setDictionaries`).

## Context providers

A `createContext` provider's `value` must be wrapped in `useMemo`, and every function inside it — including ones returned by a wrapped hook, not just locally declared ones — must be `useCallback`-stable, or the memoization is defeated at its root and every consumer re-renders whenever the provider does. `DictionaryContext.tsx` does this correctly; `EngineContext.jsx` initially didn't, because the convention lives at the return statement rather than at the exports.

**A provider mounted above `TabbedInterface` is a test change too, and its failures point at the wrong file.** Components here render in isolation with their contexts `vi.mock`ed, so a new provider obligates a mock in every test file rendering a consumer, and that mock must return _every_ field consumers destructure. A missing field is spread inside the consumer's own `useMemo`, so the stack blames the consumer rather than the mock. `BookBindingContext` hit both halves: two test files needed new mocks, then a later field addition failed 16 tests pointing at `useDictionaryConfigManagement.ts`.

## Appearance travels as CSS variables, never as state

`useAppearanceSettings` is called only from `AppearanceManager.tsx`; everything else receives appearance as custom properties written to `document.documentElement` by `applyAppearanceToCssVars` (ADR-024). Two consequences. **Anything the browser re-renders needs no wiring** — `Translator.jsx`'s `sharedTextStyle`/`inputTextStyle`/`outputTextStyle`/`characterOnlyTextStyle` are `var(…)` strings with deps `[]`, static constants rather than values derived from `appearance`; do not move them into the hook. **Anything measuring in JS must watch for the write itself** — a font change leaves every box exactly as wide as it was, so `ResizeObserver` reports nothing and a cached measurement keeps the old geometry (`useAppearanceVersion` watches the root style attribute; `useColumnMetrics` re-measures; `ReadingAnchor` drops the Reader virtualizers' caches and restores the anchor — deferred to the Reader's return, since the Appearance tab is where the font changes and a hidden panel measures as zero-height). Matching the Translator's typography means reading those inline objects — `lineHeight: '1.5'`, `fontSize: '1.25rem'`, `padding: '1.5rem'` — plus `.panel` in `TranslatorDisplayPanels.module.css` (`--surface-color`, 1px `--border-color`, `--radius-lg`, 1rem inset); the CSS modules alone do not carry them.

## Engine lifecycle — `EngineContext` / `useEngine()`

The engine is constructed once above the tab container (`App.jsx` wraps `<TabbedInterface>` in `<EngineProvider>`), not owned by `Translator.jsx`. **Only one may exist at a time**: the WASM pattern/number processors are module-scope singletons, so a second live engine silently shares state with the first. Consume it via `useEngine()` (which throws outside `EngineProvider`); never call `useTranslatorEngine`/`useEngineReinitializer` from a tab component — that builds a second, unshared engine. `EngineProvider` also wraps its children in `ErrorBoundary`, at the provider rather than around `<Translator>`, since an init failure is now shared by every tab.

The exposed fields are listed in `EngineContext.d.ts`. What that file cannot tell you:

- **`engineVersion` increments once per successfully constructed engine** (mount and every `reinitialize()`) and is the cache-invalidation signal for anything holding translated output — nothing inside the engine survives reinitialization. It counts engine constructions, not dictionary edits: a dictionary edited on disk without a reload does not bump it, correctly, because the running engine has not seen that edit either.
- **`reinitialize(rawDicts, options)`** never throws — errors land in `enginePhase`/`initError`. Pass raw, unfiltered dicts; the hook filters internally. Non-React callers check `engineRef.current?.isReady()` after awaiting it, since `enginePhase` is async state they cannot read.
- **`reinitializeEngine` is the one to call from `Translator.jsx`** — `reinitialize` wrapped by `useEngineReinitializer`, which awaits it and then fires the fire-and-forget WASM dictionary-sync validation. `useForceReloadContext`/`useForceReload` consume this one.
- **Destroy-before-replace is structural, not a convention.** `useTranslatorEngine`'s `runEngineInit` destroys the outgoing engine before constructing its replacement, on the mount path and every `reinitialize()` — not only on the `useForceReload` path that also calls `destroyEngine()` first. A throwing `destroy()` is caught and logged, never blocking the replacement.
- **The init lock lives in `reinitialize`**, which sets `isInitializingRef.current = true` synchronously on entry while the init effect checks `enginePhase === 'loading' && !isInitializingRef.current`. `handleForceReload` must NOT add a lock of its own.
- **`ENGINE_PRIORITIES`** is defined and exported by `useTranslatorEngine.js` and passed to both `reinitialize()` and the hook's own init — change priorities there only.
- **Post-ready setup** (engine stats, debounced callbacks, dev tools) happens in a `useEffect([enginePhase])` in `Translator.jsx`, firing on every transition to `'ready'`, `reinitialize` included.
- **`useDictionaryReloadGuard`'s `consumeReloadTransition()` must be called once at the top of `loadAndTranslate`, before any early return** — it reads the previous reload state, updates its ref and returns `justFinishedReloading` atomically, so a later call skips the ref update and breaks reload-skip detection.
- **`cancelAllTranslations` (from `useTranslationController`) returns `{ count, cleanupComplete }`, not a Promise.** `const { count, cleanupComplete } = cancelAllTranslations(); if (count > 0) await cleanupComplete;` — awaiting the call itself resolves immediately, waiting for nothing.
- **`showReadinessOverlay` must not short-circuit on `initializationError`.** When init fails that error is truthy _and_ `enginePhase === 'error'`, so adding `!initializationError` hides the overlay and lets users work against a broken engine. Correct condition: `!loadError && (isLoading || enginePhase !== 'ready')`.

## Virtualized lists

**Every virtualized scroller needs per-row offsets and `overflow-anchor: none` — WebKit (the Tauri WebView) scroll-anchors on any layout shift of rendered rows, pulls `scrollTop` back, and the list flickers then sticks while scrolling; Chrome suppresses anchoring on transform changes, so devtools never reproduces it.** Position each row at its own global offset (absolute `top`, or a per-row `translateY` like `ReaderPanel`), never one shared slice shifted by `translateY(startIndex * h)` — the Dictionary table's shape until 2026-09-25.

## Config is read and written through `appConfig.ts`

Use `loadAppConfig()` from `utils/appConfig.ts` everywhere — never `window.electronAPI.loadConfiguration()` directly, which returns raw unvalidated data with absent or wrong-typed defaults. `saveAppConfig()` is the sole writer to config disk anywhere in `src/` (verified 2026-07-24), which is what makes the cache safe to trust in-session; grep for existing call sites before adding a new `loadConfiguration`/`saveConfiguration` one. For a force reload, pass `forceConfigReload: true` to `reinitialize` rather than calling `invalidateAppConfig`/`loadAppConfig` yourself.

**A setting reaching `appConfig.ts` is not a setting reaching the engine.** The chain is `saveAppConfig` → `loadAppConfig` → `TranslationEngine.js` options → `WasmDictionaryManager._doInitialize(_config)`, and that last parameter (`_config`) is discarded, as the underscore says: settings die at WASM init. Wire new WASM-related config through `EnhancedDictionaryManager`'s constructor options instead.

## `ClickableTranslationOptimized` paragraph logic

Breaks on every `\n` via an inline `useMemo`. Do NOT replace it with `groupSegmentsIntoParagraphs` — that utility detects Chinese indentation, which Vietnamese translated text does not have.

Empty paragraphs (consecutive `\n` in the source) are preserved deliberately so blank lines in the Chinese render in the Vietnamese; `.paragraph`'s `min-height: 1lh` gives the empty `<div>`s height. Do NOT add an `if (currentParagraph.length > 0)` guard around the flush — that drops blank lines and reintroduces the linebreak-fidelity regression against the char-only path.

## Testing these components

**jsdom implements no layout and several missing APIs — stub via `Object.defineProperty`/`vi.spyOn`, never assume real behavior.** Confirmed: `navigator.clipboard`/`window.getSelection` (`useHotkeyHandler.ts`'s clipboard quick-add path — NOT `window.electronAPI.readClipboard`, which is `useClipboardTranslation`'s); `Element.isContentEditable` (always `false` regardless of the attribute — `isEditableTarget`'s last clause, which every hotkey passes through); scroll geometry (`scrollTop` is a real settable property on a detached element, but `scrollHeight`/`clientHeight` are always `0` and no scroll event ever fires, so a scroll test stubs both sizes and dispatches the echo itself — `usePanelSync.test.ts`); `ResizeObserver` (`react-resizable-panels`' `Panel`/`Group`/`Separator` construct it directly and unguarded and `src/test/setup.ts` does not mock it, so mock those three as trivial pass-throughs, `({children}) => <>{children}</>` — `TranslatorDisplayPanels.tsx`).

**Memo-regression tests need their own file.** Testing whether `React.memo` actually skips a re-render requires `vi.mock`ing the child with a spy double, and that mock also poisons any sibling test in the same file asserting the real child's rendered output. Isolate into a new file (`SegmentedParagraphs.memoization.test.tsx` beside `SegmentedParagraphs.test.tsx`) rather than mocking inside the behavioral one.
