# src/components — Gotchas

## Every tab is mounted at once

`TabbedInterface` toggles tabs with CSS `visibility`, never conditional render, and everything below follows from that. `TabPanel` is the one wrapper that does it, and `tabDomIds` pairs each nav button's `aria-controls`/`id` with its panel's `id`/`aria-labelledby`; a new tab is a `TabPanel`, not another hand-written `div`. A tab that needs to know it is showing takes `isActive` from `TabbedInterface` and never defaults it to `true`.

**Anything listening globally must be gated by tab identity — or by something only one tab can hold.** `useHotkeyHandler` has four call sites — `TabbedInterface.tsx` (tab switching + Dictionary-tab shortcuts), and `DictionaryManager.tsx` (undo/redo), `Translator.jsx` and `reader/BookReader.tsx` via `<HotkeyHandler>` — and all four listen at once. Each declares the tab it belongs to (`ownTab`, or `'app'` for `TabbedInterface`); which tab is _showing_ comes from `VisibleTabProvider` (`src/components/VisibleTabContext.tsx`), never from the caller. A caller-passed tab once let Cmd+Z on the Reader undo the last dictionary edit out of sight. Add Dictionary-tab hotkeys to `TabbedInterface`, per-tab ones to that tab's `HotkeyHandler` props — the handler only applies an answer: which dictionary a Cmd-1..6 digit selects, and when Cmd-6 is refused, is `dictionaryTabNavigation` (`utils/dictionary/DictionaryTabNavigation.ts`), a function with its own tests. `SelectionMapping`'s mapper registry (Translator + Reader, both live) is the second kind: the DOM selection sits in one panel, so only one mapper answers — don't add tab gating to it, Cmd-7 reaches it from the `'app'` registration.

**A mounted tab costs on every switch, so keep each one cheap to carry.** Every tab component is `memo`'d (pinned by `__tests__/TabbedInterface.renders.test.tsx`); a tab reads `useVisibleTab` only in a child (`<HotkeyHandler>`), never in its own body, or every switch re-renders the whole tab; and any list whose length comes from the user's data is virtualized with `useVirtualScrollRange`. The Rules tab drew all 545 rules (~22k DOM nodes) and cost 240–440 ms per switch, to itself and to Configuration, until 2026-10-27. A tab switch flips the inherited `visibility` of every descendant, so any rule that gives many elements a transition on `all` (or on `visibility`) starts one transition per element and keeps the old tab painted until they end. The `prefers-reduced-motion` rule in `index.css` did exactly that with `transition-duration: 0.01ms` on `*` (the default `transition-property` is `all`): with macOS Reduce Motion on, each switch started ~700 `CSSTransition:visibility` objects, ~650 ms of delayed ticks and a ghost of the old tab. Count them with `document.getAnimations()` right after a switch. `content-visibility: hidden` was tried and is slower (WebKit lays the whole panel out on show), `display: none` resets every inner scroller; both were wrong turns.

**One action, one call site.** Hotkey handlers are keyed by the dispatch table's own action types (`useHotkeyHandler({ handlers, ownTab })`) — no second vocabulary of `on*` props to translate into. Each action is registered by exactly one owner: the Reader passes its action record as its `handlers` map, Cmd+B (`bindDictionaries`) included, and the tab container no longer registers it. Before wiring a handler, grep the action type across `handlers:` maps — two registrations answering the same key while both owners are visible run it twice (ownership in `matchHotkey` is what normally prevents that). Which actions start from the selection/clipboard is `SOURCE_ACTION_LABELS` in `HotkeyDispatchTable.ts`, read by the hook and the Reader palette alike. `useReaderCommands.test.ts` asserts every hinted palette row runs the very function its key does.

**A hidden tab is still reachable, but its modals are not.** A hotkey can drive another mounted tab's component imperatively via `forwardRef`/`useImperativeHandle` (`RulesManagerHandle`, following the older `dictionarySearchRef` precedent) without a second instance of its state hooks. Any modal opened that way must render via `createPortal(..., document.body)` — a nested overlay inherits `visibility: hidden` from the still-hidden tab-panel ancestor despite `position: fixed`.

**Gating a reaction on the tab being visible drops, not defers, what arrives while it is hidden — and some signals only ever arrive then.** The Appearance tab is where fonts change and the Translator is where most reloads start, so a Reader effect doing `if (!isActive) return` on `appearanceVersion`/`engineVersion` never ran in practice (relayout and re-anchor both shipped dead until 2026-09-25). Record the event while hidden and apply it on the `isActive` false→true edge (`ReadingAnchor.setActive`); a hidden tab is `visibility: hidden`, so its panels keep their layout and measure at real size (probed 2026-11-12).

**Bindings live in one table and are copied nowhere.** Key→action dispatch is `src/utils/ui/HotkeyDispatchTable.ts` (`matchHotkey`) — change shortcuts there, not in the hook body. Every tab rule lives there too — ownership first (a registration answers only while its `ownTab` is the visible tab, or always if `'app'`, which is what stops Cmd+R reloading for the Reader and the Translator both), then each action's own tab rule (`QUICK_ADD_TABS`/`NEW_RULE_TABS`, undo/redo on the Dictionary tab only, Cmd+Shift+V on the Translator only). The hook keeps only the skip when a callback isn't wired, which `matchHotkey`, being pure, cannot know, and one call to `resolveQuickAddSource` (`utils/highlighting/SelectionMapping.ts`) for what an Add starts from — it never copies the selection to the clipboard (it did until 2026-09-26, overwriting whatever the user had copied). Tab shortcuts are the exception: `src/constants/tabs.ts`'s `TAB_ORDER` is their single source — nav bar and `Option/Alt+digit` both derive from it by index. Anything that _displays_ a binding (the Reader's palette hints, `docs/HOTKEYS.md`) is a second copy of the table: assert it against `matchHotkey` (`PaletteCommands.test.ts` parses each hint back into its keypress), or the UI advertises a dead key. Bindings stay pinned literally in `HotkeyDispatchTable.test.ts` on purpose — they live in muscle memory, so a reorder must fail a test rather than silently follow the array.

## The JS↔TS boundary is checked by the ratchet, not by `type-check`

`type-check` has `checkJs: false`; `bun run type-check:ratchet` checks the JavaScript (`tsconfig.test.json`) and fails on any new error. In `Translator.jsx` it catches an import of a name the module no longer exports and a prop value of the wrong type (`ownTab={42}` against `HotkeyOwner`). What it does not catch:

- **Handlers.** A JS function's parameters are untyped there (`noImplicitAny: false`), so a `.tsx` prop type for a `Translator.jsx` handler is checked against almost nothing: a three-parameter arrow passed as `translateFromClipboard` compiles. After narrowing a handler type, trace the `.jsx` producer.
- **Hand-written `.d.ts` files.** `src/types/engineConformance.ts` fails `tsc` when the `TranslationEngine` interface declares a member the class lacks (names only; signatures are still unchecked). `EngineContext.d.ts` exists because `createContext(undefined)` makes `useEngine()` destructure `never` in a `.tsx` file; nothing checks it against the provider, so a key added to the provider's `value` must be added there by hand. And an `as any` at the first consumer hides a wrong declaration from the second (`prebuiltSegments` was declared `TranslationSegment[]` while `matchWordSegments` fills it with `WordSegment[]`; it is now `WordSegment[]` through one shared import, so a renamed field fails `tsc` in the component). The `Translator.jsx` → `useTranslationResults.js` hop is still unchecked. Trace the producer, don't trust the declaration.

TypeScript's own narrowing has two traps here: an optional property accessed through an `&&` spread widens (`SemanticType` → `string`) — extract a local or assign imperatively (`if (metadata.semanticType) entry.semanticType = metadata.semanticType`); and an inline array literal passed to a generic component's prop (`<Foo<T> options={[{value:'x',…}]} />`) widens narrow-union `value` fields to their base type unless the array carries `as const`, compiling standalone and failing only at the generic call site.

Nor does `tsc` see two swapped arguments of one type (`addEntry(dictionaryId, source, translation)`, all `string`): a new caller gets a test asserting the argument order against a mocked `addEntry` (`useCandidateFinder.add.test.ts` caught one written the wrong way round).

## Frequently-updating values travel by ref, not by dep array

Never list frequently-updating state or callback props in a `useEffect` dep array that creates a `setInterval` or `addEventListener` — the subscription is torn down and rebuilt on every update. Use `const ref = useRef(value); ref.current = value;` and read `ref.current` inside the callback (`useHotkeyHandler.ts`'s keydown listener, whose props are all mirrored into one `optionsRef` rather than per-prop refs).

**The same refs are invisible to `React.memo`, so a memoized child needs every input it renders from as an actual prop.** A getter that is stable by design (`useCallback(…, [])` reading through a ref) cannot signal that its data changed, and state read off a stable object inside the child — `virtualizer.getVirtualItems()` — is not in the props comparison at all, so the child stops re-rendering on scroll. Both bit `ReaderPanel` in one change: the rendered range and total size became props, and an explicit `contentVersion` counter (`useWindowedTranslation`'s `contentVersion`) is what tells it a page or a chunk landed. Before memoizing, list what the component reads that no prop describes. The inverse also defeats it: a prop that changes on every scroll step (a slice-local index, an `isScrolling` flag) re-renders every memoized row per step.

**A ref mirror of the listener's props is not enough when the mirrored callback closes over state itself.** `step` in `useChapters.ts` (the Reader's `goToChapter`) asks `useReadingAnchor`'s `readLine()` rather than using the `anchorLine` it closed over, because a key-repeated `]` can fire before React re-renders from the first press, and `optionsRef` would hand the listener that stale closure.

**Anything memoized is rebuilt whenever any of its deps changes: the work reruns, and state kept inside it is dropped.** A cache built in a `useMemo` lives only as long as its most volatile dep, so key it in state on its own invalidation value instead (`useCandidateReading`'s gloss cache had tab visibility among its deps and emptied on every tab switch until 2026-11-24). A dep whose identity changes on every write reruns everything memoized on it: a `Set` in state is a new reference per `setState`, and the Dictionary Store hands out a new `dictionaries` object per edit, so a `useCallback`/`useMemo` over either rebuilds on every update or Add. Cheap work that needs the latest value: ref mirror, deps `[]`. Expensive work over one consistent set: read it once when the work starts (the Candidate finder re-tested 18k survivors against 4,082 patterns per Add until 2026-10-26, now `snapshotFinderDictionaries`).

**State whose correctness is ordering across async work — a queue, generation counters, a flag cleared at several exits — lives in a plain module with `subscribe`/`getSnapshot`, and the hook is an adapter over `useSyncExternalStore`** (`ReadingAnchor`, `DictionaryStore`, `WindowFiller`, `BookBindingStore`, `BookLinesStore`). Kept in an effect or a ref mirror, its bugs are reachable only through `renderHook` and timers. Its tests run the module directly: a fire-and-forget operation (`announceOpenBook`) has no promise to await, so flush with one macrotask turn (`await new Promise((r) => setTimeout(r, 0))`) where `act` did it under a provider, and keep only a few provider tests, for wiring (`BookBindingStore.test.ts` / `BookBindingContext.test.tsx`). The adapter makes the module once in `useState` and calls `open()` in a mount effect and `close()` in its cleanup; a remount reruns the effect on the same instance, so `open()` must be idempotent (a second call only lifts a `close()`) and late results after `close()` must be dropped (`ChapterOutlineStore`).

**A best-effort write must not be able to break its caller.** Wrap it `void (async () => { try { await save() } catch { log } })()`, never `save().catch(log)`: a bare `vi.fn()` mock returns `undefined`, so `.catch` throws synchronously inside the caller (`ReaderTab`'s `rememberReading` failed every open that way in tests).

**State set inside a `useEffect` must not appear in its deps** — a flag reset in the effect body and listed as a dep re-triggers the effect.

**Two async requests whose results land in one place can race, and only the latest-started may land.** A same-key check cannot tell which one _started_ more recently: count requests (a `requestId` incremented per request, applied only if it still matches on resolution). `useLibrary.scan` is the plain case (a slow scan of the old folder replaced the one just chosen); `ReaderTab`'s `openBook` is the same across different keys (`latestOpenRef`; a dedup ref keyed by file name stops a double click, not a second book, ADR-057 addendum). **A shared counter is right only while both requests produce the same output**: `ChapterOutlineStore`'s mount fetch and `setOverride` both write `headers`, but the mount fetch also produces election's outcome (`candidates`), which nothing else writes. Guard only the contended output, let the other always land, and read the latest override from a ref on resolution, not the closure's copy.

**eslint's `exhaustive-deps` only sees a dependency it can read syntactically at the call site** — a ref from a custom hook, or a callback built by a factory function, are both invisible to it. A ref returned by a custom hook (not `useRef` in the same component) needs listing in the dep array by hand — it's as stable as any other ref (`useReaderPanel`'s `scrollRef`, consumed by `useReaderPanels.ts`). `useCallback(factoryCall(...), deps)` warns "pass an inline function instead" even with a correct deps array, because the first arg isn't a literal — `useMemo(() => factoryCall(...), deps)` keeps the same identity while giving the linter a literal to scan. For a factory whose result never needs rebuilding, `useState(() => factoryCall(...))` sidesteps the dep array entirely (`useReaderEngine`).

## React state updater rules

**Never `throw` inside a state updater** (`setState(prev => { throw … })`): React 18 Concurrent Mode may call updaters more than once, and throws bypass the `await` chain. Do existence checks on the closed-over variable before `setState`.

**Never assign a `let` inside an updater for use outside it** — it may run twice. Compute from the closed-over snapshot first. For undo/redo-style history read a ref's `.current` directly instead of a closure variable (dictionary history keeps its list and cursor in a ref; the dictionaries themselves live in the Dictionary Store, outside React state).

## Context providers

A `createContext` provider's `value` must be wrapped in `useMemo`, and every function inside it — including ones returned by a wrapped hook, not just locally declared ones — must be `useCallback`-stable, or the memoization is defeated at its root and every consumer re-renders whenever the provider does. `DictionaryContext.tsx` does this correctly; `EngineContext.jsx` initially didn't, because the convention lives at the return statement rather than at the exports.

**Anything on a tab's mount path is a test change too, and its failures point at the wrong file** — a provider mounted above `TabbedInterface`, or a new toast/IPC call in any tab's mount effect: every tab mounts for real in a test rendering `TabbedInterface` unless stubbed (a Transform Rules load toast broke `TabbedInterface.cmd6`'s toast spy until `RulesManager` was stubbed, 2026-09-29). Components here render in isolation with their contexts `vi.mock`ed, so a new provider obligates a mock in every test file rendering a consumer, and that mock must return _every_ field consumers destructure. A missing field is spread inside the consumer's own `useMemo`, so the stack blames the consumer rather than the mock. `BookBindingContext` hit both halves: two test files needed new mocks, then a later field addition failed 16 tests pointing at `useDictionaryConfigManagement.ts`. Anything a test feeds into a hook's effect deps must keep one identity across renders — a mock's functions, or a `renderHook(() => useX(makeDeps()))` deps object — or the effect re-runs every render: a timeout (`useDictionaryConfigManagement`'s mount effect vs a `useDictionary` mock returning a fresh `loadDictionary` each call; its tests now run over the real stores, `configuration/__tests__/realStores.tsx`) or clobbered state (`useDictionaryEntryForm`'s auto-populate re-filling an edited translation). Hoist with `vi.hoisted`, or build the deps once outside the callback. A context mock that reads refs must also notify (`useSyncExternalStore` over a version counter): tabs are memoized, so `rerender` with the same props skips them (`DictionaryManager.composition.test.tsx`'s `notifyContextChange`).

## Appearance travels as CSS variables, never as state

`useAppearanceSettings` is called only from `AppearanceManager.tsx`; everything else receives appearance as custom properties written to `document.documentElement` by `applyAppearanceToCssVars` (ADR-024). Two consequences. **Anything the browser re-renders needs no wiring** — `Translator.jsx`'s `sharedTextStyle`/`inputTextStyle`/`outputTextStyle`/`characterOnlyTextStyle` are `var(…)` strings with deps `[]`, static constants rather than values derived from `appearance`; do not move them into the hook. **Anything measuring in JS must watch for the write itself** — a font change leaves every box exactly as wide as it was, so `ResizeObserver` reports nothing and a cached measurement keeps the old geometry (`useAppearanceVersion` watches the root style attribute; `useColumnMetrics` re-measures; `ReadingAnchor` drops the Reader virtualizers' caches and restores the anchor — deferred to the Reader's return, since the Appearance tab is where the font changes). Matching the Translator's typography means reading those inline objects — each pane's `lineHeight` (the section's `--*-line-height`), `fontSize: '1.25rem'`, `padding: '1.5rem'` — plus `.panel` in `TranslatorDisplayPanels.module.css` (`--surface-color`, 1px `--border-color`, `--radius-lg`, 1rem inset); the CSS modules alone do not carry them.

## Engine lifecycle — `EngineContext` / `useEngine()`

The engine is constructed once above the tab container (`App.jsx` wraps `<TabbedInterface>` in `<EngineProvider>`), not owned by `Translator.jsx`. **Only one may exist at a time**: the WASM pattern/number processors are module-scope singletons, so a second live engine silently shares state with the first. Consume it via `useEngine()` (which throws outside `EngineProvider`); never call `useTranslatorEngine` from a tab component — that builds a second, unshared engine. `EngineProvider` also wraps its children in `ErrorBoundary`, at the provider rather than around `<Translator>`. That boundary catches a tab failing to render, which takes every tab down, and says so. It **never sees an engine-initialization failure**: the provider's own hooks run outside its boundary, and `reinitializeEngine` reports through `initError` rather than throwing. So each tab shows an init failure itself — the Translator's error panel, the Reader's `ReaderEngineErrorBanner`.

The exposed fields are listed in `EngineContext.d.ts`. What that file cannot tell you:

- **`engineVersion` increments once per successfully constructed engine** (mount and every `reinitialize()`) and is the cache-invalidation signal for anything holding translated output — nothing inside the engine survives reinitialization. It counts engine constructions, not dictionary edits: a dictionary edited on disk without a reload does not bump it, correctly, because the running engine has not seen that edit either.
- **`reinitializeEngine(rawDicts, options)`** never throws — it resolves `{ ok: true } | { ok: false, error }`, and a failure also lands in `enginePhase`/`initError`. Pass raw, unfiltered dicts; the hook filters internally. Non-React callers read the outcome, since `enginePhase` is async state they cannot read. It is the only door (`useEngine()` no longer exposes the raw `reinitialize`); `useForceReloadContext`/`useForceReload` and `BookBindingContext`'s rebuild consume it (the post-reload WASM sync validation was deleted, ADR-058).
- **Destroy-before-replace is structural, not a convention.** `useTranslatorEngine`'s `runEngineInit` destroys the outgoing engine before constructing its replacement, on the mount path and every `reinitialize()` — not only on the `useForceReload` path that also calls `destroyEngine()` first. The swap is one `engineAccess.replace` turn (ADR-085 addendum): it waits for the engine call in flight, so a rebuild never destroys the engine under a running Reader chunk (the book-binding rebuild did, and the dead engine's Pattern Store toasted patterns off). Never call `reinitializeEngine` from inside an `engineAccess.run` callback; it would wait on itself. A throwing `destroy()` is caught and logged, never blocking the replacement. `destroyEngine()` is `useEngine()`'s (owned by `useTranslatorEngine`, next to the init lock) and does nothing while an init runs: that engine is half-built, and the reload's own `reinitializeEngine` is queued behind the init and replaces it.
- **The init lock lives in `reinitializeEngine`**, which sets `isInitializingRef.current = true` synchronously on entry while the init effect checks `enginePhase === 'loading' && !isInitializingRef.current`. A call that arrives mid-init is queued, not dropped, and queued calls collapse into one run with the latest arguments (see GLOSSARY.md "Engine Reinitialization"); the mount init goes through the same entry. `handleForceReload` must NOT add a lock of its own.
- **Dictionary priorities are not an engine option.** `priorityOf` (`utils/dictionary/DictionaryIdClassifier.ts`) is the one ladder; change a rank there (GLOSSARY.md "Dictionary priority ladder").
- **Post-ready setup** (engine stats, debounced callbacks, dev tools) happens in a `useEffect([enginePhase])` in `Translator.jsx`, firing on every transition to `'ready'`, `reinitialize` included.
- **`useDictionaryReloadGuard`'s `consumeReloadTransition()` must be called once at the top of `useAutoTranslateTrigger`'s effect, before any early return** — it reads the previous reload state, updates its ref and returns whether a reload just finished, atomically, so a later call skips the ref update and breaks reload-skip detection.
- **A cancelled or timed-out translation is inert (`TranslationRunner.ts`).** `translateText` passes the run's `signal` to the engine and wraps `onBatchComplete` in `guard(...)`, so a superseded run cannot write streaming state over its successor. Final state (`setResultArrays` etc.) is applied inside the task, after the engine call — an aborted run never reaches it because the engine throws first. A new callback or setter inside the task must go through `guard` or sit after the last `await`. The `cleanup` callback gets `{ superseded }`: when true, a newer run owns the streaming flags, so cleanup must not reset them. A run that ends early by preempt, timeout or engine error writes `latestPartialText()` to `translatedText` in the `catch`; a plain `TranslationCancelledError` does not (ADR-105). Timeout is `translationTimeoutMs(len)`: 30 s minimum, +100 ms/char, 60 s ceiling.
- **`translateText` resolves a `TranslateTextOutcome` (`types/UITypes.d.ts`): `{ status: 'done', text }` or `{ status: 'skipped', reason }`.** Invalid input, a reload in progress, an already-running translation, an unready engine, a Reader preempt and an `EngineAccess` refusal are all `skipped`; the toast or log has already happened, so a caller returns quietly (`useAutoTranslateTrigger`) or throws (`useReloadRetranslate`, which `useForceReload` reports as a failed retranslate). A timeout or a cancel by a newer run still rejects. `translateText` has no component test; the skip handling is pinned in the two hooks' tests. Extracting it (or only its guards or error mapping) was declined, ADR-091.
- **Before "fixing" a stale closure, trace every caller: the frozen value may be what lets a path through.** Example: `translateCharacterOnly` has no reload guard, and must not get one. `useReloadRetranslate` calls it (`setTimeout(0)`) inside the reload window — `useForceReload` clears the flag ~100 ms later, after `restoreScrollPositions` — so a live check would silently drop the character-only retranslate after every dictionary reload. Its deps are `[]` for a second reason: `useAutoTranslateTrigger` lists it in its effect deps, so a changing identity would re-fire that effect on each reload toggle. User-driven callers guard themselves (`useAutoTranslateTrigger`, `useClipboardTranslation`, `useForceReload`). Until 2026-10-08 a check read the frozen `useState` value (`false` forever) and never fired.
- **`cancelAllTranslations` (from `createTranslationRunner`, `src/utils/TranslationRunner.ts`) returns `{ count, cleanupComplete }`, not a Promise.** `const { count, cleanupComplete } = cancelAllTranslations(); if (count > 0) await cleanupComplete;` — awaiting the call itself resolves immediately, waiting for nothing.
- **`showReadinessOverlay` must not short-circuit on `initializationError`.** When init fails that error is truthy _and_ `enginePhase === 'error'`, so adding `!initializationError` hides the overlay and lets users work against a broken engine. Correct condition: `!loadError && (isLoading || enginePhase !== 'ready')`.

## The app runs in macOS WebKit, not Chrome or jsdom

The Tauri WebView is WebKit on macOS, so input and layout behaviour that passes in jsdom and Chrome devtools can break in the app. Each of these shipped green:

- **Option/Alt hotkeys match `event.code` (`'Digit1'`, `'KeyG'`), never `event.key`**: macOS remaps every Option+key per layout (Option+1 → `¡`), and `preventDefault`, or the character lands in the focused input.
- **A control reached with Tab needs `tabIndex={0}`**: WebKit leaves buttons and checkboxes out of the Tab order (the Add form's "Usable as X/Y" pill). Roving-tabindex rows (`SemanticTypePicker`) already set it.
- **Enter-to-submit skips `keyCode === 229`, not just `isComposing`**: WebKit fires `compositionend` before the committing Enter's keydown, so a Vietnamese/Chinese IME submits half-typed text (the Candidate finder row's translation field).
- **A virtualized scroller needs per-row offsets and `overflow-anchor: none`**: WebKit scroll-anchors on any layout shift of rendered rows and pulls `scrollTop` back, so the list flickers then sticks. Position each row at its own offset (absolute `top`, or per-row `translateY` like `ReaderPanel`), never one slice shifted by `translateY(startIndex * h)`. A fixed-height table gets all of this from `VirtualTableBody` (GLOSSARY.md "Virtual table body"); render through it rather than copying the spacer. Paint per row too: each row takes its band from its global index (`RowShell`'s `index`, the kit's opaque `TableRow` stripe), never one background on the spacer (a stripe gradient on 165k–660k px spacers never painted; WebKit limit inferred), and never a colour mixed with `transparent` (`--page-background`'s dots show through).

## Config is read and written through `appConfig.ts`

A `saveAppConfig()` can reject with "Couldn't read config.json; not saving over it" — the file failed to load this session, and defaults are never written over it (GLOSSARY.md "Unreadable app files"); surface the error, don't retry it into a loop. Use `loadAppConfig()` from `utils/appConfig.ts` everywhere — never `window.electronAPI.loadConfiguration()` directly, which returns raw unvalidated data with absent or wrong-typed defaults. `transformAppConfig()` (which `saveAppConfig()` wraps) is the sole writer to config disk anywhere in `src/` (re-checked 2026-10-01), which is what makes the cache safe to trust in-session; a write that decides from what it read uses `transformAppConfig(current => ({ value, result }))`, never `loadAppConfig()` then `saveAppConfig()`, and a component that renders from config reads it with `useAppConfig()` (`src/hooks`), never a `loadAppConfig` + `subscribeAppConfig` copy in state (every tab stays mounted, so a mount-time read goes stale); grep for existing call sites before adding a new `loadConfiguration`/`saveConfiguration` one. For a force reload, pass `forceConfigReload: true` to `reinitialize` rather than calling `invalidateAppConfig`/`loadAppConfig` yourself.

**A setting reaching `appConfig.ts` is not a setting reaching the engine.** The chain is `saveAppConfig` → `loadAppConfig` → `TranslationEngine.js` options, and an option the engine never reads is dropped silently. The WASM dictionary tier, where these settings used to die at `WasmDictionaryManager._doInitialize(_config)`, was deleted. Wire a new setting through a constructor option the receiving module reads, and test that it arrives.

## `ClickableTranslationOptimized` paragraph logic

Breaks on every `\n` via an inline `useMemo`. Do NOT replace it with `groupSegmentsIntoParagraphs` — that utility detects Chinese indentation, which Vietnamese translated text does not have.

Empty paragraphs (consecutive `\n` in the source) are preserved deliberately so blank lines in the Chinese render in the Vietnamese; `.paragraph`'s `min-height: 1lh` gives the empty `<div>`s height. Do NOT add an `if (currentParagraph.length > 0)` guard around the flush — that drops blank lines and reintroduces the linebreak-fidelity regression against the char-only path.

## Testing these components

**No test renders `Translator.jsx`, so logic written inside `translateText` is untested.** Put the stateful part behind a hook's interface with its own test, and leave Translator a one-line call (`useStreamingTranslation.latestPartialText()`, ADR-105).

**jsdom implements no layout and several missing APIs — stub via `Object.defineProperty`/`vi.spyOn`, never assume real behavior.** Confirmed: `navigator.clipboard`/`window.getSelection` (`useHotkeyHandler.ts`'s clipboard quick-add path — NOT `window.electronAPI.readClipboard`, which is `useClipboardTranslation`'s); `Element.isContentEditable` (always `false` regardless of the attribute — `isEditableTarget`'s last clause, which every hotkey passes through); scroll geometry (`scrollTop`/`scrollLeft` are real settable properties on a detached element, but `scrollHeight`/`scrollWidth`/`clientHeight`/`clientWidth` and every `getBoundingClientRect()` are `0` — stub the getters with `vi.spyOn(HTMLElement.prototype, 'clientWidth', 'get')` and the rects with a prototype spy keyed on the element, as `DictionaryEntry.test.tsx`'s quick-switch scroll test does — and no scroll event ever fires, so a scroll test stubs both sizes and dispatches the echo itself — `usePanelSync.test.ts`); `ResizeObserver` (`src/test/setup.ts` does not mock it: `react-resizable-panels`' `Panel`/`Group`/`Separator` construct it directly and unguarded, so mock those three as trivial pass-throughs, `({children}) => <>{children}</>` — `TranslatorDisplayPanels.tsx`; `useVirtualScrollRange` (Dictionary, Rules) constructs it in its scroller ref — `vi.stubGlobal` a no-op class, and its `containerHeight` defaults to `600`, so a small list renders fully without firing it).

**A test that depends on a module's own semantics — its lock, "same value saves nothing", a cache a Rust-side write drops — fakes that module's IPC edge, not the module.** `installFakeConfigDisk()` (`src/test/fakeConfigDisk.ts`) backs the real `appConfig` with a fake `config.json`; set a field on `disk.raw` to play a Rust write. It is a wrapper over `installFakeAppFile({ load, save }, initial)` (`src/test/fakeAppFile.ts`), which fakes any App file's load/save pair — typed against `ElectronAPI` and, not being a `*.test.ts`, checked by `tsc`, so a renamed command breaks the fake at compile time — the book-record and transform-rule backends' default stubs use it directly; its `load`/`save` are the installed `vi.fn`s, so a test overrides one for a failure or a malformed payload. A hand mock re-implements the lock and drifts from it, which is fine while `appConfig` is not what the test is about (14 files still do).

**Memo-regression tests need their own file.** Testing whether `React.memo` actually skips a re-render requires `vi.mock`ing the child with a spy double, and that mock also poisons any sibling test in the same file asserting the real child's rendered output. Isolate into a new file (`SegmentedParagraphs.memoization.test.tsx` beside `SegmentedParagraphs.test.tsx`) rather than mocking inside the behavioral one.
