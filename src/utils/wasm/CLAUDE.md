# src/utils/wasm — WASM Wrapper Lifecycle

The WASM wrappers share one binary, so failure is always collective.

The one wrapper (PatternProcessor) imports `translation_wasm_core.js`, and `WasmSharedModule.js` holds the instantiated binary. Any panic corrupts the shared `dlmalloc` linear memory permanently, so a panic anywhere must retire everything: the wrapper and the shared module's own cache. (A second wrapper, ConflictResolution, was deleted 2026-10-07, ADR-083; add the next one to `WasmCascadeDiscipline.test.js`'s list. The registry and the lifecycle class stay generic with one wrapper on purpose: `WasmSharedModule` and the wrapper both register a retire handler, and the loader is a leaf that must not import the wrapper. No second WASM processor is planned; do not collapse them for that reason alone, ADR-083/ADR-070.)

- **Every instantiation goes through `loadSharedWasmModule()` (`WasmSharedModule.js`); no wrapper calls the generated `init` itself.** `init` is not safe to call concurrently: each racing caller instantiates the module again and the last one to finish overwrites its `wasm` binding (measured 2026-10-03: three concurrent `init(buf)` made three `WebAssembly.instantiate` calls). The loader fetches and instantiates once (there is no hash check: ADR-080), shares one in-flight promise, rejects with the load error (so a lifecycle's backoff can classify it) and tries again on the next call, and is retired for good by the cascade. It has no retry of its own: each wrapper's `WasmProcessorLifecycle` retries its whole sequence. A new wrapper calls it from its `instantiateFn`; `WasmCascadeDiscipline.test.js` fails on a bare `init(` or `.default(` anywhere else. Wrapper tests mock `WasmSharedModule` and drive the mocked `default`.
- **Retire on panic, never retry.** A wrapper's registered cascade handler (below) is the one place that destroys and nulls its instance and sets its failed flag, and the lifecycle's `initialize()` returns false once `permanentlyFail()` ran. A `catch` around a WASM call does three things: log, `fireCascadeRetire()` (which runs the panicking wrapper's own handler too), and return the fallback. Do not repeat the destroy/null/fail lines inline — four wrappers did until 2026-10-03, and a throw from `__destroy_into_raw` inside the `catch` would have escaped it and masked the fallback, where the registry swallows it. **Any** throw in the `try` retires everything, including a JS-side `JSON.parse` failure on a bad result: telling a Rust panic from another error is brittle, so retiring is the deliberate, conservative choice. Once `panic = "abort"` fires, `borrow_mut_count` is stuck — retrying yields "recursive use" forever.
- **Cascade only through `src/utils/wasm/WasmCascadeRegistry.js`.** Each wrapper calls `registerCascadeHandler(fn)` once at module load; each panic catch calls `fireCascadeRetire()`, which invokes every handler including its own. A direct sibling call is redundant rather than a safety net: all wrappers are statically imported from `TranslationEngine.js`, so all are registered before any translation runs. **Confirmed twice** — four wrappers reached a sibling directly until 2026-08-08 (sole cause of the only import cycle this repo's static analysis ever flagged), and the 2026-08-08 cleanup left two survivors in `WasmDictionaryManager.js` (deleted since, ADR-073), each sitting one line above the `fireCascadeRetire()` that already covered it, until 2026-08-31. Removing them deleted the last wrapper-to-wrapper import in the directory. `WasmCascadeDiscipline.test.js` now enforces the registration, the fire, the no-sibling-retire edge, and the module-privacy of retire functions; it is also what tells you a new wrapper has to join the cascade at all.
- **`__destroy_into_raw()` before every `instance = null`.** Otherwise FinalizationRegistry stays active, and the stale callback fires when dlmalloc reuses the freed Rc address — the next method call panics in `alloc/rc.rs`. Use `__destroy_into_raw()` (JS-only, safe post-panic), never `.free()` (calls into WASM, unsafe after `panic = "abort"`).
- **A lifecycle retries transient init errors on backoff timers, so gate background init with `MODE !== 'test'`** (a rejected init under vitest otherwise leaves retries running). To test retry or panic with the real lifecycle, mock `../wasm/WasmSharedModule`, not the lifecycle class: `TranslationEngine.phase1.test.js` does for the real binary.
- **Singletons trigger background init at module bottom** with `.initialize().catch(warn)`; missing it forces every first caller onto the slow JS path.
- **`new URL(path, import.meta.url)` needs a hard-coded string literal.** Template literals defeat Vite's asset URL transform — resolves in dev, breaks in production, so no test in this repo can see it. Enforced repo-wide by `SourceConventionScan.test.js`.

Wrappers that deviate, and why:

- Every wrapper holds a `WasmProcessorLifecycle` (`WasmCascadeDiscipline.test.js` fails otherwise): on a runtime panic call `lifecycle.permanentlyFail()`, **not** `lifecycle.reset()`, which clears `_hasFailed` and allows re-init from the corrupted binary.
- `WasmPatternProcessor.js` — exports functions rather than a singleton; its module-bottom prewarm is one `loadSharedWasmModule()` call (skipped in tests) that starts the fetch and instantiation before the patterns dictionary is ready; the instance itself still waits for it.
- `WasmPatternProcessor.js` — `processTokensWasm` receives only `semanticTokens` (`getSemanticTokens`-filtered, non-semantic tokens dropped); a result's `startIndex`/`endIndex` index into the ORIGINAL `tokens` array via each token's `originalIndex` field, so any bounds check against `tokens.length` must run in `TwoPhasePatternProcessor.js` (still has `tokens` in scope), never inside `processTokensWasm` itself.

`translation_wasm_core.d.ts` is auto-generated and the linter reverts manual edits — `__destroy_into_raw` is absent from it, so suppress TS2339 with `// @ts-ignore` on the call line rather than editing the `.d.ts`.
