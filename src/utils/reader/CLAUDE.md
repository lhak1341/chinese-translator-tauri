# src/utils/reader — Gotchas

## A required field added to a shared type lands silently in every test fixture

Test files are excluded from `tsc` (see root `CLAUDE.md`), so a fixture literal missing a newly required field type-checks fine and silently drifts from what production code actually returns — grep the type's name for fixture literals as part of the change, not after. `CachedChunk.characterOnlyText` hit this; `BookRecord` (`src/types/ReaderTypes.ts`) is closed against this by construction: every test builds records through `__tests__/bookRecordFixture.ts`'s `makeBookRecord`, which spreads `emptyBookRecord`, so a new field needs three sites — the type, its default in `BookRecord.ts`'s `emptyBookRecord`, and its repair in `validateBookRecord` — plus, only if it is one of the reader's answers, one word in `READER_ANSWER_FIELDS`. The two refresh paths (`recordBookOpened`, `applyReconciliation`) both go through `refreshBookRecord` and need nothing. `BookRecordValidation.test.ts`'s `rawRecord` stays hand-written on purpose: it builds malformed input.

## Windowed translation is four seams that must stay wired together

`TranslationWindow.ts` (pure arithmetic) and `TranslationChunkCache.ts` (LRU) decide everything; `WindowedTranslationFill.ts`'s `fillPlan` is the one place that actually calls the engine — a plain async generator, no React, driven by `src/hooks/useWindowedTranslation.ts`, which owns scheduling: the effect, the cache instance, the two generation counters (`generationRef`/`bookGenerationRef` — see below), and folding landed chunks back into per-line strings/segments (`rebuild`), which it hands out as finished `PanelRow`s (`getRow.translation`/`.original`/`.characterOnly`) plus one `contentVersion` — the row rules (stand-in Chinese with no runs while pending, gap-filling on the original panel only) live there, not in `BookReader`. Split 2026-09-19 (architecture review candidate #1) precisely so the fill loop's correctness properties — cancellation, the cache read/write protocol, the two-call ordering — could be unit-tested without `renderHook`; see `WindowedTranslationFill.test.ts`. Three signals have to reach the hook, and each one fails silently rather than loudly when it does not:

- **`linesVersion` from `useBookLines`.** `getLine` is referentially stable and reads through a ref, so nothing downstream can tell from its identity that new lines arrived. `planChunks` stops at the first unfetched line — without `linesVersion` in the fill effect's deps, a plan blocked on a page still in flight is never re-planned, and the region stays Chinese forever with no error.
- **`engineVersion` from `useEngine`, passed as `dictionaryVersion`.** A change makes every cached chunk stale — invalidated, not discarded (`setVersion` keeps the entries; `isFresh`, not `has`, is what planning asks). Each stale chunk is still rendered until its own replacement lands, so a reload repaints the page a chunk at a time instead of reverting it to dim Chinese for the length of the refill. Drop the signal entirely and a reload leaves the previous engine's translations on screen permanently. `useOutlineTranslations` stamps its titles with the same version for the same reason. A chunk being replaced keeps its old gloss **text** (the gloss pass is a whole engine call behind) but drops its gloss **segments**, which were relabeled against the outgoing translation's units.
- **`isEnabled` gated on the Reader being the visible tab, and every Reader-side engine caller serialized through one queue.** `translateWithSegments` resets engine-wide segment state on entry, so the single shared engine serves exactly one caller at a time — true across tabs (the tab gate) and _within_ the Reader too, now that viewport fill and outline-title translation (`useOutlineTranslations`) are two independent loops sharing one component: `createReaderEngine` (`ReaderEngine.ts`, via `useReaderEngine`) serializes them on one promise chain. The queue is built in `ReaderTab`, not `BookReader`: `BookReader` remounts on every book (ADR-050), and the previous book's in-flight call must stay ahead of the next book's. Add a third Reader-side engine call there, not straight at `engineRef` — the `EngineCall` brand makes the bypass a compile error at any hook option typed with it. **Known gap, accepted 2026-09-25:** the tab gate stops new Reader calls on a switch but does not abort one already in flight, so a Translator translation started within that window (under one chunk's engine time) can land its reset mid-call. Unreported. If it ever bites, the fix is an engine-wide queue in `EngineContext` that the Translator's two call sites (`Translator.jsx`) also route through — architecture review 2026-09-25, candidate #2, option (b).

**Every generation-guarded engine loop in the Reader takes two separate staleness signals, `isStale()` and `isAbandoned()` — collapsing them into one has now shipped three times.** Twice in `fillPlan` (2026-09-19, below), and once in `useOutlineTranslations`, whose docstring claimed its single-effect shape made it immune: any re-run of that one effect (an anchor-fed `priorityLine`, `isEnabled` toggling) bumped the one counter checked after the `await`, discarding finished title batches on ordinary scrolling (fixed 2026-09-26). One effect is no protection. Stale means "don't start the next unit"; only a book or dictionary-version change makes a landed result wrong.

- **`isStale()`**, checked only before _starting_ a new chunk, answers "is there a newer plan than this one?" — true on every ordinary re-plan (anchor move, page landing, resize). Skipping a not-yet-started chunk here is free.
- **`isAbandoned()`**, checked after each of a chunk's two `await`s, answers "has the cache itself stopped being trustworthy?" — true only on a book switch or unmount. Must use a _separate_ counter (`bookGenerationRef`, bumped only in the book-change effect and on unmount) from the one `isStale()` uses (`generationRef`, bumped on every fill-effect re-run).

First shipped bug: only `cache.version` (dictionary-scoped) was re-checked after an `await`, never generation at all. A book switch bumps `generationRef` in a _different_ effect (the fingerprint-change one) than the fill effect, so a chunk already `await`ing `translateChunk`/`translateGloss` when the switch happened was unaffected by that check and still landed in the _new_ book's cache under a coincidentally-matching line-range key.

Second shipped bug, introduced by fixing the first one: the fix made `isAbandoned` reuse `generationRef` — the _same_ counter `isStale` uses, which bumps on every ordinary re-plan, not just a book switch. That abandoned a chunk's own gloss call on nothing more than an anchor move mid-`await`. Since `translateChunk`'s result had already been cached (marking the chunk `isFresh`), no future plan ever retried the orphaned gloss — the reference panel showed Chinese for that chunk _forever_, silently, no error logged, at a rate proportional to how often the reader scrolls. Caught only by live testing (`bun run tauri:dev`), not by the unit suite that shipped alongside the first fix — its tests asserted the _fixed_ behavior was reachable, not that _ordinary_ re-plans left it alone. `WindowedTranslationFill.test.ts` and `useWindowedTranslation.test.ts` both now pin the distinction explicitly, including a test proven to fail against the second-bug version before being fixed.

**A chunk that throws is isolated, not fatal to the plan.** `fillPlan` yields it as a `skipped` event; the hook logs it (`logger.error`) and moves on to the next chunk rather than surfacing a banner or aborting the rest of the visible window. A skipped chunk stays `!isFresh` forever, so it retries the next time planning re-runs for any reason (anchor move, `linesVersion`/`dictionaryVersion` bump) — no separate give-up-after-N-attempts tracking exists, on purpose: the cost of not giving up is bounded by how often the reader actually revisits that passage, not by a timer.

**Bands are nested by construction, and the keep band is not decoration.** `keep` (±6 viewports) is much wider than `fetch` (±2) so that crossing the fetch boundary repeatedly evicts nothing — collapsing them to one threshold reintroduces exactly the thrash the second band exists to prevent, and the symptom is a re-translation cost, not a visible bug.

**Chunk size is two numbers, not one.** `CHUNK_TARGET_CHARS` (600) is what packing aims at; `CHUNK_CEILING_CHARS` (1200) is the hard limit, because word-level highlighting silently drops candidates above roughly that many characters _per engine call_ — no error, no partial result, just an untagged tail. Raising the target without re-checking the ceiling is how that gets reintroduced. Both are overridable per call (`planChunks(range, getLine, lineCount, {targetChars, ceilingChars})`) so the spec's "re-confirm the chunk size in the real app" can be done without editing the module.

**A chunk key must stay a pure function of the book's text — two rules in `planChunks` exist only for that, and both look like inefficiencies.**

1. **A chunk never spans a paragraph; packing restarts at every paragraph's own first line.** The snapped fetch band starts at a different paragraph every time the anchor crosses one, so greedy packing carried across paragraph boundaries gives the same lines a different span — and so a different key — on almost every scroll. The symptoms are re-translation of text already cached, plus the same lines rendered twice where two differently-keyed spans overlap (`assembleTranslatedLines` concatenates per line, which is what `splitLongLine`'s sub-line pieces need). The cost is more, smaller calls where paragraphs are short.
2. **A paragraph with an unfetched line on either side is skipped entirely, not planned over its visible part.** A chunk minted over a prefix is a key the full paragraph will never match, so both would sit in the cache and both would render. `linesVersion` is what brings the paragraph back once its page lands.

**The anchor is `computeAnchor`'s line, not `virtualRows[0].index`.** The virtualizer's item list includes `OVERSCAN_ROWS` (24) above the viewport, so `firstIndex` (`virtualRows[0].index`) sits up to 24 lines _before_ what's actually visible. `BookReader` used `firstIndex` for chapter detection/stepping/the line display until 2026-09-19 — for up to 24 lines after really crossing a chapter boundary, `]` still detected the previous chapter and jumped back to a start already passed. Fixed by switching those to `anchorLine`; `firstIndex`/`lastIndex` stay correct only for the prefetch range (`requestRange`, now inside `useReaderPanels`), where the overscan margin is exactly what's wanted.

**A programmatic `scrollToIndex` jump's own `scroll` event can regress `anchorLine` right back.** The jump can land on a row the virtualizer has only estimated the height of — translated Vietnamese routinely wraps to more lines than the Chinese-based estimate — so once it (and earlier rows) render and measure, the virtualizer's settling shifts which line a given `scrollTop` maps to, walking the anchor backward far enough to cross back over the boundary just jumped past. `ReadingAnchor.scrollToLine` sets the anchor eagerly (safe: `align: 'start'` guarantees the target line sits exactly at `scrollTop`), queues it for writing, and discards its own next measurement for both the published anchor and the persisted position. Until 2026-09-25 only the published one skipped it: `useReadingPosition` computed its own anchor from the same scroll event and could write the walked-back line to disk.

## Clickable highlighting is chunk-scoped, and a row's runs must equal its plain text

`LineSegments.ts` converts a chunk's highlighting payload into one run list per raw file line. Two rules it exists to keep, both silent when broken:

- **`unitIndex` numbers one chunk's own semantic arrays.** A 600-character chunk is one engine call with its own arrays starting at zero, and a screen holds several, so a highlight is a `{chunkKey, unitIndex}` pair everywhere it travels (`ReaderHighlight`). A bare index lights one word per chunk on screen. The same pair is what makes the Chinese and Vietnamese panels highlight each other with no mapping step: they are two views of one unit. This is also why the highlight is cleared on a book change and on `engineVersion` — a chunk key is a line range, so it names a different passage in another book and different Vietnamese after a dictionary reload.
- **A line's runs concatenate to exactly `assembleTranslatedLines`' string for that line.** Both come from `chunkLineRanges` for that reason; slices always come from the chunk's text, never from a segment's own stored string (the Vietnamese producer tidies spaces around quotation marks inside its segment text). Break this and rows silently reflow as chunks land, because the row's character count changes the moment highlighting has something to render. The stored `translatedText` is NFC-normalized for the same reason — `matchWordSegments` measured its offsets against an NFC copy.

**The Chinese panel needs `fillSegmentGaps`, the Vietnamese one does not.** The Chinese panel renders the file's own line whether or not anything translated it, so a row a chunk covers only partly would drop the rest; the Vietnamese row _is_ whatever the chunks produced, so its runs tile it by construction. Chinese offsets are therefore the file line's own (`chunk.startChar` for a chunk's first line), while Vietnamese offsets accumulate across the chunks of a split line.

**The character-only panel's units are relabeled, not its own.** Its text comes from a second engine pass with semantic arrays of its own, so its unit 3 and the full translation's unit 3 are unrelated. `bridgeGlossSegments` rewrites each gloss run with the full-translation unit covering the same _source characters_, which is exact here because both passes ran over one identical chunk source — the Translator needs `findCharacterOnlyMatch`'s fuzzy text matching only because its two passes cover a whole document independently. Do not reach for that bridge here. A gloss run no full-translation unit covers becomes plain text rather than getting an invented index.

## Cross-panel sync is line-indexed and one-way

**Checked on macOS WebKit only.** `overflow-anchor: none` (`Reader.module.css`) is a hint whose support differs between webviews, and the per-frame resync in `usePanelSync` is what actually holds the panels together. The app is used on macOS; Windows/WebView2 has never been checked and is out of scope until someone runs it there (Reader spec #21 close-out, 2026-09-27).

`PanelSync.ts` maps a reading position between the three Reader panels as a **line index plus a sub-line fraction**, never a pixel ratio. With tens of rows visible out of 75,000+, almost every row is unmeasured, so each panel's total height is a large, shifting estimate; `scrollTop / scrollHeight` compounds three of those errors and grows worse with distance from the measured region. A line index has zero error by construction, and the fraction's error is bounded by one line height at the one place alignment is looked at.

`usePanelSync` (inside `useReaderPanels`) writes follower offsets from an **animation-frame-throttled scroll handler**, not from the reading anchor (`ReadingAnchor`), which feeds persistence and translation scheduling. The two are deliberately separate: the durable anchor can afford to arrive late, follower pixels cannot — a lag there is visible as the left panels trailing the right one during a drag.

**Only the master drives.** The translation panel is the scroll master; the reference panels are `overflow: hidden` (`.readerFollower`) and move only when the sync writes them — a wheel over one is forwarded to the master instead. Writing a follower fires its own scroll event, and that echo is recognized by **offset, not timing**: the sync remembers the `scrollTop` it last wrote each follower (read back after the write, since the browser rounds), and a follower scroll within 1px of it is ignored. Any other follower scroll — Tab focus into a row, a selection drag, the browser clamping an offset after the content shrank — calls `resync()` and is pulled back to the master. Nothing ever writes the master, so there is no lossy round trip to walk the panels apart. Until 2026-09-25 this was a multi-driver sync with a next-frame "who is driving" latch, which let a follower's stray scroll drag the master along (see `docs/guides/deleted-symbols.md`).

The measurement resync (`resync()` on any panel's total size changing) cannot fight a drag for the same reason: the reader can only ever drag the master, and the master is never written.

**The character-only gloss is a second engine pass, run after the translation is published.** `useWindowedTranslation` sets the chunk with `characterOnlyText: null`, rebuilds, and only then calls `translateGloss` — folding both into one `translateChunk` doubles the latency of every window fill for a panel that is reference material. A `null` gloss is left out of the assembled lines entirely; assembling it as `''` would blank the reference panel instead of leaving the Chinese showing.

`@tanstack/react-virtual` v3: `virtualizer.measurementsCache` is the public per-index array (measured where mounted, `estimateSize` elsewhere) — `getMeasurements()` is private, and `getOffsetForIndex()` clamps to the max scroll offset, so it is wrong for a raw row top and right for a scroll target.

**Any number the estimate depends on that Appearance owns must be measured, not hardcoded.** `useColumnMetrics` reads the panel's font size and its `--reader-paragraph-spacing` back off the scroll element; a fixed 30px line height under-estimated every unvisited region by a quarter once the font could be 1.25rem. Reading a custom property back needs unit resolution — `getComputedStyle` returns the authored token (`1rem`), not a used pixel value, hence `cssLengthToPx`. Row spacing is `padding`, never `margin`: resize observations exclude margins, so a margin makes every row under-report its height and the error compounds down the document.

**Unmeasured rows are estimated per index, never by a fixed height.** `estimateRowSize` scales the line's Chinese character count by the panel's own `emPerChar` and biases it slightly upward. A fixed skeleton height fails differently in kind, not degree: its error is systematic, so long lines are underestimated every time and the error accumulates monotonically down the document instead of cancelling.

## Records read after a write must read under the lock

Writes to `books.json` run later, on `withBookRecordsLock`; `loadBookRecords()` returns the cache as it is now. So a read that must see a write already queued has to go through the lock itself: `withBookRecordsLock(loadBookRecords)`. Example: Back queues the final position flush in `BookReader`'s unmount cleanup (`ReadingAnchor.close()`), and `ReaderTab`'s reopen branch reads under the lock so a fast reopen doesn't restore the position from before it (pinned by `ReaderTab.openBook.test.tsx`). A view that just wants to _stay_ current subscribes instead (`useBookRecords`).

## The binding is the authority; the config keys it writes are a cache

`BookBindingContext` applies a binding by writing `engine.activeProperNouns` and `ui.defaultQuickAddDictionary`, then reinitializing — and it is allowed to fail that write and carry on, because a book that will not bind must still be readable. So anything in Reader context needing "the active fiction's dictionaries" reads the binding (as `boundFictionDictionary`, below), not those keys: the config route is a longer path to the same answer through a value the Reader itself wrote, and after a failed apply it still names the _previous_ book. For the add-entry bar's Cmd-5/Cmd-6 targets, `readerQuickAddView` (`ReaderQuickAddTarget.ts`) builds the view the shared quick-add rule (`quickAddTarget`, `utils/dictionary/QuickAddTarget.ts`) decides from: config _as the binding implies it_, through the same `BindingActivation` arithmetic `BookBindingContext` writes. The rule is shared with the Translator; the view is not — never hand the Reader config as loaded. The Reader hands its view loader to `useDictionaryModals`, so every Add it opens — Cmd-1..4 included — stores that view, and the Add form's dropdown (`quickAddChoices`) offers only what the binding implies. Until 2026-09-26 only Cmd-5/Cmd-6 used it, and the dropdown read config as loaded, so after a failed apply it could offer the previous novel's dictionary. Until 2026-09-26 an unbound (or "none") book whose apply had failed filed its names under the previous novel's dictionaries that way. For a book with no fiction dictionary the view carries only config's _non-fiction_ entries, so Cmd-5 lands on a non-fiction dictionary and Cmd-6 has no target.

**Read the dictionary in use (`boundFictionDictionary`), not the recorded answer (`binding`).** They differ when the bound dictionary no longer exists: the book then reads with none, and `missingFictionDictionary` names it. Until 2026-09-26 nothing checked, so renaming a fiction dictionary in the Configuration tab left every book bound to it writing the old, nonexistent id into `activeProperNouns` on its next open, reading with no fiction dictionary and no word of why — and the Reader's Cmd-5 would have filed names under that id. Renames now carry into book records (`renameBoundDictionary`), and the open-time existence check covers what no rename sees: a reset, an import, a file renamed in Finder.
