# src/utils — Gotchas

Five properties generate almost every trap in this directory. Read the rule, then the instances under it.

📖 WASM wrapper lifecycle (retire-on-panic, cascade registry, `FinalizationRegistry`) lives in [`wasm/CLAUDE.md`](wasm/CLAUDE.md) — scoped there since it's entirely about `src/utils/wasm/*.js`.

---

## 1. These APIs do not validate their arguments — a wrong one degrades silently

No throw, no warning, no error. The wrong value produces plausible-looking output with a piece missing, which is why these keep recurring. Check the signature at the call site.

| Call                                    | Wrong argument                                                                                                | What silently happens                                                                                                                                                                                                                                                                                                                              |
| --------------------------------------- | ------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `addUnit(…, source, …)`                 | `'patterns'`, `'numbers'`, `'passthrough'`, or `match.dictionary`                                             | `getSourcePriority` returns 999, below the character fallback. Correct: `'pattern'`, `'number_conversion'`, `'characters'`, `'phrases'` — only an active proper-noun dictionary name is a valid `source` besides these (`isActiveProperNounSource`)                                                                                                |
| `engine.initialize(options)`            | omitted `options.activeProperNouns`                                                                           | Falls back to `['properNouns']`, and `filterDictionariesForEngine` drops every `properNouns-*` novel dict, so names go un-capitalized. Pass all dictionaries (the engine filters them); the engine never reads config from disk. Call sites: `useTranslatorEngine.js` (initial load, and force reload via `reinitialize(forceConfigReload: true)`) |
| `getSemanticTokens(x)`                  | a string (e.g. `chunk.content`)                                                                               | Returns `[]`. For chunk token counts use `this.tokenizer.tokenize(chunk.content).length`; the wrong call zeros all cross-chunk offsets and breaks same-translated-text disambiguation                                                                                                                                                              |
| `validatePhasePriority(p)`              | `PHASE_PRIORITIES.patterns` / `.properNouns` / `.numbers`                                                     | All three are `undefined` — those keys are `translationSource` strings, not phase-group labels. Pass a literal `1\|2\|3\|4\|5`                                                                                                                                                                                                                     |
| `TokenType.X` in `TranslationEngine.js` | a member that doesn't exist (`SPACE`/`NEWLINE` — the enum has only `WHITESPACE`, `PUNCTUATION`, `UNKNOWN`, …) | Evaluates to `undefined`, no throw: `!== TokenType.SPACE` is always true and a `case` never matches. The file is JS, so `tsc` can't see it. Check `TextTokenizer.ts`'s enum (2026-10-03: whitespace tokens warned and were silently dropped)                                                                                                       |

Same shape, different mechanism: **a caller-supplied numeric limit defaulted with `||` treats a legitimate `0` as absent**, and **a memo read with `if (cached)` treats a cached `null` (a known miss) as absent** (`DictionaryManager.translate` re-walked the trie for every miss until 2026-10-10): test `!== undefined`. The deleted `WasmMemoryPoolManager`'s `initialPoolSize`/`shrinkThreshold` had the identical bug. Grep for `|| 50` / `|| 30` style defaults before assuming `0` is impossible.

## 2. Code that looks redundant here is load-bearing — each of these was already removed once, and broke something

Treat this list as the answer to "why is this checked twice?" The second check is not the same check. Each entry is a claim about live code: confirm it still has a production caller before honoring it — two entries here defended code that never ran (the Phase 2/4 conflict inversion and `buildTypeFilter`, both deleted 2026-09-26).

- **`resolveGlobalConflicts` (Phase 4) lets phrases beat patterns at equal length**, because Phase 1 pattern tokens are already consumed by then. **In practice that tie-break never fires against a real Phase 1 winner**: `processRemainingPhrases` skips any phrase candidate whose span holds a claimed token (`isClaimed`) first, and only `type: 'phrase'` entries enter the pool. A phrase-dictionary entry **cannot** override a winning pattern; the only lever is a competing **pattern** entry, which wins ties in Phase 1's `find_best_pattern_match` via fewer variables (see `dictionary/CLAUDE.md`'s Pattern Variable Contract). The Phase 2 twin `resolveMatchConflicts` was dead and is deleted (`docs/guides/deleted-symbols.md`).
- **`applyHierarchicalResults` has no overlap check** — `select_optimal_results` in `wasm-core/src/pattern_processor/two_phase.rs` already guarantees non-overlapping results. A JS-side dedupe would mask WASM selection bugs instead of surfacing them.
- **`applyMatchToTokens`'s orphan-release loop** — when Phase 2+ overwrites a Phase 1 leader, it scans forward from `startIndex + tokenSpan` and resets orphaned `*_consumed` followers to unprocessed. Without it, Phase 2's skip guard and `postProcess` silently drop those tokens, violating the never-omit-content contract.
- **`postProcess`'s `else if (token.translationSource)` orphan safety net** — recovers consumed Chinese tokens whose `groupLeader === null` (released by orphan-release) or whose leader has `translated === null`, via char dict fallback. Do not collapse to `continue`.
- **`WordSegmentMatcher.matchWordSegments` pass 2 reuses pass 1's `foundWords[i].position`** — given pass 1's global pairwise non-overlap guarantee and pass 2's strict left-to-right walk, an independent `indexOf` re-search can mathematically never diverge. It is not a safety net; it cannot catch anything.
- **`SegmentPrecomputer.ts`'s two scan loops are not unification candidates** — `precomputeOriginalSegments` (Chinese panel) does raw exact `startsWith` with grapheme-cluster indexing; the deleted `precomputeSegments` (Vietnamese panel) did punctuation-skip and case/whitespace-normalized matching. Genuinely different matching problems. See ADR-036.
- **`cleanupFormatting`'s `^` capitalization needs `capitalizeStart`** — `postProcess` (every Full Translation chunk) passes `false`, `finishCharOnlyText` passes `true`. Without the option the rule capitalizes every chunk's first letter independently and overrides `applySmartCapitalization` context.
- **Phase 4 (`processRemainingPhrases`) reads no pattern setting** — phrase processing is pure JS and runs whether or not structural patterns are loaded. Do not gate it on the Pattern Store's state (`enabled`, `processor`, `patterns?.length`) (ADR-006 addendum; pinned in `TranslationEngine.pipeline.test.js`).
- **Do not wire `SemanticArrayMetadata.translatedStart`/`.translatedEnd` validity into `checkSemanticArrayCorruption`.** Both are `-1` from `addUnit` until `postProcess`'s position loop runs, after all 5 phases; the check fires during each phase, so it would flag every entry of every translation.
- **Deleting code's only caller or writer orphans what it called and what it wrote — after every deletion, grep each callee and each field the deleted code assigned.** Examples: removing the sole assigner of engine segments' `translatedStart` left `_logUnpositionedSegments` (`=== -1`) warning on every progressive translation; deleting `translateWithChunking` left `ChunkPostProcessor.reconstructTextWithSegments` callerless. The inverse hides in JS: a method deleted from a TS class leaves its JS callers calling nothing, so grep the name in `*.js`/`*.jsx` and `.d.ts` option types. A `typeof x.m === 'function'` guard hides the dead call for good; an unguarded one throws only when its branch runs, so a failure-only branch needs a test that drives it (`getCorruptionTelemetry()` threw a `TypeError` at every phase checkpoint for months). Same in reverse for a clear: `invalidateDictionaryCaches` emptied `properNounTranslations`, whose only writer is `initialize()`, so casing restoration stopped after the first dictionary edit until a reload. Before clearing state in a targeted invalidation, grep who rebuilds it. Same for the declarations, parameters, comments and docs that name or promise the deleted thing: after a deletion, grep its class and sibling names in `*.d.ts`, `@import` lines (a JS file's `@import` of a missing type is never flagged), comments, `docs/`, `.claude/skills/` (the corpus-ab harness reads engine fields; it still named `semanticPatternProcessor` ten days after ADR-101) and file headers — and the behaviour in words (`invalidat` for an invalidation), since ADRs and GLOSSARY.md describe behaviour, not symbols: a name-only sweep missed ADR-055's decision 5 and ADR-052 (2026-10-20). ADR-101 left seven dead types, `initialCache` and "both adapters" in six files, and ADR-080's deleted hash check was still advertised in `CSP_SECURITY.md` and a source header (both fixed 2026-10-11). The inverse: **adding a second caller falsifies every "sole caller" / "the only phase that" claim** — grep those phrases in `GLOSSARY.md`, comments and tests, and run the full suite before calling a pin verified (a Phase 2 test asserted `findMatchesAtToken` was Phase 2's alone until Phase 4 joined it, 2026-10-24; the pin's own break-check, run on one file, never saw it).
- **Two implementations of one classification must be kept in sync by construction, not discipline: hand-copied DATA (a predicate, a regex alternation, a char array) drifts from its source of truth.** Derive the copy, give it one owner, or pin both with a shared fixture. Examples: `applySmartCapitalization`'s punctuation arrays vs `capitalizationRules` (now derived); `PatternTemplateEngine.isVariableChar` reimplemented as raw `[A-Z]` in two validators (now `PatternEntryRules.ts`); `NumberProcessor.findLongestNumberMatch`'s hand-counted token window undercounting `percentage` by 1 (now `test-fixtures/number-parity.json`). Duplicated LOGIC using that data at different call-time granularity is a different animal; check before merging. The `parseChineseNumber` and window drifts do NOT implicate the range-family converters (`convertTenThousandRange` etc.).
- **Scaffolding that only calls itself or its own tests keeps getting built and never wired in (`getDebugInfo()`, `createScopedLogger()`): grep the WHOLE `src/` tree, `docs/guides/`, and call shapes (`engine.X(`, `this.X(`, optional `x.X?.(`) before trusting a local "looks used" read.** A `getDictionary\(` sweep missed the `getDictionary?.('phrases')` caller and called the method two-caller (2026-10-24). A bare-name scan misses a dead method whose name a live one shares (`TranslationEngine.clearCache` vs `DictionaryManager.clearCache`); follow the chain across the JS→WASM→Rust seam (`resolveMatchConflicts` → `resolveMatchConflictsCore`); `window.translationEngine` exposes every engine method to devtools, and `development.md` names `getGlobalStats`/`getMemoryUsage` as console reads, so decide deliberately whether a zero-caller method is a console tool.

## 3. Implementations that must move together

Changing the algorithm in one and not the other produces divergence that no test catches at the seam.

**WASM is the only pattern matcher (ADR-101).** `PatternStore.js` parses the pattern dictionary, owns the WASM processor's init and decides whether Phase 1 runs; it does no matching itself. When WASM cannot run, Phase 1 is skipped and the user gets an error toast. A fix to pattern matching lives in `wasm-core/src/pattern_processor/` and is verified by `cargo test --manifest-path wasm-core/Cargo.toml`; vitest only reaches Rust through `TranslationEngine.phase1.test.js`, which loads the real binary.

| Rule                         | Lives in                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| ---------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Spacing (11 rules)           | `src/utils/text/TextAssembly.js::needsSpace()` (fixture `test-fixtures/text-assembly-parity.json`, run by `TextAssembly.parity.test.js`; positions are UTF-16 code units; the Rust twin is deleted, ADR-079) **and** `src/utils/text/CharOnlySpacing.ts::needsSpaceCharOnly()`, a third adapter that decides from the original (untranslated) token stream, tested standalone in `CharOnlySpacing.test.ts` and called by `CharOnlyAssembly.ts`                                                                          |

## 4. Position arithmetic in `postProcess` has four independent traps

- **`token.start` is a UTF-16 index into the NFC-normalized text, never a byte offset.** `TextTokenizer.tokenize` normalizes first, so for text that is not already NFC the index does not point into the caller's string. Anything else keyed by position must index that same NFC text, or every lookup after the first composed sequence (か+U+3099) lands one off. Chunk `startIndex` is UTF-16 too. For arithmetic against JS strings use cumulative `tokenCharPositions[i] = sum of tokens[0..i-1].value.length`.
- **The `tokenCharPositions` loop must read `originalValue ?? value`.** Phrase processing sets `tokens[K].originalValue = tokens[K].value` (`"部"`) then mutates `.value` to the full word (`"部分"`). Reading `.value` double-counts and shifts every subsequent `originalStart` by the consumed-token count.
- **`postProcess` positions are chunk-local; `originalStart` must be global.** `tokenCharPositions` counts from the chunk's own content, so anything stored as an offset into the whole text needs `options.chunkCharOffset` (`TextChunk.startIndex`) added. Leading punctuation is its own empty chunk, so the first content chunk starts past 0 (`“金玉律！”` stored `[0,1,2]` for `[1,2,3]`). `tokenIndex` has the same split (`chunkOffset`).
- **Whitespace regexes must preserve `\n`.** Any `replace()` on `cleanedFinalResult`, the `wordSegments` rebuild, or `normalizeLineWhitespace` (`FormattingPasses.ts`) uses `[ \t]+` or `[^\S\r\n]+`, never bare `\s+`, which silently drops paragraph breaks next to quotes and punctuation (`"Dòng một\n。"` came back as `"Dòng một。"`). To optionally swallow a break use an alternation with an empty branch, `[^\S\r\n]*(\r?\n|)[^\S\r\n]*`, not `?`, so the replacement never interpolates `"undefined"`. `TranslationEngine.regression.test.js` pins one call site, not the class.
- **Any post-assembly text mutation that changes length after click-to-highlight positions are recorded desyncs them.** `translateDirectly` records `assembledPositions` from `assembleWithSpacing()`'s output, then runs `cleanupFormatting()` on that string; a regex there that inserts/removes a char (the period-space rule on `NumberProcessor`'s `"99.9%"`) shifts every later position silently. Run any new post-`assembleWithSpacing` transform before the position loop, or prove it length-preserving.

## 5. State has one owner — do not re-add a local copy

Each concern below once existed as copies on the engine or a caller, and the copies drifted. Use the owner; the "do not" is the non-obvious part.

- **Engine teardown: `destroy()`** (clears `processedBatchCache`, `semanticArrayBuilder`, the pattern variable cache, `dictionaryManager` caches). Called by `useForceReload` and by `useTranslatorEngine.js`'s `runEngineInit` before every replacement; the second call is a no-op. Do not re-add manual cache clearing in reload paths.
- **Semantic array construction and validation: `SemanticArrayBuilder.ts` and `SemanticArrayValidator.ts`.** Add fields to `SemanticArrayMetadata` (declared once, in `src/types/SemanticTypes.d.ts`, with `SemanticArrays` and `Segment`), init in `addUnit()`, handle in `setPositionByMatch()`; no sibling needs a field sync. Do not duplicate the capacity/sync check on the builder.
- **Whether Phase 1 runs: `PatternStore`.** It builds the processor, holds the one `PatternFailureTracker` (warns, resets or disables), shows every Phase 1 toast, and answers `matchTokens` with results or `null`. A failure that leaves `isWasmPatternProcessorReady()` false (a panic retires the processor for good) disables at once with one toast, bypassing the tracker. The tracker measures its window from the first failure of a run, so a processor that never worked disables too. Do not add a failure counter, a Phase 1 flag or a pattern toast to the engine or to `WasmPatternProcessor.js` (its toast was deleted 2026-10-24, ADR-101 addendum). An `applyHierarchicalResults` error is not a matcher failure (ADR-101 addendum 2026-10-21).
- **Pattern processor readiness: `isWasmPatternProcessorReady()`.** Do not compose a second check from the wrapper's internals.
- **Token source strings: `consumedSource()` / `isConsumedSource()` / `isPatternSource()` / `validateConsumedTokenContract()` in `TranslationSourcePriority.ts`.** Do not concatenate or test the `_consumed` suffix, or hand-list Phase 1 sources, elsewhere.
- **Variable cache lookup stages: `PatternVariableCache.js`** (`TwoPhasePatternProcessor.processTokens` calls it directly and times it). Do not mirror phrase-type or full-text-scan changes into the processor, and do not re-add a stage that reads `translated` off the tokens: Phase 1 runs on freshly tokenized text, so none is set (a stage did, until 2026-10-24; see `deleted-symbols.md`). Canonical phrase type fallback is `metadata?.semanticType || 'concept'`, not `'phrase'`; the typing rule is `resolveType` inside `PatternVariableCache.js`.
- **Writing a match onto tokens: `placeSpan` / `placeGroupedSpan`** (`TokenClaim.ts`; GLOSSARY.md "TokenClaim", ADR-109): the claim plus the semantic unit, from one `source`. Phase 1 and 3 use the light shape, Phases 2, 4 and 5 the grouped one. Do not call `addUnit` beside a claim; pass `{ builder: null }` to place without recording. Do not hand-write a leader/follower loop at a new phase, and do not set `translated`/`translationSource` on a span's tokens elsewhere; the Phase 5 sentinels and `NumberLiangFix` are the two deliberate exceptions. Reading a claim is `isClaimed(token)` from the same module: do not hand-write a `translated !== null || translationSource || isGrouped …` check (four shapes of it drifted, one carrying a flag with no writer).
- **App file cache, lock, unread refusal: `createAppFile`** (`appFile.ts`; GLOSSARY.md "App file"). Each file's module supplies only IPC calls, a parser and its failed-read behavior. Do not add a `let cache`, a hand-rolled `Promise`-chain lock or an `unread` flag, or a save that is not a `transform`.
- **Dev console globals: `installDevConsole(engine)`** (`__devtools__/DevConsole.js`). Do not add debug utilities in App.jsx or Translator.jsx.
- **Token ordering by text position: `compareByTokenIndex` / `resolveTokenIndex`** (`TextPositionMapper.ts`; missing/negative `tokenIndex` sorts last). `processChunksInParallel` assigns semantic array indices by chunk **completion** order, not text order, so every ordering by position goes through it: `WordSegmentMatcher.ts` (same-length tiebreak), `SegmentPrecomputer.ts` (`precomputeOriginalSegments`), and `CharacterOnlyBridge.ts`'s `findCharacterOnlyMatch` neighbor slices. Hand-rolled comparators caused an intransitive-comparator bug and a disagreement on the missing-`tokenIndex` fallback. `CharacterOnlyBridge.ts`'s `occurrenceInSource` is a separate linear count with its own dual-sided fallback, not a sort; do not force it through the comparator.

Dev console commands are never automatically tested and rot silently (a guard property that stopped existing; `window.runPatternParityTests` referenced a property that never existed). Invoke any new command manually once to confirm its guard passes.

## Token and phase semantics

- **`isGrouped` discriminates phrase followers from pattern-consumed tokens.** Both set `groupLeader`. Phrase follower: `isGrouped = true`, `translationSource = 'phrases_consumed'`. Pattern-consumed: `isGrouped` unset, `translationSource = '*_consumed'`. Filtering by `groupLeader` alone conflates them — `getSemanticTokens` uses `isGrouped && groupLeader !== null` to exclude only phrase followers. **Phase 4 reads its matches through `findMatchesAtToken`, as Phase 2 does**, never from text rebuilt out of the tokens and addressed by `token.start`: a grouped leader's `value` is the grouped text, one shorter per space the span skipped (`墨 子` as `墨子`), so such text runs behind `.start` (until 2026-10-24 Phase 4 did that, and every phrase after a space-spanning name was missed: `墨 子在这里` gave `giá lý` for `这里`; ADR-108 addendum). Pinned in `TranslationEngine.pipeline.test.js`.
- **Every phase must set `groupLeader = startIndex` on consumed tokens at the mark site.** `=== undefined` triggers char-fallback exactly like `null` does, silently corrupting every multi-token match from that phase. `applyMatchToTokens` (Phase 2/4), `applyHierarchicalResults` (Phase 1), and `NumberProcessor.applyConversionResult` (Phase 3 JS) all set it. **`copyWasmTokens` does not copy `groupLeader`** — WASM-path phases need a post-`copyWasmTokens` sweep.
- **A match span is a token count from the start through the last matched token, including non-semantic tokens between them.** The lookup (`reconstructTextFromIndex`) stops only at punctuation, so `墨 子` matches `墨子` across the space; `getTokenSpanForText` counted just the matched tokens, `claimGroupedSpan` claimed that many, and 子 fell to Phase 5 (`Mặc Tử tử`, fixed 2026-10-13).
- **Phase 1 output has no `isGrouped`/`groupedWith`.** `applyHierarchicalResults` marks only `translationSource`, `translated`, `groupLeader`. Detect a Phase 1 leader via `translated !== null && translationSource && !translationSource.endsWith('_consumed')`, never via `isGrouped` or `groupedWith.length` — always `false`/`0` there.
- **Phase 2 proper noun lookahead:** `applyProperNouns` defers a match at position i if any j ∈ [i+1, i+tokenSpan) has a **strictly longer** match — stops "日元" (2 chars at i=1) consuming the 元 that "元始圣人" (4 chars at i=2) needs. Same-length matches at a later position do not defer; earlier start wins (孔宣 beats 宣兄). Applies to shared-index and fallback paths alike.
- **`find_best_pattern_match` / `findBestPatternMatch` tie-break order:** longer match wins, then fewer variables (more literal chars = more specific), then higher priority, then **whichever candidate is iterated first** — `is_better` requires a strict improvement, so a full tie silently resolves by position. Without rule 2, a 2-variable `X的Y上` silently beats a 1-variable `X的手腕上` at equal length. Do not reorder, and any change to how the candidate set is built (filtering, indexing, chaining slices) must emit candidates in their original slice order or it changes output — `VariableLiteralIndex::collect_candidates` sorts indices ascending for exactly this reason.
- **`checkSemanticArrayCorruption` toasts at most once per translation** via a translation-scoped `let corruptionToastShown = false`; `isCorrupted` (the builder's sticky getter) stays true across all 5 phase checks and the final one after `postProcess`, which reuse the flag. Any new site that toasts on `isCorrupted` must reuse it. The builder has no telemetry method (`TranslationEngine.corruption.test.js`).
- **`allowedVariableTypes` is enforced in Rust by plain string equality** (`matcher.rs::is_variable_type_allowed`) — no Rust list of `SemanticType` values exists, so adding, removing, or renaming one in `src/constants/SemanticTypes.ts` never requires a Rust change. One type is special-cased there: `number` fills only the `#` variable (see `wasm-core/CLAUDE.md`). Semantic token types: `chinese_char`, `chinese_word`, `latin_word`, `number`. Fiction dicts (`properNouns-f_*`) contain all `SemanticType` values — `metadata.semanticType` is authoritative and the heuristic fires only when it is absent.
- **Never fake per-call isolation by swapping a `this.*` field.** `this.<field> = perCallValue` around an `await` does not isolate calls dispatched via `.map()`/`Promise.all`: each async function runs synchronously to its first `await`, so every call's swap runs before any does real work and all but the first capture the wrong value (the root cause of the deleted `isolatedSemanticBuilder`). Pass the value as a parameter or closure.

`SemanticArrayMetadata` tags each field by who reads it: `tokenIndex` is consumed by both highlighting paths; `originalStart`/`originalEnd` are written by Full Translation's `postProcess` only and read by `precomputeOriginalSegments`. `buildSegmentsFromPositions` fires only when **all** `metadata[].originalStart >= 0`, so in practice only for single-chunk texts (no internal punctuation): in a later chunk `postProcess` calls `setPositionByMatch` with a chunk-local `tokenIndex` while `addUnit` stored the global one, so no unit matches and `originalStart` stays `-1` (ADR-036 addendum). Test short and long texts separately when changing anything upstream of it.

## Punctuation, quotes, and chunk boundaries

- **The formatting passes live in `src/utils/text/FormattingPasses.ts`, not on `TranslationEngine`**: `cleanupFormatting`, `applySmartCapitalization`, `capitalizeFirstLetter`, `applyCharOnlySupplements` and the per-mode finishing entry points (`finishFullText`, `cleanFullText`, `finishCharOnlyText`; GLOSSARY.md "TextFinishing") are pure functions; test them with plain inputs (no engine boot). The engine passes the punctuation lookup (`engine.lookupPunctuation`) and `this.properNounTranslations` and owns only the call ORDER, except the Full Translation tail whose order lives in `text/FullTextAssembly.ts` with its twin `CharOnlyAssembly.ts`. `applyCharOnlySupplements` is a third capitalization rule set kept beside the other two; reconcile them there, not in the engine.
- **`cleanupFormatting()` cannot move to WASM.** It runs the hard-coded punctuation list in `FormattingPasses.ts` through the dictionary lookup first (the injected `translatePunct` lookup — the blocking constraint), then space-after-punctuation, colon-quote handling and the `capitalizeStart` rule. It has one path; a second `useChunking !== false` branch that nothing reached was deleted 2026-10-24. It is the single authoritative post-assembly cleanup in `postProcess()` — do not duplicate the logic elsewhere.
- **`translatePunctuation` runs twice per chunk, and `translatedPunctuation` is always derived from `chunk.punctuation`, never from itself.** The batch loop translates each batch, then `assembleFullText` translates every chunk again for cross-chunk comma spacing. Because the second run starts from the source punctuation again, it gives the same result; applying the dictionary to its own output would not (`……→…` gave `……` in the preview and `…` in the final text, and `「→“` with `“→"` ended as `"`). This was a `chunk.punctuationTranslated` flag until 2026-10-11; do not read `translatedPunctuation` as the dictionary's input, and do not preset it expecting it to be kept (a preset is overwritten). The scan is one pass, longest key first, so entries do not chain. Pinned by the two-pass block in `ChunkPostProcessor.test.js`.
- **Phase 5 (`processRemainingTokens`) is a point lookup, `DictionaryManager.lookupCharacter(token.value)`, because every `characters` key is one code point** (ADR-087). It does not read `findMatchesAtToken` and has no longest-match loop, so a multi-character `characters` key never matches there; `DictionaryManager.loadDictionaries` warns on one. Do not restore a span search without changing that rule.
- **`processCharacterOnlyTokens` stamps only `chinese_char` tokens.** `applyMatchToTokens` returns at once for any other start token, so a punctuation lookup there stamps nothing. Punctuation is translated afterwards by `cleanupFormatting`'s `lookupPunctuation` (ADR-089). Do not restore a punctuation matcher in that pass without first making `applyMatchToTokens` accept a punctuation start token.
- **The character-only pass writes nothing to `this.*`.** `processCharacterOnlyTokens` passes `recordMatches: false` to `applyMatchToTokens`, which skips the shared `semanticArrayBuilder.addUnit`; `translateWithCharactersOnly` hands the stamped tokens to `assembleCharOnlyResult` (`text/CharOnlyAssembly.ts`), which adds the units to a private builder. The pass awaits nothing (a point lookup, ADR-087), so it runs start to finish without yielding. Pinned by `TextFinishing.test.ts` (`character-only pass leaves the engine state of Full Translation alone`). The remaining Translator-vs-Translator and Translator-vs-Reader `reset()` overlaps are the accepted gap in `src/utils/reader/CLAUDE.md`.
- **Spacing/cleanup regexes near Chinese/digit/punctuation boundaries must allowlist, never denylist: a denylist silently admits every new punctuation mark.** (1) Space after a Chinese char: the WASM tokenizer types some chars (`…`, `》`) as `unknown`, so add a space only when the next token is `chinese_char`, `latin_word`, `TokenType.NUMBER`, or opening-element punctuation, never via `!== 'punctuation' && !== 'whitespace'`. (2) `spaceLettersAndDigits` matches `\p{L}` letters instead of excluding `,.-+%()/~`, which missed `!?:;` and closing quotes (`"2,700!"` → `"2,700 !"`). (3) Anything touching `.` must treat it as a decimal point only with digits on BOTH sides: excluding only a following `\d` also suppressed the space after a real sentence end (`...rồi.5 người`), and the char-only capitalize-after-punctuation regex needs `[^\p{L}\d]*`, not `\P{L}*`, or `1.75 mét` capitalizes `mét`. Audit any new regex touching `.`. (4) The closing-quote class in `cleanupFormatting`'s three spacing rules is derived from `QUOTE_CATEGORIES.CLOSING` (`FormattingPasses.ts`); three hand-typed copies once left `’` out of two, so character-only gave `『你好。』` as `. ’` (fixed 2026-10-24). Full Translation never hit it: a chunk's content holds no punctuation.
- **A character with two roles needs both neighbours checked before a spacing rule treats it as punctuation.** `.` between digits is a decimal point; `’` between letters is an apostrophe, not a closing quote (`Thori’dal` was split into `Thori’ dal`, desyncing every later highlight). The same check applies to any new quote or period rule.
- **`「` (U+300C) is not an opening quote** — `QuoteProcessor.isOpeningQuote('「')` returns false, so `fixAngleQuotePositioning` skips it. That function fires for `《`, `〈`, and curly quotes, and uses `chunk.translatedPunctuation || fallback` so dict mappings (`《→«`, `〈→<`) survive. Colon context in a skipped chunk's `startedBy` is not propagated to the content chunk here; `applySmartCapitalization`'s fallback block (checking `chunks[i-1].content.trim() === ""`) handles that instead.
- **Quote-adjacency rules must scan for a closing+opening quote PAIR, not just the immediate first/last char — same gap hit spacing and capitalization.** `PunctuationProcessor.processSequence` needs `!endsWithOpeningQuote` in `needsTrailingSpace` (WASM combines consecutive punctuation like `”《`/`！”“` into one field); its space-between-quotes branch must gate on any non-space prefix before the trailing opening-quote run, not `CLOSING_PUNCT.includes(result[0])` — that missed sentence-ender+quote sequences (`！”“`, three back-to-back dialogue lines). `TranslationEngine.js`'s char-only capitalize-after-punctuation regex had the mirror bug: required `\s+` immediately after `.!?`, missing `!” “x` where a closing quote sits before the space — fixed to `\P{L}*\s\P{L}*`. Fixed 2026-08-29.
- **Separate empty-content chunks come from leading punctuation, not mid-text punctuation.** The JS chunker's char-loop flushes only when a content char follows accumulated punctuation, or at end of input — mid-text punctuation merges onto the still-open preceding chunk. `chunkText('道：「说')` yields `[{content:"道", punctuation:"：「", startedBy:"start"}, {content:"说", punctuation:"", startedBy:"：「"}]`. Leading punctuation (`《标题》内容`) is what produces `{content:"", punctuation:"《", startedBy:"start"}`. Verified against `TextChunker.chunkText()`; an earlier worked example here was wrong.

## Dictionaries

- **There is no persisted trie cache** (deleted 2026-10-05, ADR-075). `DictionaryManager.loadDictionaries` builds every trie from the loaded JSON with `buildTrieFromDictionary` (19–92 ms for all dictionaries together). Old `*.trie.json` files in the dictionaries directory are orphans nothing reads; Rust still excludes the name from dictionary listing and ZIP import.
- **Check any entry-shape assumption against the production dictionaries, not unit-test fixtures.** The bundled `src/dictionaries/*.json` are samples too (`characters`: 340 entries, no 两, against 13,338 in production), so a rule keyed to a dictionary VALUE (`NumberLiangFix` needs 两 → `lưỡng`) can only be checked against the production file. Entries are a bare string (legacy) or `{translation, allowAsPatternVariable, semanticType?, …}`; in `properNouns*.json` 29,647 of 29,974 are objects. A `typeof v === 'string'` filter drops them silently — `ProperNounCapitalizationMap.ts` did until 2026-10-04, with a test pinning the skip. Readable in the default sandbox (2026-10-10); use `dangerouslyDisableSandbox` only after an EPERM.
- **Trie-node metadata is `{allowAsPatternVariable, semanticType}`** — the only two fields trie readers use (`PatternVariableCache`, `VariableTypeClassifier`). Per-dictionary `priority` lives in `DictionaryManager.metadata`; pattern priority is computed in Rust (`pattern.rs::calculate_priority`). Neither reads a trie node, so do not add `priority` or `allowedVariableTypes` back to nodes.
