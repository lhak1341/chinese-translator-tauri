# src/utils — Gotchas

Five properties generate almost every trap in this directory. Read the rule, then the instances under it.

📖 WASM wrapper lifecycle (retire-on-panic, cascade registry, `FinalizationRegistry`) lives in [`wasm/CLAUDE.md`](wasm/CLAUDE.md) — scoped there since it's entirely about `src/utils/wasm/*.js`.

## 1. These APIs do not validate their arguments — a wrong one degrades silently

No throw, no warning, no error. The wrong value produces plausible-looking output with a piece missing, which is why these keep recurring. Check the signature at the call site.

Correct: `'pattern'`, `'number_conversion'`, `'characters'`, `'phrases'` — pass `match.dictionary` as arg 6 instead                                                                                                                                                                                                                                        |

Grep for `|| 50` / `|| 30` style defaults before assuming `0` is impossible.

## 2. Code that looks redundant here is load-bearing — each of these was already removed once, and broke something

Treat this list as the answer to "why is this checked twice?" The second check is not the same check.

- **`resolveGlobalConflicts` (Phase 4) lets phrases beat patterns at equal length**, because Phase 1 pattern tokens are already consumed by then. Its Phase 2 twin with the inverse order, `resolveMatchConflicts`, was called only from the dead `createPhraseGroups` and was deleted 2026-09-26 along with its WASM export (`resolveMatchConflictsCore`) — the "architectural inversion" this bullet used to defend had not run in production; see `docs/guides/deleted-symbols.md`. **In practice the Phase 4 tie-break never fires against a real Phase 1 winner**: both `resolveGlobalConflicts` call sites (`processRemainingPhrasesSequential`/`processRemainingPhrasesParallel` in `TranslationEngine.js`) skip any phrase candidate overlapping an already-`translated`/`translationSource`-set token before conflict resolution runs, and only `type: 'phrase'` entries are ever pushed into that pool. So a phrase-dictionary entry **cannot** override an already-winning pattern — the only lever is a competing **pattern** entry, which races the original inside Phase 1's `find_best_pattern_match` and wins ties via fewer variables (verified 2026-08-29; see `dictionary/CLAUDE.md`'s Pattern Variable Contract for the 0-variable-pattern mechanism this enables).
- **`applyHierarchicalResults` has no overlap check** — `select_optimal_results` in `wasm-core/src/pattern_processor/two_phase.rs` already guarantees non-overlapping results. A JS-side dedupe would mask WASM selection bugs instead of surfacing them.
- **`applyMatchToTokens`'s orphan-release loop** — when Phase 2+ overwrites a Phase 1 leader, it scans forward from `startIndex + tokenSpan` and resets orphaned `*_consumed` followers to unprocessed. Without it, Phase 2's skip guard and `postProcess` silently drop those tokens, violating the never-omit-content contract.
- **`postProcess`'s `else if (token.translationSource)` orphan safety net** — recovers consumed Chinese tokens whose `groupLeader === null` (released by orphan-release) or whose leader has `translated === null`, via char dict fallback. Do not collapse to `continue`.
- **`WordSegmentMatcher.matchWordSegments` pass 2 reuses pass 1's `foundWords[i].position`** — given pass 1's global pairwise non-overlap guarantee and pass 2's strict left-to-right walk, an independent `indexOf` re-search can mathematically never diverge. It is not a safety net; it cannot catch anything.
- **`SegmentPrecomputer.ts`'s two scan loops are not unification candidates** — `precomputeOriginalSegments` (Chinese panel) does raw exact `startsWith` with grapheme-cluster indexing; the deleted `precomputeSegments` (Vietnamese panel) did punctuation-skip and case/whitespace-normalized matching. Genuinely different matching problems. See ADR-036.
- **`buildVariableCache`'s `shouldInclude` needs its `hasUnconstrainedPatterns` guard** — `requiredTypes` filtering is only correct when every pattern is constrained; one unconstrained pattern accepts any type, so filtering would exclude entries it needs. `if (!requiredTypes || hasUnconstrainedPatterns) return true;`
- **`cleanupFormatting`'s `^` capitalization needs `!options.isParallelChunk`** — each parallel chunk runs with `useChunking: false`, so without the guard the rule capitalizes every chunk's first letter independently and overrides `applySmartCapitalization` context.
- **`createOptimalPhraseGroups` (Phase 4) checks only `enableTwoPhasePatterns`, not `patterns?.length`** — phrase processing is pure JS and runs whether or not structural patterns are loaded. Do not re-add a `patterns?.length > 0` guard.
- **Segment cleanup's synchronous hard ceiling** — `MEMORY_THRESHOLDS.SEGMENT_CLEANUP_TRIGGER` (75) is idle-deferred and `SmartMemoryCoordinator`'s backstop is pressure-reactive (10s sampling); neither bounds `translationSegments.length` deterministically. `SEGMENT_CLEANUP_HARD_CEILING` (100) trims synchronously at the push site. `Translator.jsx` had a caller-side watchdog for this exact gap, deleted 2026-07-24. If segments ever exceed 100 the bug is in the engine's own cleanup — do not patch it from `Translator.jsx`.
- **Do not wire `SemanticArrayMetadata.translatedStart`/`.translatedEnd` validity into `checkSemanticArrayCorruption`.** Both initialize to `-1` in `addUnit` and stay `-1` until `postProcess`'s position-tracking loop runs, _after_ all 5 phases. The corruption check fires _during_ each phase, so it would see `-1` on every entry of every translation — 100% false positive, not an edge case. Shipped and reverted same-day, 2026-08-16.
- **Two independently-implemented checks over the same classification must be kept in sync by construction, not discipline — hand-copied DATA (a predicate, a regex alternation, a char array) drifts from its source of truth. Duplicated LOGIC using that data at different call-time granularity is a different animal, check before merging (see this section's own theme).** Confirmed drift instances: `validateConsumedTokenContract`'s `.includes('_consumed')` predicate must match `getSourcePriority`'s check exactly (no derivation link — pure discipline, watch this one). `NumberProcessor.parseChineseNumber`'s internal hundreds/thousands regex was narrower than the top-level match regex it was supposed to mirror (see `wasm-core/CLAUDE.md`; fixed by matching Rust's `(.*)` catch-all shape, 2026-08-29). `applySmartCapitalization`'s three hand-copied punctuation arrays drifted from `capitalizationRules` (fixed by deriving them from it, 2026-08-29). `capitalizeFirstLetter`'s leading-digit skip (chunk-based path) drifted from `translateWithCharactersOnly`'s sibling regex — missing the `/\d/.test(pre) ? m : ...` guard that keeps "500 năm" lowercase, wrongly producing "500 Năm" (fixed 2026-08-31). Pattern-variable classification (`PatternTemplateEngine.isVariableChar`) was independently reimplemented via raw `[A-Z]`/`[XYZ]` regex in `PersistTimeValidator.ts`/`DictionaryEntryValidator.ts`, missing that a capital letter fused to a real word (e.g. the Y in Vietnamese "Yến") isn't a variable — unified into `PatternEntryRules.ts` 2026-09-07. `NumberProcessor.findLongestNumberMatch`'s hand-counted token window undercounted the `percentage` pattern's max decimal span by 1, silently truncating `百分之一千二百三十四点五六` to `1234.5%` (fixed 2026-08-30); the Rust-side spec window is still hardcoded at 8, unwidened — see `wasm-core/CLAUDE.md`. **This drift bug and `parseChineseNumber`'s do NOT implicate `NumberProcessor`'s range-family converters** (`convertTenThousandRange` etc.) — don't cite them as range-converter evidence again (2026-09-09, candidate #3 grilling: exactly that citation was wrong). Also confirmed — **`getDebugInfo()`-shaped scaffolding that calls only itself/its own tests, never production, keeps getting built and then never wired in — grep the WHOLE `src/` tree for a method's callers before trusting a local "looks used" read.** Confirmed 3x: `PunctuationProcessor`/`QuoteProcessor` + `NumberProcessor.getDebugInfo()`/`.testConversion()` (2026-09-08, ~185 dead lines), `logger.ts`'s `createScopedLogger()` (2026-09-09, predated `warnIfSlow` bolted onto it 2 days prior without anyone checking the function itself was called). `SemanticPatternProcessor`/`SemanticArrayBuilder`'s own `getDebugInfo()`s not yet audited. **Inverse case** — don't over-apply this: `NumberProcessor`'s `options.debugLevel`/`log` threading looks like the same bloat but is wired live to `TranslationEngine.js`'s `this.debugLevel` (call sites `:6286`, `:6757`), same shape as `DictionaryManager.js:151`/`SemanticPatternProcessor.js:127` — check those call sites before collapsing it into a direct `logger.debug()` call.

## 4. Position arithmetic in `postProcess` has four independent traps

- **`token.start` is a byte offset, not a char offset.** Chinese chars are 3 bytes, so it runs ~3× too large for char arithmetic. Use cumulative `tokenCharPositions[i] = sum of tokens[0..i-1].value.length`.
- **The `tokenCharPositions` loop must read `originalValue ?? value`.** Phrase processing sets `tokens[K].originalValue = tokens[K].value` (`"部"`) then mutates `.value` to the full word (`"部分"`). Reading `.value` double-counts and shifts every subsequent `originalStart` by the consumed-token count.
- **Whitespace regexes must preserve `\n`.** Any `replace()` on `cleanedFinalResult`, the `wordSegments` rebuild, or `applyFinalCleanup` uses `[ \t]+` or `[^\S\r\n]+`, never bare `\s+` — `\s` matches `\n`/`\r` and silently drops paragraph breaks next to quotes and punctuation. **Confirmed twice**; the second was `cleanupFormatting`'s own chunking branch (the default path), whose remove-spaces-before-punctuation rule ate the break whenever the next line started with punctuation — `"Dòng một\n。"` came back as `"Dòng một。"`. Fixed 2026-08-31 with `[^\S\r\n]*(\r?\n|)[^\S\r\n]*`, an alternation with an empty branch rather than `?` so the replacement never interpolates `"undefined"`; covered by `TranslationEngine.regression.test.js`. That test pins one call site, not the class — a new whitespace regex elsewhere is still on you.
- **Any post-assembly text mutation that changes length after click-to-highlight positions are recorded desyncs them.** `translateDirectly` records `assembledPositions` from `wasmTextAssembler.assembleWithSpacing()`'s output, then runs `cleanupFormatting()` on that same string — a `cleanupFormatting` regex that inserts/removes a char (e.g. the period-space rule, bitten by `NumberProcessor`'s `"99.9%"` decimal output, fixed 2026-08-29) shifts every position after the insertion point with no error, just silently-wrong highlighting. Any new post-`assembleWithSpacing` transform must run before the position loop, or be proven length-preserving.

## Token and phase semantics

- **`isGrouped` discriminates phrase followers from pattern-consumed tokens.** Both set `groupLeader`. Phrase follower: `isGrouped = true`, `translationSource = 'phrases_consumed'`. Pattern-consumed: `isGrouped` unset, `translationSource = '*_consumed'`. Filtering by `groupLeader` alone conflates them — `getTextFromTokens` and `getSemanticTokens` use `isGrouped && groupLeader !== null` to exclude only phrase followers. Pattern-consumed tokens must stay in `getTextFromTokens` output so text aligns with tokenizer-cached `.start` positions; stripping them shifts phrase lookup offsets for every later token.
- **Every phase must set `groupLeader = startIndex` on consumed tokens at the mark site.** `=== undefined` triggers char-fallback exactly like `null` does, silently corrupting every multi-token match from that phase. `applyMatchToTokens` (Phase 2/4), `applyHierarchicalResults` (Phase 1), and `NumberProcessor.applyConversionResult` (Phase 3 JS) all set it. **`copyWasmTokens` does not copy `groupLeader`** — WASM-path phases need a post-`copyWasmTokens` sweep.
- **Phase 1 output has no `isGrouped`/`groupedWith`.** `applyHierarchicalResults` marks only `translationSource`, `translated`, `groupLeader`. Detect a Phase 1 leader via `translated !== null && translationSource && !translationSource.endsWith('_consumed')`, never via `isGrouped` or `groupedWith.length` — always `false`/`0` there.
- **Phase 2 proper noun lookahead:** `applyDictionaryTranslation` defers a match at position i if any j ∈ [i+1, i+tokenSpan) has a **strictly longer** match — stops "日元" (2 chars at i=1) consuming the 元 that "元始圣人" (4 chars at i=2) needs. Same-length matches at a later position do not defer; earlier start wins (孔宣 beats 宣兄). Applies to shared-index and fallback paths alike.
- **`find_best_pattern_match` / `findBestPatternMatch` tie-break order:** longer match wins, then fewer variables (more literal chars = more specific), then higher priority, then **whichever candidate is iterated first** — `is_better` requires a strict improvement, so a full tie silently resolves by position. Without rule 2, a 2-variable `X的Y上` silently beats a 1-variable `X的手腕上` at equal length. Do not reorder, and any change to how the candidate set is built (filtering, indexing, chaining slices) must emit candidates in their original slice order or it changes output — `VariableLiteralIndex::collect_candidates` sorts indices ascending for exactly this reason.
- **`checkSemanticArrayCorruption` toasts at most once per translation** via a translation-scoped `let corruptionToastShown = false`; `isCorrupted` is sticky across all 5 phase checks. Any new site that toasts on `isCorrupted` must reuse the flag.
- **`allowedVariableTypes` is enforced in Rust by plain string equality** (`matcher.rs::is_variable_type_allowed`) — no Rust list of `SemanticType` values exists, so adding, removing, or renaming one in `src/constants/SemanticTypes.ts` never requires a Rust change. One type is special-cased there: `number` fills only the `#` variable (see `wasm-core/CLAUDE.md`). Semantic token types: `chinese_char`, `chinese_word`, `latin_word`, `number`. Fiction dicts (`properNouns-f_*`) contain all `SemanticType` values — `metadata.semanticType` is authoritative and the heuristic fires only when it is absent.
- **Never fake per-call isolation by swapping a `this.*` field.** `this.<field> = perCallValue` around an `await` does not isolate calls dispatched via `.map()`/`Promise.all` — async functions run synchronously to their first `await`, so `.map()` executes every call's synchronous prefix, including the swap, before any does real async work. This was the confirmed root cause of the deleted `isolatedSemanticBuilder` mechanism (2026-08-18): every call past the first captured and restored the wrong value. Parallel chunks now write straight to the shared `this.semanticArrayBuilder`. If per-call isolation is genuinely needed, pass the value as a parameter or closure.

`SemanticArrayMetadata` in `SemanticArrayBuilder.ts` tags each field by who actually reads it (architecture review 2026-07-30): `tokenIndex` is consumed by both highlighting paths; `originalStart`/`originalEnd` are char-only-exclusive; `phase`/`dictionary` are provenance-only with zero readers today. `buildSegmentsFromPositions` fires only when **all** `metadata[].originalStart >= 0`, so in practice only for single-chunk (short) texts — test short and long texts separately when changing anything upstream of it.

## Punctuation, quotes, and chunk boundaries

- **`cleanupFormatting()` cannot move to WASM and has two branches.** It always runs 27-char dictionary-lookup punctuation translation first (`this.dictionaryManager.translate()` — the blocking constraint), then branches: `options.useChunking !== false` gives a simple spacing fix and early return; the else branch also applies space-after-punctuation and colon-quote handling. It is the single authoritative post-assembly cleanup in `postProcess()` — do not duplicate the logic elsewhere.
- **`translate()` is prefix-match, not exact lookup.** A multi-char key like `'……'` with no exact dict entry matches the 1-char prefix `'…'` and replaces 2 chars with a 1-char translation, silently dropping one. Only add multi-char keys to the 27-char list if they exist as literal punctuation-dict entries.
- **Guard partial matches in `processCharacterOnlyTokens`.** `findLongestMatchAtPosition` on a multi-char punctuation token returns a shorter match than the token's value; check `match.word.length >= token.value.length` before `applyMatchToTokens`, or `token.translated` takes the sub-translation and the remaining chars are lost.
- **Spacing/cleanup regexes near Chinese/digit/punctuation boundaries must allowlist, never denylist — a denylist silently admits every new punctuation mark.** Three confirmed instances: (1) the space-after-Chinese-char rule — the WASM tokenizer types some chars (`…`, `》`) as `unknown`; add a space only when the next token is `chinese_char`, `latin_word`, `TokenType.NUMBER`, or opening-element punctuation, never via `!== 'punctuation' && !== 'whitespace'`. (2) `applyFinalCleanup`'s Vietnamese-text-vs-digit spacing (`TranslationEngine.js`) used an exclusion class (`,.-+%()/~`) that missed `!?:;`/closing quotes, so a converted number got spaced from following punctuation (`"2,700!"` → `"2,700 !"`, fixed 2026-08-29 by matching `\p{L}` letters instead of excluding punctuation). (3) `cleanupFormatting`'s space-after-punctuation rule matched literal `.` with no digit exclusion, splitting `NumberProcessor`'s decimal output (`"99.9%"` → `"99. 9%"`) — fixed by excluding a following `\d` from the lookahead. Audit any new post-processing regex touching `.` for this now that decimals exist in translated output. (4) `TranslationEngine.js`'s char-only capitalize-after-punctuation regex used `\P{L}*` meaning "skip quotes/spaces," but `\P{L}` also matches digits — a decimal like `1.75 mét` got its following word wrongly capitalized. Fixed 2026-08-30 by narrowing to `[^\p{L}\d]*`. (5) The `\d`-lookahead fix to (3) over-corrected: checking only the following char also suppressed the space when a real sentence ends and the next one starts with a digit (`...rồi.5 người` stayed unspaced). Fixed 2026-08-30 by requiring digits on BOTH sides before treating it as a decimal point.
- **`「` (U+300C) is not an opening quote** — `QuoteProcessor.isOpeningQuote('「')` returns false, so `fixAngleQuotePositioning` skips it. That function fires for `《`, `〈`, and curly quotes, and uses `chunk.translatedPunctuation || fallback` so dict mappings (`《→«`, `〈→<`) survive. Colon context in a skipped chunk's `startedBy` is not propagated to the content chunk here; `applySmartCapitalization`'s fallback block (checking `chunks[i-1].content.trim() === ""`) handles that instead.
- **Quote-adjacency rules must scan for a closing+opening quote PAIR, not just the immediate first/last char — same gap hit spacing and capitalization.** `PunctuationProcessor.processSequence` needs `!endsWithOpeningQuote` in `needsTrailingSpace` (WASM combines consecutive punctuation like `”《`/`！”“` into one field); its space-between-quotes branch must gate on any non-space prefix before the trailing opening-quote run, not `CLOSING_PUNCT.includes(result[0])` — that missed sentence-ender+quote sequences (`！”“`, three back-to-back dialogue lines). `TranslationEngine.js`'s char-only capitalize-after-punctuation regex had the mirror bug: required `\s+` immediately after `.!?`, missing `!” “x` where a closing quote sits before the space — fixed to `\P{L}*\s\P{L}*`. Fixed 2026-08-29.
- **Separate empty-content chunks come from leading punctuation, not mid-text punctuation.** The JS chunker's char-loop flushes only when a content char follows accumulated punctuation, or at end of input — mid-text punctuation merges onto the still-open preceding chunk. `chunkText('道：「说')` yields `[{content:"道", punctuation:"：「", startedBy:"start"}, {content:"说", punctuation:"", startedBy:"：「"}]`. Leading punctuation (`《标题》内容`) is what produces `{content:"", punctuation:"《", startedBy:"start"}`. Verified against `TextChunker.chunkText()` with WASM mocked out; an earlier worked example here was wrong.

## Dictionaries

- **`*.trie.json` files are the JS Map-based trie cache**, written by `PrecomputedTrieCache.js` — nothing WASM-related. Do not delete them; they speed up cold starts.
- **Trie-node metadata is not uniform across load paths.** Two paths remain (unified 2026-09-09: `lazyLoadDictionary` now shares `buildTrieFromDictionary` with the main load loop's cache-miss fallback, both producing `priority`/`allowAsPatternVariable`/`semanticType`/`allowedVariableTypes`): `buildTrieFromDictionary` (main load loop's fallback, `lazyLoadDictionary`) vs `DictionaryTrieLoader`'s cache-hit build (raw JSON `target` only, no derived metadata). Do not assume completeness on the cache-hit path.
