# src/utils — Gotchas

Five properties generate almost every trap in this directory. Read the rule, then the instances under it.

📖 WASM wrapper lifecycle (retire-on-panic, cascade registry, `FinalizationRegistry`) lives in [`wasm/CLAUDE.md`](wasm/CLAUDE.md) — scoped there since it's entirely about `src/utils/wasm/*.js`.

## 1. These APIs do not validate their arguments — a wrong one degrades silently

No throw, no warning, no error. The wrong value produces plausible-looking output with a piece missing, which is why these keep recurring. Check the signature at the call site.

## 2. Code that looks redundant here is load-bearing — each of these was already removed once, and broke something

Treat this list as the answer to "why is this checked twice?" The second check is not the same check. Each entry is a claim about live code: confirm it still has a production caller before honoring it — two entries here defended code that never ran (the Phase 2/4 conflict inversion and `buildTypeFilter`, both deleted 2026-09-26).

- **`resolveGlobalConflicts` (Phase 4) lets phrases beat patterns at equal length**, because Phase 1 pattern tokens are already consumed by then. Its Phase 2 twin with the inverse order, `resolveMatchConflicts`, was called only from the dead `createPhraseGroups` and was deleted 2026-09-26 along with its WASM export (`resolveMatchConflictsCore`) — the "architectural inversion" this bullet used to defend had not run in production; see `docs/guides/deleted-symbols.md`. **In practice the Phase 4 tie-break never fires against a real Phase 1 winner**: both `resolveGlobalConflicts` call sites (`processRemainingPhrasesSequential`/`processRemainingPhrasesParallel` in `TranslationEngine.js`) skip any phrase candidate overlapping an already-`translated`/`translationSource`-set token before conflict resolution runs, and only `type: 'phrase'` entries are ever pushed into that pool. So a phrase-dictionary entry **cannot** override an already-winning pattern — the only lever is a competing **pattern** entry, which races the original inside Phase 1's `find_best_pattern_match` and wins ties via fewer variables (verified 2026-08-29; see `dictionary/CLAUDE.md`'s Pattern Variable Contract for the 0-variable-pattern mechanism this enables).
- **`applyHierarchicalResults` has no overlap check** — `select_optimal_results` in `wasm-core/src/pattern_processor/two_phase.rs` already guarantees non-overlapping results. A JS-side dedupe would mask WASM selection bugs instead of surfacing them.
- **`applyMatchToTokens`'s orphan-release loop** — when Phase 2+ overwrites a Phase 1 leader, it scans forward from `startIndex + tokenSpan` and resets orphaned `*_consumed` followers to unprocessed. Without it, Phase 2's skip guard and `postProcess` silently drop those tokens, violating the never-omit-content contract.
- **`postProcess`'s `else if (token.translationSource)` orphan safety net** — recovers consumed Chinese tokens whose `groupLeader === null` (released by orphan-release) or whose leader has `translated === null`, via char dict fallback. Do not collapse to `continue`.
- **`WordSegmentMatcher.matchWordSegments` pass 2 reuses pass 1's `foundWords[i].position`** — given pass 1's global pairwise non-overlap guarantee and pass 2's strict left-to-right walk, an independent `indexOf` re-search can mathematically never diverge. It is not a safety net; it cannot catch anything.
- **`SegmentPrecomputer.ts`'s two scan loops are not unification candidates** — `precomputeOriginalSegments` (Chinese panel) does raw exact `startsWith` with grapheme-cluster indexing; the deleted `precomputeSegments` (Vietnamese panel) did punctuation-skip and case/whitespace-normalized matching. Genuinely different matching problems. See ADR-036.
- **`cleanupFormatting`'s `^` capitalization needs `!options.isParallelChunk`** — each parallel chunk runs with `useChunking: false`, so without the guard the rule capitalizes every chunk's first letter independently and overrides `applySmartCapitalization` context.
- **`createOptimalPhraseGroups` (Phase 4) checks only `enableTwoPhasePatterns`, not `patterns?.length`** — phrase processing is pure JS and runs whether or not structural patterns are loaded. Do not re-add a `patterns?.length > 0` guard.
- **Do not wire `SemanticArrayMetadata.translatedStart`/`.translatedEnd` validity into `checkSemanticArrayCorruption`.** Both initialize to `-1` in `addUnit` and stay `-1` until `postProcess`'s position-tracking loop runs, _after_ all 5 phases. The corruption check fires _during_ each phase, so it would see `-1` on every entry of every translation — 100% false positive, not an edge case. Shipped and reverted same-day, 2026-08-16.
- **Deleting code's only caller or writer orphans what it called and what it wrote — after every deletion, grep each callee and each field the deleted code assigned.** `5cc7b0d` removed the sole assigner of engine segments' `translatedStart`, so `_logUnpositionedSegments` (`=== -1`) warned on every progressive translation until 2026-10-05. Deleting `translateWithChunking` (same day) left `ChunkPostProcessor.reconstructTextWithSegments` with no caller, and `chunk.semanticIndex`, its only reader, with no writer. The inverse hides in JS: a method deleted from a TS class leaves its JS callers calling nothing, so after a deletion grep the name in `*.js`/`*.jsx` and in `.d.ts` option types. A `typeof x.m === 'function'` guard hides the dead call for good (`semanticArrayBuilder.clearCache()`); an unguarded one throws only when its branch runs, and a failure-only branch needs a test that drives it (`getCorruptionTelemetry()` threw a `TypeError` at every phase checkpoint from 2026-05-16 to 2026-10-09).
- **Two independently-implemented checks over the same classification must be kept in sync by construction, not discipline — hand-copied DATA (a predicate, a regex alternation, a char array) drifts from its source of truth. Duplicated LOGIC using that data at different call-time granularity is a different animal, check before merging (see this section's own theme).** Confirmed drift instances: `validateConsumedTokenContract`'s `_consumed` check and `getSourcePriority`'s once had to match by discipline; now one owner (section 5, "Token source strings", 2026-10-04). `NumberProcessor.parseChineseNumber`'s internal hundreds/thousands regex was narrower than the top-level match regex it was supposed to mirror (see `wasm-core/CLAUDE.md`; fixed by matching Rust's `(.*)` catch-all shape, 2026-08-29). `applySmartCapitalization`'s three hand-copied punctuation arrays drifted from `capitalizationRules` (fixed by deriving them from it, 2026-08-29). `capitalizeFirstLetter`'s leading-digit skip (chunk-based path) drifted from `translateWithCharactersOnly`'s sibling regex — missing the `/\d/.test(pre) ? m : ...` guard that keeps "500 năm" lowercase, wrongly producing "500 Năm" (fixed 2026-08-31). Pattern-variable classification (`PatternTemplateEngine.isVariableChar`) was independently reimplemented via raw `[A-Z]`/`[XYZ]` regex in `PersistTimeValidator.ts`/`DictionaryEntryValidator.ts`, missing that a capital letter fused to a real word (e.g. the Y in Vietnamese "Yến") isn't a variable — unified into `PatternEntryRules.ts` 2026-09-07. `NumberProcessor.findLongestNumberMatch`'s hand-counted token window undercounted the `percentage` pattern's max decimal span by 1, silently truncating `百分之一千二百三十四点五六` to `1234.5%` (fixed 2026-08-30); the Rust-side spec window was widened to 21 the next day (2026-08-31, see `wasm-core/CLAUDE.md`) and the whole family now runs through `test-fixtures/number-parity.json`. **This drift bug and `parseChineseNumber`'s do NOT implicate `NumberProcessor`'s range-family converters** (`convertTenThousandRange` etc.) — don't cite them as range-converter evidence again (2026-09-09, candidate #3 grilling: exactly that citation was wrong). Also confirmed — **`getDebugInfo()`-shaped scaffolding that calls only itself/its own tests, never production, keeps getting built and then never wired in — grep the WHOLE `src/` tree for a method's callers before trusting a local "looks used" read.** A bare-name scan also misses a dead method whose name a live one shares (`TranslationEngine.clearCache` vs `DictionaryManager.clearCache`) — grep call shapes (`engine.X(`, `this.X(`); follow the chain transitively, across the JS→WASM→Rust seam too (`resolveMatchConflicts` → `resolveMatchConflictsCore`); and `window.translationEngine` exposes every engine method to devtools, so decide deliberately whether a zero-caller method is a console tool — and grep `docs/guides/` too, since `development.md` names `getGlobalStats`/`getMemoryUsage` as console reads (a `src`-only sweep called them caller-less, 2026-10-09; 2026-09-26 sweep, ~1,550 lines). Confirmed 3x: `PunctuationProcessor`/`QuoteProcessor` + `NumberProcessor.getDebugInfo()`/`.testConversion()` (2026-09-08, ~185 dead lines), `logger.ts`'s `createScopedLogger()` (2026-09-09, predated `warnIfSlow` bolted onto it 2 days prior without anyone checking the function itself was called). `SemanticArrayBuilder`'s own `getDebugInfo()` was audited and deleted 2026-10-09 (round 22); `SemanticPatternProcessor.getDebugInfo()` is not yet audited. `NumberProcessor`'s and `SemanticPatternProcessor`'s `options.debugLevel`/`log` threading was dead too (nothing passed a level ≥ their thresholds) and was deleted 2026-10-04 with the engine's.

Changing the algorithm in one and not the others produces divergence that no test catches at the seam.

**WASM is the live default (`bun run tauri:dev`); `SemanticPatternProcessor.js` only runs when WASM fails to init.** A fix verified only against the JS side is not verified against production — confirmed twice: `build_result` (2026-09-10, table below) and `resolve_variable_with_lookahead` (2026-09-13, table below) each had the identical bug independently in both implementations, and fixing only JS left the WASM-path production bug live until traced separately. ## 4. Position arithmetic in `postProcess` has four independent traps

- **`token.start` is a UTF-16 index into the NFC-normalized text, never a byte offset.** `TextTokenizer.tokenize` normalizes first, so for text that is not already NFC the index does not point into the caller's string. Chunk `startIndex` is UTF-16 too. For arithmetic against JS strings use cumulative `tokenCharPositions[i] = sum of tokens[0..i-1].value.length`.
- **The `tokenCharPositions` loop must read `originalValue ?? value`.** Phrase processing sets `tokens[K].originalValue = tokens[K].value` (`"部"`) then mutates `.value` to the full word (`"部分"`). Reading `.value` double-counts and shifts every subsequent `originalStart` by the consumed-token count.
- **Whitespace regexes must preserve `\n`.** Any `replace()` on `cleanedFinalResult`, the `wordSegments` rebuild, or `normalizeLineWhitespace` (`FormattingPasses.ts`) uses `[ \t]+` or `[^\S\r\n]+`, never bare `\s+` — `\s` matches `\n`/`\r` and silently drops paragraph breaks next to quotes and punctuation. **Confirmed twice**; the second was `cleanupFormatting`'s own chunking branch (the default path), whose remove-spaces-before-punctuation rule ate the break whenever the next line started with punctuation — `"Dòng một\n。"` came back as `"Dòng một。"`. Fixed 2026-08-31 with `[^\S\r\n]*(\r?\n|)[^\S\r\n]*`, an alternation with an empty branch rather than `?` so the replacement never interpolates `"undefined"`; covered by `TranslationEngine.regression.test.js`. That test pins one call site, not the class — a new whitespace regex elsewhere is still on you.
- **Any post-assembly text mutation that changes length after click-to-highlight positions are recorded desyncs them.** `translateDirectly` records `assembledPositions` from `assembleWithSpacing()`'s output, then runs `cleanupFormatting()` on that same string — a `cleanupFormatting` regex that inserts/removes a char (e.g. the period-space rule, bitten by `NumberProcessor`'s `"99.9%"` decimal output, fixed 2026-08-29) shifts every position after the insertion point with no error, just silently-wrong highlighting. Any new post-`assembleWithSpacing` transform must run before the position loop, or be proven length-preserving.

## Token and phase semantics

- **`isGrouped` discriminates phrase followers from pattern-consumed tokens.** Both set `groupLeader`. Phrase follower: `isGrouped = true`, `translationSource = 'phrases_consumed'`. Pattern-consumed: `isGrouped` unset, `translationSource = '*_consumed'`. Filtering by `groupLeader` alone conflates them — `getTextFromTokens` and `getSemanticTokens` use `isGrouped && groupLeader !== null` to exclude only phrase followers. Pattern-consumed tokens must stay in `getTextFromTokens` output so text aligns with tokenizer-cached `.start` positions; stripping them shifts phrase lookup offsets for every later token.
- **Every phase must set `groupLeader = startIndex` on consumed tokens at the mark site.** `=== undefined` triggers char-fallback exactly like `null` does, silently corrupting every multi-token match from that phase. `applyMatchToTokens` (Phase 2/4), `applyHierarchicalResults` (Phase 1), and `NumberProcessor.applyConversionResult` (Phase 3 JS) all set it. **`copyWasmTokens` does not copy `groupLeader`** — WASM-path phases need a post-`copyWasmTokens` sweep.
- **Phase 1 output has no `isGrouped`/`groupedWith`.** `applyHierarchicalResults` marks only `translationSource`, `translated`, `groupLeader`. Detect a Phase 1 leader via `translated !== null && translationSource && !translationSource.endsWith('_consumed')`, never via `isGrouped` or `groupedWith.length` — always `false`/`0` there.
- **Phase 2 proper noun lookahead:** `applyDictionaryTranslation` defers a match at position i if any j ∈ [i+1, i+tokenSpan) has a **strictly longer** match — stops "日元" (2 chars at i=1) consuming the 元 that "元始圣人" (4 chars at i=2) needs. Same-length matches at a later position do not defer; earlier start wins (孔宣 beats 宣兄). Applies to shared-index and fallback paths alike.
- **`find_best_pattern_match` / `findBestPatternMatch` tie-break order:** longer match wins, then fewer variables (more literal chars = more specific), then higher priority, then **whichever candidate is iterated first** — `is_better` requires a strict improvement, so a full tie silently resolves by position. Without rule 2, a 2-variable `X的Y上` silently beats a 1-variable `X的手腕上` at equal length. Do not reorder, and any change to how the candidate set is built (filtering, indexing, chaining slices) must emit candidates in their original slice order or it changes output — `VariableLiteralIndex::collect_candidates` sorts indices ascending for exactly this reason.
- **`checkSemanticArrayCorruption` toasts at most once per translation** via a translation-scoped `let corruptionToastShown = false`; `isCorrupted` (the builder's public getter, sticky until `reset()`) stays true across all 5 phase checks and the final one after `postProcess`, which reuses the same flag. Any new site that toasts on `isCorrupted` must reuse the flag. The builder has no telemetry method: the checkpoints called a deleted `getCorruptionTelemetry()` and threw a `TypeError` instead of toasting, from 2026-05-16 until 2026-10-09 (`TranslationEngine.corruption.test.js`).
- **`allowedVariableTypes` is enforced in Rust by plain string equality** (`matcher.rs::is_variable_type_allowed`) — no Rust list of `SemanticType` values exists, so adding, removing, or renaming one in `src/constants/SemanticTypes.ts` never requires a Rust change. One type is special-cased there: `number` fills only the `#` variable (see `wasm-core/CLAUDE.md`). Semantic token types: `chinese_char`, `chinese_word`, `latin_word`, `number`. Fiction dicts (`properNouns-f_*`) contain all `SemanticType` values — `metadata.semanticType` is authoritative and the heuristic fires only when it is absent.
- **Never fake per-call isolation by swapping a `this.*` field.** `this.<field> = perCallValue` around an `await` does not isolate calls dispatched via `.map()`/`Promise.all` — async functions run synchronously to their first `await`, so `.map()` executes every call's synchronous prefix, including the swap, before any does real async work. This was the confirmed root cause of the deleted `isolatedSemanticBuilder` mechanism (2026-08-18): every call past the first captured and restored the wrong value. Parallel chunks now write straight to the shared `this.semanticArrayBuilder`. If per-call isolation is genuinely needed, pass the value as a parameter or closure.

`SemanticArrayMetadata` in `SemanticArrayBuilder.ts` tags each field by who actually reads it (architecture review 2026-07-30): `tokenIndex` is consumed by both highlighting paths; `originalStart`/`originalEnd` are written by Full Translation's `postProcess` only (character-only never sets them, so its original panel always runs the scan) and read by `precomputeOriginalSegments`; `phase`/`dictionary` are provenance-only with zero readers today. `buildSegmentsFromPositions` fires only when **all** `metadata[].originalStart >= 0`, so in practice only for single-chunk Full Translation texts, i.e. no internal punctuation (a chunk boundary): in a later chunk `postProcess` calls `setPositionByMatch` with a chunk-local `tokenIndex` while `addUnit` stored the global one, so no unit matches and `originalStart` stays `-1`. Measured 2026-10-09 (ADR-036 addendum). Test short and long texts separately when changing anything upstream of it.

## Punctuation, quotes, and chunk boundaries

- **The formatting passes live in `src/utils/text/FormattingPasses.ts`, not on `TranslationEngine`** (moved 2026-10-03): `cleanupFormatting`, `applySmartCapitalization`, `capitalizeFirstLetter`, `applyCharOnlySupplements` and the per-mode finishing entry points (`finishFullText`, `cleanFullText`, `finishCharOnlyText`; CONTEXT.md "TextFinishing") are pure functions. The engine passes the punctuation lookup (`engine.lookupPunctuation`) and `this.properNounTranslations`; the engine owns only the call ORDER, except the Full Translation tail (punctuation, capitalization, reconstruct, `finishFullText`, segment match, builder capitalization), whose order lives in `text/FullTextAssembly.ts` with its twin `CharOnlyAssembly.ts` (2026-10-10, round 24). Test them with plain inputs (no engine boot). The character-only path's `applyCharOnlySupplements` is a third capitalization rule set kept as-is beside the other two — reconcile them there, not by editing the engine.
- **`cleanupFormatting()` cannot move to WASM and has two branches.** It always runs 27-char dictionary-lookup punctuation translation first (the injected `translatePunct` lookup — the blocking constraint), then branches: `options.useChunking !== false` gives a simple spacing fix and early return; the else branch also applies space-after-punctuation and colon-quote handling. It is the single authoritative post-assembly cleanup in `postProcess()` — do not duplicate the logic elsewhere.
- **`translatePunctuation` runs twice per chunk, and the dictionary must apply only once** (2026-10-10, round 24): the batch loop translates each batch, then `assembleFullText` translates every chunk again for cross-chunk comma spacing. `chunk.punctuationTranslated` (set in `translatePunctuationNormally`) makes the second run skip the dictionary. Without it the second run re-applied every entry to its own output: `……→…` gave `……` in the batch preview and `…` in the final text, and a chain like `「→“` with `“→"` ended as `"`. The scan is one pass, longest key first, so entries do not chain. A caller that builds chunks without `TextChunker` and sets `translatedPunctuation` itself still gets it translated in place on the first run.
- **`translate()` is prefix-match, not exact lookup.** A multi-char key like `'……'` with no exact dict entry matches the 1-char prefix `'…'` and replaces 2 chars with a 1-char translation, silently dropping one. Only add multi-char keys to the 27-char list if they exist as literal punctuation-dict entries.
- **Phase 5 (`processRemainingTokens`) is a point lookup, `dictionary.get(token.value)`, because every `characters` key is one code point** (ADR-087). It does not read `MatchSource` and has no longest-match loop, so a multi-character `characters` key never matches there; `DictionaryManager.loadDictionaries` warns on one. Do not restore a span search without changing that rule.
- **`processCharacterOnlyTokens` stamps only `chinese_char` tokens.** `applyMatchToTokens` returns at once for any other start token, so a punctuation lookup there stamps nothing. Punctuation is translated afterwards by `cleanupFormatting`'s `lookupPunctuation` (ADR-089). Do not restore a punctuation matcher in that pass without first making `applyMatchToTokens` accept a punctuation start token.
- **The character-only pass writes nothing to `this.*`** (2026-10-07, architecture review round 15, candidate #2). `processCharacterOnlyTokens` passes `recordMatches: false` to `applyMatchToTokens`, which then skips the shared `semanticArrayBuilder.addUnit`; `translateWithCharactersOnly` hands the stamped tokens to `assembleCharOnlyResult` (`text/CharOnlyAssembly.ts`), which adds the units to a private builder. Before this, every character match also landed in the shared builder (labelled `'phrases'`), so a `translateText` that started during the pass's `await openMatchSource` could receive them. The pass no longer awaits anything (a point lookup, ADR-087 addendum 2026-10-10): it runs start to finish without yielding. Pinned by the `character-only pass leaves the engine state of Full Translation alone` tests in `TextFinishing.test.ts`. The remaining Translator-vs-Translator and Translator-vs-Reader `reset()` overlaps are the accepted gap in `src/utils/reader/CLAUDE.md`, not this.
- **Spacing/cleanup regexes near Chinese/digit/punctuation boundaries must allowlist, never denylist — a denylist silently admits every new punctuation mark.** Three confirmed instances: (1) the space-after-Chinese-char rule — the WASM tokenizer types some chars (`…`, `》`) as `unknown`; add a space only when the next token is `chinese_char`, `latin_word`, `TokenType.NUMBER`, or opening-element punctuation, never via `!== 'punctuation' && !== 'whitespace'`. (2) `spaceLettersAndDigits`'s Vietnamese-text-vs-digit spacing (`FormattingPasses.ts`; it was `TranslationEngine.applyFinalCleanup` until 2026-10-05) used an exclusion class (`,.-+%()/~`) that missed `!?:;`/closing quotes, so a converted number got spaced from following punctuation (`"2,700!"` → `"2,700 !"`, fixed 2026-08-29 by matching `\p{L}` letters instead of excluding punctuation). (3) `cleanupFormatting`'s space-after-punctuation rule matched literal `.` with no digit exclusion, splitting `NumberProcessor`'s decimal output (`"99.9%"` → `"99. 9%"`) — fixed by excluding a following `\d` from the lookahead. Audit any new post-processing regex touching `.` for this now that decimals exist in translated output. (4) `TranslationEngine.js`'s char-only capitalize-after-punctuation regex used `\P{L}*` meaning "skip quotes/spaces," but `\P{L}` also matches digits — a decimal like `1.75 mét` got its following word wrongly capitalized. Fixed 2026-08-30 by narrowing to `[^\p{L}\d]*`. (5) The `\d`-lookahead fix to (3) over-corrected: checking only the following char also suppressed the space when a real sentence ends and the next one starts with a digit (`...rồi.5 người` stayed unspaced). Fixed 2026-08-30 by requiring digits on BOTH sides before treating it as a decimal point.
- **A character with two roles needs both neighbours checked before a spacing rule treats it as punctuation.** `.` between digits is a decimal point (items 3 and 5 above); `’` between letters is an apostrophe, not a closing quote — the space-after-closing-quote rule in `cleanupFormatting` split `Thori’dal` into `Thori’ dal` (and, being post-assembly, desynced every highlight after it) until 2026-10-01. The same check applies to any new quote or period rule.
- **`「` (U+300C) is not an opening quote** — `QuoteProcessor.isOpeningQuote('「')` returns false, so `fixAngleQuotePositioning` skips it. That function fires for `《`, `〈`, and curly quotes, and uses `chunk.translatedPunctuation || fallback` so dict mappings (`《→«`, `〈→<`) survive. Colon context in a skipped chunk's `startedBy` is not propagated to the content chunk here; `applySmartCapitalization`'s fallback block (checking `chunks[i-1].content.trim() === ""`) handles that instead.
- **Quote-adjacency rules must scan for a closing+opening quote PAIR, not just the immediate first/last char — same gap hit spacing and capitalization.** `PunctuationProcessor.processSequence` needs `!endsWithOpeningQuote` in `needsTrailingSpace` (WASM combines consecutive punctuation like `”《`/`！”“` into one field); its space-between-quotes branch must gate on any non-space prefix before the trailing opening-quote run, not `CLOSING_PUNCT.includes(result[0])` — that missed sentence-ender+quote sequences (`！”“`, three back-to-back dialogue lines). `TranslationEngine.js`'s char-only capitalize-after-punctuation regex had the mirror bug: required `\s+` immediately after `.!?`, missing `!” “x` where a closing quote sits before the space — fixed to `\P{L}*\s\P{L}*`. Fixed 2026-08-29.
- **Separate empty-content chunks come from leading punctuation, not mid-text punctuation.** The JS chunker's char-loop flushes only when a content char follows accumulated punctuation, or at end of input — mid-text punctuation merges onto the still-open preceding chunk. `chunkText('道：「说')` yields `[{content:"道", punctuation:"：「", startedBy:"start"}, {content:"说", punctuation:"", startedBy:"：「"}]`. Leading punctuation (`《标题》内容`) is what produces `{content:"", punctuation:"《", startedBy:"start"}`. Verified against `TextChunker.chunkText()`; an earlier worked example here was wrong.

## Dictionaries

- **There is no persisted trie cache** (deleted 2026-10-05, ADR-075). `DictionaryManager.loadDictionaries` builds every trie from the loaded JSON with `buildTrieFromDictionary` (19–92 ms for all dictionaries together). Old `*.trie.json` files in the dictionaries directory are orphans nothing reads; Rust still excludes the name from dictionary listing and ZIP import.
- **Check any entry-shape assumption against the production dictionaries, not unit-test fixtures.** The bundled `src/dictionaries/*.json` are samples too (`characters`: 340 entries, no 两, against 13,338 in production), so a rule keyed to a dictionary VALUE (`NumberLiangFix` needs 两 → `lưỡng`) can only be checked against the production file. Entries are a bare string (legacy) or `{translation, allowAsPatternVariable, semanticType?, …}`; in `properNouns*.json` 29,647 of 29,974 are objects. A `typeof v === 'string'` filter drops them silently — `ProperNounCapitalizationMap.ts` did until 2026-10-04, with a test pinning the skip. Readable in the default sandbox (2026-10-10); use `dangerouslyDisableSandbox` only after an EPERM.
- **Trie-node metadata is `{allowAsPatternVariable, semanticType}`** — the only two fields trie readers use (`PatternVariableCache`, `VariableTypeClassifier`). Per-dictionary `priority` lives in `DictionaryManager.metadata`; pattern priority is computed by `SemanticPatternProcessor.parsePattern`. Neither reads a trie node, so do not add `priority` or `allowedVariableTypes` back to nodes.
