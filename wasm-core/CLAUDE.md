# wasm-core

## Every gate in the pattern pipeline fails silently

Nothing here returns an error when a pattern doesn't fire — it just doesn't fire. Five separate gates produce that same symptom, so "my pattern does nothing" is a checklist, not a diagnosis:

- **Index lookup uses the first char only.** `get_index_key` (`index.rs`) stores patterns under the **first char** of the first literal (`"传"` for `传奇级X`). Any lookup in `process_phase_a`/`process_phase_b` must use `first_char = token.value.chars().next()`, never the full token value — a compound token (`"传奇"`) returns no patterns at all.
- **Variable span cap.** `DEFAULT_MAX_VARIABLE_SPAN = 6` (`matcher.rs`) caps variable resolution in **Phase A and static dict lookups only**. Phase B overrides it with `max(6, max_phase_a_key_chars)`, computed once per invocation in `two_phase.rs::process_phase_b`. A Phase B pattern failing to absorb a Phase A result usually means that result's token count exceeded the cap. **`#` is the exception: `span_cap(var_name, …)` (`matcher.rs`) gives it `NUMBER_VARIABLE_SPAN = 8`, the longest numeral the JS cache supplies (`NumberVariable.js`'s `MAX_NUMERAL_SPAN`; `NumberVariableSpan.sourceScan.test.js` keeps them equal), because a 7-character numeral like 一千二百三十四 silently never matched under the 6 cap (ADR-097).** The matcher, the Phase A bonus estimator and `VariableLiteralIndex` all read `span_cap`; the 12 patterns that start with `#` sit in the index's separate `by_first_literal_wide` map, looked up in an 8-token window, and routing them into the narrow map drops them silently. Putting them in `always` instead is correct but doubled the median call time (ADR-097).
- **A result's `start_index`/`end_index` are ORIGINAL token indices; `semantic_tokens` positions are not.** `matcher.rs` sets them from `SemanticToken::original_index` (the caller's token array, whitespace and punctuation included) because the JS side indexes with them, while `semantic_tokens` holds only the semantic tokens, so a position there runs behind the index by the non-semantic tokens before it. Slicing or walking `semantic_tokens` with a result's index panics (past the end) or reads the wrong tokens (`estimate_leading_bonus`, `estimate_trailing_bonus`, `mark_tokens_as_protected` and Phase B's advance all did, ADR-098). Convert with `position_of` (a candidate's start) or `position_after` (the token after its end) first. Overlap bookkeeping that compares result indices only with each other (`used_tokens`, the composition checks) needs no conversion. Test with gapped `original_index` values: a test whose tokens have `original_index == position` cannot see this.
- **Phase B must be strictly longer than what Phase A protected.** `get_max_phase_a_length` (`matcher.rs`) feeds a `current_matched_text.chars().count() <= max_phase_a_length` check that fails with "Phase A match is longer or equal length". This is what enables hierarchical composition: the outer pattern must cover more chars than the inner.
- **`semanticType: "$X"` resolves at match time.** The resolved type (e.g. `"character"`) lands in `PatternProcessingResult.semantic_type`, not the literal `"$X"`. Phase B's enhanced cache type-gates on that resolved value against `allowedVariableTypes` — a wrong type on the Phase A result kills the composite.
- **`#` is the number variable, and numbers fill nothing else.** `parse_pattern` reads `#` as a variable and injects `allowedVariableTypes["#"] = ["number"]`; `matcher.rs::is_variable_type_allowed` (the one type check shared by the matcher and the Phase A bonus) rejects `number`-typed values for every letter variable. The `number` entries exist only when some pattern contains `#`: they come from JS `src/utils/pattern/NumberVariable.js` (1–10 as words, above 10 as `NumberProcessor` digits), added in `TwoPhasePatternProcessor.buildVariableCache` only. **`#o` in a template is the ordinal reading** (`nhất` for 1, `tư` for 4; every other number reads as its cardinal): `NumberVariable.js` puts an `ordinal` on those cache entries, `test_pattern_match` fills the template variable `#o` from it (the cardinal when absent), and `build_result` tries the longer name first, so no parser change. Chinese-side patterns still use `#`. The JS matcher that once mirrored this is deleted (ADR-101).
- **Two competing `allowAsPatternVariable: true` patterns race.** If inner A and outer B both set it, B can win Phase A by being longer, consume the tokens A needed, and then fail Phase B's ≤-length guard. Fix: set `allowAsPatternVariable: false` on the intended _outer_ pattern so only A runs in Phase A.

**WASM failure disables two-phase for the whole session.** `applyPatterns`' catch block sets `this.settings.enableTwoPhasePatterns = false` after 3 failures (`TranslationEngine.js`), and Phase 1 is then skipped with an error toast (ADR-101); there is no JS fallback. A rebuilt WASM binary that seems to have no effect usually means the _old_ binary tripped the counter. Vite HMR on any JS file resets the engine instance and clears the flag; a full WebView reload also works.

## Phase A composite-coverage scoring

`select_non_overlapping_phase_a` scores candidates as own chars plus `compute_composite_bonus()`, where the bonus is the verified literal chars a Phase B pattern would add if this candidate were its variable (trailing after, or leading before), plus — on the trailing side — the longest type-allowed direct cache hit for a variable right after that literal run (`X手中的Y`: 肖姓女子 scores 4+3+4, not 4+3; a variable needing its own Phase A match still counts 0). A shorter candidate wins when it enables a longer composite. If the wrong candidate wins, check whether the loser's semantic type passes the intended wrapping pattern's `allowedVariableTypes` — that is what the bonus gates on. On an exact score tie, check `calculate_priority` (`pattern.rs`): it tie-breaks fewer-variables-wins, matching `find_best_pattern_match`, but was inverted until 2026-08-29 (silently favouring a longer, more-variable pattern over a shorter, more-specific one waiting to compose — `这位X` losing to `X的Y`). `.priority`'s only real consumers are `find_best_pattern_match` and this tie-break.

**A repro here must reproduce production STATE, not just production scale — otherwise it answers a question you did not ask, confidently.** Three confirmed instances: correctness, performance and input shape. (1) 2026-09-13: `compute_composite_bonus` summed a pattern's leading/trailing bonuses independently, letting an unrelated `<literal>X<literal>`-shaped decoy (`在X中`) phantom-contribute from only its trailing side, its required leading literal nowhere nearby; a hand-picked 3-pattern repro showed correct behavior on both inputs, and only loading the real `patterns.json` via `parse_patterns_dict` surfaced the interference. (2) 2026-09-16: a criterion bench using the real dictionary but an EMPTY variable cache and `DEFAULT_MAX_VARIABLE_SPAN` rated a candidate prefilter 2-7x FASTER; in production, where `phase_b_max_var_span = max(6, max_phase_a_key_chars)` is much larger and the cache is populated, the same change measured 2-3x SLOWER and was reverted. (3) 2026-10-11: the pattern-processor benchmark's first harness fed whole 1,500-character windows and panicked on 164 of 248, while the engine's 35,760 real calls were chunks of at most 47 semantic tokens and never did; capture the arrays the engine hands `applyPatterns` and replay those. Load the real dictionary AND a realistic cache/span before trusting any result from this module — and note that proving a filter _sound_ proves nothing about whether it is _worth it_. Cheapest faithful harness: a throwaway `wasm-core/examples/<name>.rs` that runs `parse_patterns_dict` on the real `patterns.json` and `process_tokens` with a hand-built cache, via `cargo run --example <name>` (sandbox off: it reads Application Support); delete it after. Loading two dictionary files in the same harness and diffing outputs is the check before writing any bulk `patterns.json` rewrite.

**The two bonus functions are not mirror images, so testing one proves nothing about the other.** `test_phase_a_composite_bonus_wins_over_larger_own_span` (`tests/two_phase_test.rs`) covers the trailing path end-to-end via `process_tokens`; `estimate_leading_bonus` has its own 5 direct tests in `two_phase.rs`'s inline `mod tests::estimate_leading_bonus`. Trailing scans forward from `var_idx+1` and `break`s at the next variable; leading scans forward through `tokens[..var_idx]` and `.clear()`s on hitting a variable, keeping only the LAST contiguous literal run before `var_idx` (verified: a `[Lit, Var, Lit, Lit, Var]`-shaped pattern correctly discards the run before the earlier variable).

## This crate is a parity mirror, and every divergence truncates silently

Several modules here exist to mirror a JS implementation, not to be called from it. **`number_processor.rs` is spec-only** — `#[wasm_bindgen]` was deliberately removed from the struct and impl, and the file is kept as the spec/test suite for `NumberProcessor.js`. What it converts is pinned in `test-fixtures/number-parity.json`, which `mod tests::parity` runs through `process_tokens` beside the JS runner; its remaining tests call the converters and helpers directly. Do NOT add `#[wasm_bindgen]` back; read `docs/adr/ADR-041-keep-number-processor-rs-as-parity-spec.md` before proposing deletion again, which has happened repeatedly.

**Every parity bug found so far had the same shape: one side's matcher was narrower than the other's, and the narrow side truncated its input instead of failing.** That is why none of them surfaced as errors. Confirmed instances, each worth reading as a pattern rather than a fact:

- `extract_ascending_pair` required `second == first + 1` (consecutive only) while JS's `isAscendingRangePair` requires only `second > first` — so 三八 → "30-80" was unreachable. Widened 2026-09-09, and `convert_teen_age_range`'s separate bug (discarding the actual second digit, always returning an adjacent pair) had to be fixed alongside, since the widened check would otherwise have let a non-adjacent pair reach it for the first time.
- `parse_chinese_number`'s internal `THOUSANDS_RE`/`HUNDREDS_RE` use a bare `(.*)` remainder catch-all. **This is the correct shape — keep it if porting logic here.** JS used to hand-write a second, narrower enumerated regex for the same internal match, missing the bare-`十`-with-no-leading-digit branch, so 三千二百十五 silently truncated to 3200 (the outer thousands regex matched; "十五" vanished in the recursive call on remainder "二百十五"). Fixed by matching this file's catch-all shape rather than unifying two enumerated lists. If this is ever rewritten to an enumerated alternation, re-check whether JS's top-level `CONVERSION_PATTERNS` — which must stay enumerated, since it decides how many characters to consume — has grown branches the internal matcher lacks.
- Decimal-percentage, closed 2026-08-31: the Rust window is now `start_index + 21`, matching JS's `endIndex <= startIndex + 20`. Widening it was not enough on its own — the `percentage` regex also lacked JS's optional `(?:点([一二三四五六七八九零]+))?` decimal group and its bare-`百` alternative, returning `1234%` with no `百分之百` branch at all. `test_converter_decimal_percentage_spans_full_window` asserts the full `百分之一千二百三十四点五六` → `1234.56%` plus its end index. **A window shorter than the input truncates silently, so any change to either side's window belongs in a test that asserts the end index, not just the string.**

**Fixtures, one pattern, and the test must call production.** `conflict-resolution-parity.json` (the Rust twin deleted, ADR-083), `tokenizer-`, `text-assembly-` and `chunker-parity.json` (ADR-079) now feed JS tests alone; `pattern-variable-parity.json` and `build-result-parity.json` still feed both sides. A "parity" test that re-implements the algorithm tests only itself (seen twice, in Rust and in JS; both deleted). Offsets Rust returns to JS are UTF-16 code units (`encode_utf16().count()`), never `chars().count()`; the astral case in `text-assembly-parity.json` pinned it before the Rust assembler was deleted.

**A parity test only holds if something runs it.** `wasm-core`'s `cargo test` was not in CI until 2026-08-25. The drift check that day found `b1dd912`'s 一千零六→1,006 fix correctly mirrored, but two JS regression cases with no Rust equivalent (二零二四年→năm 2024, 百分之两百→200%) and a percentage test that discarded its result (`let _ = ...`) and so was structurally unable to fail. All three fixed same day; it runs in CI now. Re-check for assertion-shaped `let _ =` bindings when adding to any parity test file — a 2026-08-31 sweep found zero, so this is a reading habit, not a scan.

## Apparent status is not real status

Four different signals in this crate have each claimed something was live, wasm-only, hot, or covered, and been wrong. Trace the real call path or the origin commit; never accept the signal alone.

- **`lib.rs`'s `// ✅ ACTIVE SYSTEMS` header lies in both directions.** A `pub mod` absent from it with no retention note here is a strong signal of abandoned work (confirmed twice) — but absence is necessary, not sufficient: `pattern_processor` is live and absent, since only NumberProcessor and DictionaryEngine are named by design. Presence is not sufficient either: a module once listed as active for clickable highlighting had been built and never wired, and the comment was never corrected. Pair every liveness check with a real caller-grep.
- **A `#[cfg(target_arch = "wasm32")]` gate outlives its reason.** Seen once: a gate protecting a `js_sys::Array` return type stayed after the function was rewritten to return a `String` through `serde_json::to_string`. `unicode_properties` was never wasm-only either. Confirmed by `git log -p -- <file>` to the origin commit, then a native `cargo test` with the gates stripped, before ungating for real. Check whether the wasm-only dependency a gate protects is still used.
- **A name that sounds like the hot path usually isn't.** Dictionary-lookup matching is the JS trie (`DictionaryManager.findAllMatches`/`findMatchesAtToken`), not anything in this crate (it has no trie since ADR-073). A native Rust lookup index in `src-tauri` was advertised as the path for text ≥50 chars, but on real books no chunk ever reached it (0 of 35,760 calls) and it was deleted (ADR-108). Trace the call path, on real text, before benchmarking or optimizing anything for "translation speed".
- **"It compiles" depends on what you compiled.** `cargo build --tests` enumerates every call site the compiler can see and is the completeness check when removing or renaming a `pub` item or a `parse_pattern`/`SemanticPattern` positional field — grep under-counts: a bare positional value has no field name to match, a sweep scoped to `wasm-core/src` skips `wasm-core/tests/` (a removed method once left a caller in `two_phase_test.rs`), and `two_phase.rs`, `index.rs` and `mod.rs` each carry inline `#[cfg(test)] mod tests` with `parse_pattern(...)` calls outside `wasm-core/tests/`. `benches/*.rs` is NOT covered by `--tests` and silently bit-rotted (2026-08-20: `pattern_matching.rs` had stale `parse_pattern` and `find_best_pattern_match` calls, broken across an unknown number of prior signature changes). CI now runs `cargo check --benches` on both crates.

**Deleting a module means checking `Cargo.toml` too** — grep for any dependency only that module used (`bincode` once had a single consuming module) and drop it. An unused compiled dependency is the same shallow-surface problem as the dead code.

## Build profile, dev binary, and WASM-only panics

`npm run build-wasm-dev` (`wasm-pack build --dev`) produces debug WASM — `overflow-checks = true`, `debug_assertions = true`, unoptimized. A panic in `tauri:dev` may not reproduce in production (`build-wasm` uses release: `overflow-checks = false`, `opt-level = 3`), so establish whether a WASM panic is debug-only before assuming a logic error. **Benchmarking corollary:** `bun run dev` and `bun run tauri:dev` both run `build-wasm-dev` first and silently overwrite a release binary with a debug one, so timings taken through them are meaningless (measured 7838 ms debug vs 2089 ms release on one input). Profile with `bun run build-wasm && bunx tauri dev`, or `bun run build-wasm` plus a plain `./node_modules/.bin/vite`.

**Dev binary path:** `build-wasm-dev` outputs to `src/wasm/translation_wasm_core_bg.wasm`, which is what the dev server serves. `public/wasm/` is updated only by production builds and can be months stale without breaking dev — check `src/wasm/` when diagnosing a stale-binary bug.

**WASM-side logging:** `#[cfg(target_arch = "wasm32")] { web_sys::console::log_1(&format!("...").into()); }` inside any Rust function — `web-sys` with the `"console"` feature is already a dep. Remove before commit.

**Debug-build panics: five confirmed causes,** four Rust-side and one JS-side. If `cargo test` passes, the bug is WASM-debug-specific and is almost certainly one of these:

1. Shadow-stack exhaustion from deep `opt-level=0` call chains — split the work across separate WASM calls.
2. Heap-allocated fields on a `#[wasm_bindgen]` struct reached via raw `__wbg_ptr` (HashMap, Vec) — move them to `lazy_static!` and pre-initialize in the constructor, outside the `&self` borrow window.
3. A `lazy_static` initialized lazily: the first method call that hits it initializes while the wasm-bindgen `RcRefMut` borrow is live → `alloc/rc.rs hint::assert_unchecked`. Not OOB; intermittent and input-dependent. Pre-initialize **all** lazy_statics in the constructor.
4. `regex::Regex`'s first `.find()`/`.captures()` inside a struct method allocates a per-thread `Pool<Cache>` via `regex-automata 0.4.x` `Pool::get_slow` — same borrow-window class as (3), but panics at `rt/mod.rs:287:25` "attempt to subtract with overflow" in `Drop for Ref`. Run `.find("")` on every `Regex` in the constructor.
5. JS-side FinalizationRegistry stale callback: nulling a wrapper variable without calling `.__destroy_into_raw()` first leaves the GC callback registered; when dlmalloc reuses the freed Rc address, it fires and decrements the new Rc to 0, so the next method call reads count=0 and trips `alloc/rc.rs hint::assert_unchecked` (line shifts by Rust version — 3743 in 1.84, 3753 in 1.96, same check). The fix is in the JS wrapper, not Rust. See `src/utils/wasm/CLAUDE.md`.

Narrow an OOB location with `web_sys::console::log_1` checkpoints at key statements.

## Toolchain posture

**Warnings are errors locally as well as in CI.** `/.cargo/config.toml` sets `[build] rustflags = ["-D", "warnings"]`, matching what CI's `actions-rust-lang/setup-rust-toolchain@v1` exports by default, so there is no class of failure that only appears after a push. Expect the gap to show up as dead-code and unused-binding lints in **test** code, which normal local runs never surface — both failures found before this was aligned were latent for weeks and neither was a real defect. Prefer closing the gap over `#[allow(...)]`: an unconstructed `MatchType::Other` in a since-deleted parity test marked a genuine parity hole (the else-branch of a type ternary, reached by `literal`, `semantic`, `structural_pattern` and `composite` matches). That file was a private re-implementation and is gone, and so is the whole conflict-resolution tier (2026-10-07, ADR-083); `test-fixtures/conflict-resolution-parity.json` still covers the 'other' tier, through the JS function.

**Scope wasm32-specific linker flags in `.cargo/config.toml`'s `[target.wasm32-unknown-unknown]`**, never inline in a `package.json` script. Inline `RUSTFLAGS=` bleeds into host-target build scripts (`cargo install`), and Apple `ld` rejects GNU-only flags like `-z`. The stack-size flag lives in `/.cargo/config.toml`.

**`cargo fmt` has never been run on this crate — don't treat the drift as your regression, and don't mass-reformat.** `rustfmt --check src/*.rs` (2026-08-17) shows drift in every file, and the crate has no rustfmt config to explain it as intentional; no CI gate or hook enforces it. When `rustfmt --check` flags a file you're editing, confirm the specific lines are ones your diff touched before fixing them. A crate-wide pass is pure mechanical churn with zero architectural value, and it buries `git blame`/`git log -p` under a reformat-only commit spanning nearly every line — exactly the archaeology this file's own entries (the stale-liveness discovery, the wasm32-gate trace) depend on. **Ruled out for mechanization 2026-08-31**: the reasoning is the payload, not the rule, and no formatting conflict has actually occurred. Reverse it if merge conflicts or review friction appear — and then the hook is for new drift only, still not a retroactive reformat. To check one file: `rustfmt --check <path>` from inside `wasm-core/`, because `cargo fmt --manifest-path wasm-core/Cargo.toml -- --check <path>` ignores the path and checks the whole crate.

## Test placement

- `tests/two_phase_test.rs` — two-phase + hierarchical composite tests
- `tests/pattern_matching_test.rs` — `find_best_pattern_match` + `PatternMatcher` unit tests
- `tests/pattern_semantic_type_test.rs` — semantic type propagation Phase A → Phase B

**`pub(crate)` functions (e.g. a `*_core` function) are unreachable from `wasm-core/tests/*.rs`** — integration test files see only the crate's public API, so tests against one must live in that source file's own `#[cfg(test)] mod tests` (nest a submodule such as `mod tests::parity` if it needs file-like organization).

**`#[wasm_bindgen]` structs are testable from a native `#[cfg(test)] mod tests`, no `wasm-bindgen-test` needed** — a struct such as `NumberProcessor::new()` constructs and its methods run under plain `cargo test`, because `Result<_, JsValue>` only touches JS when a `JsValue` is actually built. That covers happy-path and assertion tests, and stops working the moment a test drives an error branch calling `JsValue::from_str`. Assert through the `#[wasm_bindgen]` getters rather than private fields, and the test doubles as a JS-boundary check.

## Building a new WASM boundary validator? Check `Option<T>` first

A field that is not an `Option<T>` on a `#[wasm_bindgen]` struct is guaranteed present and correctly typed by serde, so a `typeof` check on it defends against a corruption shape that cannot occur from valid Rust serialization. What serde can't guarantee is a semantically-wrong-but-correctly-typed value — an out-of-range index from a Rust arithmetic bug — and that is the actual recurring bug class here. Check the struct's `Option<T>` usage before choosing a validator shape; `src/utils/wasm/WasmBoundaryValidation.ts`'s `isPatternMatchInBounds` is the index-bounds-only pattern this leads to.
