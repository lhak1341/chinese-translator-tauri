# wasm-core

## Every gate in the pattern pipeline fails silently

Nothing here returns an error when a pattern doesn't fire — it just doesn't fire. Five separate gates produce that same symptom, so "my pattern does nothing" is a checklist, not a diagnosis:

- **Index lookup uses the first char only.** `get_index_key` (`index.rs`) stores patterns under the **first char** of the first literal (`"传"` for `传奇级X`). Any lookup in `process_phase_a`/`process_phase_b` must use `first_char = token.value.chars().next()`, never the full token value — a compound token (`"传奇"`) returns no patterns at all.
- **Variable span cap.** `DEFAULT_MAX_VARIABLE_SPAN = 6` (`matcher.rs`) caps variable resolution in **Phase A and static dict lookups only**. Phase B overrides it with `max(6, max_phase_a_key_chars)`, computed once per invocation in `two_phase.rs::process_phase_b`. A Phase B pattern failing to absorb a Phase A result usually means that result's token count exceeded the cap.
- **Phase B must be strictly longer than what Phase A protected.** `get_max_phase_a_length` (`matcher.rs`) feeds a `current_matched_text.chars().count() <= max_phase_a_length` check that fails with "Phase A match is longer or equal length". This is what enables hierarchical composition: the outer pattern must cover more chars than the inner.
- **`semanticType: "$X"` resolves at match time.** The resolved type (e.g. `"character"`) lands in `PatternProcessingResult.semantic_type`, not the literal `"$X"`. Phase B's enhanced cache type-gates on that resolved value against `allowedVariableTypes` — a wrong type on the Phase A result kills the composite.
- **`#` is the number variable, and numbers fill nothing else.** `parse_pattern` reads `#` as a variable and injects `allowedVariableTypes["#"] = ["number"]`; `matcher.rs::is_variable_type_allowed` (the one type check shared by the matcher and the Phase A bonus) rejects `number`-typed values for every letter variable. The `number` entries exist only when some pattern contains `#`: they come from JS `src/utils/pattern/NumberVariable.js` (1–10 as words, above 10 as `NumberProcessor` digits), added in `TwoPhasePatternProcessor.buildVariableCache` only. The JS fallback matcher has no `#` support, so a `#` pattern simply never matches there.
- **Two competing `allowAsPatternVariable: true` patterns race.** If inner A and outer B both set it, B can win Phase A by being longer, consume the tokens A needed, and then fail Phase B's ≤-length guard. Fix: set `allowAsPatternVariable: false` on the intended _outer_ pattern so only A runs in Phase A.

**WASM failure disables two-phase for the whole session.** `applyPatterns`' catch block sets `this.settings.enableTwoPhasePatterns = false` after 3 failures (`TranslationEngine.js`), and the JS fallback then runs silently. A rebuilt WASM binary that seems to have no effect usually means the _old_ binary tripped the counter. Vite HMR on any JS file resets the engine instance and clears the flag; a full WebView reload also works.

## Phase A composite-coverage scoring

`select_non_overlapping_phase_a` scores candidates as `own_chars + composite_bonus`, where `composite_bonus` is the verified literal chars a Phase B pattern would add if this candidate were its variable (trailing after, or leading before), plus — on the trailing side — the longest type-allowed direct cache hit for a variable right after that literal run (`X手中的Y`: 肖姓女子 scores 4+3+4, not 4+3; a variable needing its own Phase A match still counts 0). A shorter candidate wins when it enables a longer composite. If the wrong candidate wins, check whether the loser's semantic type passes the intended wrapping pattern's `allowedVariableTypes` — that is what the bonus gates on. On an exact score tie, check `calculate_priority` (`pattern.rs`): it tie-breaks fewer-variables-wins, matching `find_best_pattern_match`, but was inverted until 2026-08-29 (silently favouring a longer, more-variable pattern over a shorter, more-specific one waiting to compose — `这位X` losing to `X的Y`). `.priority`'s only real consumers are `find_best_pattern_match` and this tie-break; `trie.rs` has an unrelated same-named field, so don't let a bare `.priority` grep pull it in.

**A repro here must reproduce production STATE, not just production scale — otherwise it answers a question you did not ask, confidently.** Two confirmed instances, one correctness and one performance. (1) 2026-09-13: `compute_composite_bonus` summed a pattern's leading/trailing bonuses independently, letting an unrelated `<literal>X<literal>`-shaped decoy (`在X中`) phantom-contribute from only its trailing side, its required leading literal nowhere nearby; a hand-picked 3-pattern repro showed correct behavior on both inputs, and only loading the real `patterns.json` via `parse_patterns_dict` surfaced the interference. (2) 2026-09-16: a criterion bench using the real dictionary but an EMPTY variable cache and `DEFAULT_MAX_VARIABLE_SPAN` rated a candidate prefilter 2-7x FASTER; in production, where `phase_b_max_var_span = max(6, max_phase_a_key_chars)` is much larger and the cache is populated, the same change measured 2-3x SLOWER and was reverted. Load the real dictionary AND a realistic cache/span before trusting any result from this module — and note that proving a filter _sound_ proves nothing about whether it is _worth it_. Cheapest faithful harness: a throwaway `wasm-core/examples/<name>.rs` that runs `parse_patterns_dict` on the real `patterns.json` and `process_tokens` with a hand-built cache, via `cargo run --example <name>` (sandbox off: it reads Application Support); delete it after. Loading two dictionary files in the same harness and diffing outputs is the check before writing any bulk `patterns.json` rewrite.

**The two bonus functions are not mirror images, so testing one proves nothing about the other.** `test_phase_a_composite_bonus_wins_over_larger_own_span` (`tests/two_phase_test.rs`) covers the trailing path end-to-end via `process_tokens`; `estimate_leading_bonus` has its own 5 direct tests in `two_phase.rs`'s inline `mod tests::estimate_leading_bonus`. Trailing scans forward from `var_idx+1` and `break`s at the next variable; leading scans forward through `tokens[..var_idx]` and `.clear()`s on hitting a variable, keeping only the LAST contiguous literal run before `var_idx` (verified: a `[Lit, Var, Lit, Lit, Var]`-shaped pattern correctly discards the run before the earlier variable).

## This crate is a parity mirror, and every divergence truncates silently

Several modules here exist to mirror a JS implementation, not to be called from it. **`number_processor.rs` is spec-only** — `#[wasm_bindgen]` was deliberately removed from the struct and impl, and the file is kept as the spec/test suite for `NumberProcessor.js` (44 tests as of 2026-09-09; earlier "155"/"37" figures here were stale). Do NOT add `#[wasm_bindgen]` back; read `docs/adr/ADR-041-keep-number-processor-rs-as-parity-spec.md` before proposing deletion again, which has happened repeatedly.

**Every parity bug found so far had the same shape: one side's matcher was narrower than the other's, and the narrow side truncated its input instead of failing.** That is why none of them surfaced as errors. Confirmed instances, each worth reading as a pattern rather than a fact:

- `extract_ascending_pair` required `second == first + 1` (consecutive only) while JS's `isAscendingRangePair` requires only `second > first` — so 三八 → "30-80" was unreachable. Widened 2026-09-09, and `convert_teen_age_range`'s separate bug (discarding the actual second digit, always returning an adjacent pair) had to be fixed alongside, since the widened check would otherwise have let a non-adjacent pair reach it for the first time.
- `parse_chinese_number`'s internal `THOUSANDS_RE`/`HUNDREDS_RE` use a bare `(.*)` remainder catch-all. **This is the correct shape — keep it if porting logic here.** JS used to hand-write a second, narrower enumerated regex for the same internal match, missing the bare-`十`-with-no-leading-digit branch, so 三千二百十五 silently truncated to 3200 (the outer thousands regex matched; "十五" vanished in the recursive call on remainder "二百十五"). Fixed 2026-08-29 by matching this file's catch-all shape rather than unifying two enumerated lists. If this is ever rewritten to an enumerated alternation, re-check whether JS's top-level `CONVERSION_PATTERNS` — which must stay enumerated, since it decides how many characters to consume — has grown branches the internal matcher lacks.
- Decimal-percentage, closed 2026-08-31: the Rust window is now `start_index + 21`, matching JS's `endIndex <= startIndex + 20`. Widening it was not enough on its own — the `percentage` regex also lacked JS's optional `(?:点([一二三四五六七八九零]+))?` decimal group and its bare-`百` alternative, returning `1234%` with no `百分之百` branch at all. `test_converter_decimal_percentage_spans_full_window` asserts the full `百分之一千二百三十四点五六` → `1234.56%` plus its end index. **A window shorter than the input truncates silently, so any change to either side's window belongs in a test that asserts the end index, not just the string.**
- `text_tokenizer.rs`'s punctuation classification is a catch-all, not an enumerated list. `tokenize_text_core`'s final `else` types **any** char that isn't `is_chinese_char`/`is_latin_letter`/`is_digit`/whitespace as `TokenType::Punctuation`, mirroring JS `TextTokenizer.ts`'s `[^\w\s一-鿿]+` group. Do NOT reintroduce a finite `is_punctuation()` list: the version deleted 2026-07-17c was missing 20 of the 41 chars in production `punctuation.json` — including `…` and the corner brackets `「」『』` used constantly in Chinese-fiction dialogue — so those fell through to `unknown` in WASM while JS typed them `punctuation`, and one confirmed production bug (a `TranslationEngine.js` spacing rule needing an allowlist workaround for `'…'`) came from exactly that. A finite list is always one dictionary addition away from reopening the gap; a catch-all cannot drift. `TokenType::Unknown` stays in the enum for wire-format parity but is no longer constructed.
- Consequence of that catch-all: non-ASCII, non-CJK letters (Greek `α`, Cyrillic, accented `é`) land in it rather than `latin_word`, since `is_latin_letter` is ASCII-only. `needs_space()`/`needsSpace()` gained Rule 11 (2026-08-29, corrected 2026-08-30) so a punctuation-typed token whose first char is a Unicode Letter (Lu/Ll/Lt/Lm/Lo) still gets spaced against an adjacent Chinese char. **The Rust side must check `general_category()` via the `unicode_properties` crate, NOT `char::is_alphabetic()`** — the latter also accepts Letter_Number (Roman numeral `Ⅳ`), diverging from JS's `\p{L}`. That was the real Rule 11 bug.
- Token-count parity is a **deliberately unfixed** divergence: JS's `tokenizeJS` groups runs (`"……"` → 1 token), Rust emits one per char (`"……"` → 2). Left alone because the punctuation dictionary is single-char-keyed, so per-char tokens are safer against the dictionary-translate prefix-match truncation risk (see `docs/guides/gotchas.md`'s `cleanupFormatting` note). Characterization tests on both sides: `punctuation_run_produces_one_token_per_character` and `groups a run of punctuation into one token`.

**The shared fixture is the contract.** `test-fixtures/tokenizer-parity.json` (repo root) is the single source of truth for that divergence and 3 others (CJK Extension A, Compatibility Ideographs, underscore, BOM) plus 6 agreement spot-checks. `text_tokenizer.rs`'s `mod tests::parity::tokenize_text_core_matches_the_shared_fixture` reads it via `include_str!` + `serde_json`; the JS mirror is `src/utils/__tests__/TextTokenizer.parity.test.ts`. Adding or fixing a divergence: update the fixture first, and both sides' tests will tell you whether the implementations agree with what you just wrote.

**Three fixtures, one pattern, and the test must call production.** `test-fixtures/{tokenizer,conflict-resolution,text-assembly}-parity.json` each feed an in-module Rust `mod tests::parity` and a JS `*.parity.test.*`. A "parity" test that re-implements the algorithm tests only itself: `conflict_resolution_parity_test.rs` and `TranslationEngine.resolveConflicts.test.js` each held a private copy and were deleted 2026-10-03. Offsets Rust returns to JS are UTF-16 code units (`encode_utf16().count()`), never `chars().count()`; the astral case in `text-assembly-parity.json` pins it.

**A parity test only holds if something runs it.** `wasm-core`'s `cargo test` was not in CI until 2026-08-25. The drift check that day found `b1dd912`'s 一千零六→1,006 fix correctly mirrored, but two JS regression cases with no Rust equivalent (二零二四年→năm 2024, 百分之两百→200%) and a percentage test that discarded its result (`let _ = ...`) and so was structurally unable to fail. All three fixed same day; it runs in CI now. Re-check for assertion-shaped `let _ =` bindings when adding to any parity test file — a 2026-08-31 sweep found zero, so this is a reading habit, not a scan.

## Apparent status is not real status

Four different signals in this crate have each claimed something was live, wasm-only, hot, or covered, and been wrong. Trace the real call path or the origin commit; never accept the signal alone.

- **`lib.rs`'s `// ✅ ACTIVE SYSTEMS` header lies in both directions.** A `pub mod` absent from it with no retention note here is a strong signal of abandoned work (confirmed for `memory_management.rs` and `wasm_boundary.rs`) — but absence is necessary, not sufficient: `text_assembly`, `text_chunker`, `conflict_resolution`, and `pattern_processor` are all live and all absent, since only NumberProcessor and DictionaryEngine are named by design. Presence is not sufficient either: `position_mapper.rs` was listed as active "Used in `setPositionByMatch` for clickable highlighting" and the claim was stale — `setPositionByMatch` (`SemanticArrayBuilder.ts`) takes precomputed `startPos`/`endPos`, an O(1) tokenIndex match with no string search and no WASM call, while the real algorithm is `TextPositionMapper.ts`'s pure-JS `mapToPositions`. Git history: _"feat: add WASM Position Mapper foundation (Task #4 - partial)"_ — built, never wired, comment never corrected. Pair every liveness check with a real caller-grep.
- **A `#[cfg(target_arch = "wasm32")]` gate outlives its reason.** `is_punctuation_separator`/`chunk_text` were gated since `75ab043` to protect `chunk_text`'s then-return type `Result<js_sys::Array, JsValue>` — genuinely wasm-only. `4edb513`/`145824a` rewrote it to `Result<String, JsValue>` via pure-Rust `serde_json::to_string`, removing `js_sys::Array` from the file entirely, and the gate was never revisited. `unicode_properties` was never wasm-only either. Confirmed by `git log -p -- <file>` to the origin commit, then a native `cargo test` with the gates stripped, before ungating for real. Check whether the wasm-only dependency a gate protects is still used.
- **A name that sounds like the hot path usually isn't.** For any real translation text ≥50 chars — essentially all real usage — dictionary-lookup matching goes through a _separate_ native Rust trie in `src-tauri/src/lookup_index_engine.rs` (one Tauri IPC call, rayon-parallel across positions), not the `trie.rs` that used to live here (deleted 2026-10-04, ADR-073). Trace the call path before benchmarking or optimizing anything for "translation speed"; `docs/adr/ADR-040-reject-aho-corasick-lookup-index-swap.md` covers why an aho-corasick swap of the _actual_ hot path was evaluated and rejected.
- **"It compiles" depends on what you compiled.** `cargo build --tests` enumerates every call site the compiler can see and is the completeness check when removing or renaming a `parse_pattern`/`SemanticPattern` positional field — grep under-counts, since a bare positional value has no field name to match, and `two_phase.rs`, `index.rs` and `mod.rs` each carry inline `#[cfg(test)] mod tests` with `parse_pattern(...)` calls outside `wasm-core/tests/`. `benches/*.rs` is NOT covered by `--tests` and silently bit-rotted (2026-08-20: `pattern_matching.rs` had stale `parse_pattern` and `find_best_pattern_match` calls, broken across an unknown number of prior signature changes). CI now runs `cargo check --benches` on both crates.

**Deleting a module means checking `Cargo.toml` too** — grep for any dependency only that module used (`bincode` was `wasm_boundary.rs`'s sole consumer) and drop it. An unused compiled dependency is the same shallow-surface problem as the dead code.

## Build profile, dev binary, and WASM-only panics

`npm run build-wasm-dev` (`wasm-pack build --dev`) produces debug WASM — `overflow-checks = true`, `debug_assertions = true`, unoptimized. A panic in `tauri:dev` may not reproduce in production (`build-wasm` uses release: `overflow-checks = false`, `opt-level = 3`), so establish whether a WASM panic is debug-only before assuming a logic error. **Benchmarking corollary:** `bun run dev` and `bun run tauri:dev` both run `build-wasm-dev` first and silently overwrite a release binary with a debug one, so timings taken through them are meaningless (measured 7838 ms debug vs 2089 ms release on one input). Profile with `bun run build-wasm && bunx tauri dev`, or `bun run build-wasm` plus a plain `./node_modules/.bin/vite`.

**Dev binary path:** `build-wasm-dev` outputs to `src/wasm/translation_wasm_core_bg.wasm`, which is what the dev server serves. `public/wasm/` is updated only by production builds and can be months stale without breaking dev — check `src/wasm/` when diagnosing a stale-binary bug.

**WASM-side logging:** `#[cfg(target_arch = "wasm32")] { web_sys::console::log_1(&format!("...").into()); }` inside any Rust function — `web-sys` with the `"console"` feature is already a dep. Remove before commit.

**Debug-build panics: five confirmed causes,** four Rust-side and one JS-side. If `cargo test` passes, the bug is WASM-debug-specific and is almost certainly one of these:

1. Shadow-stack exhaustion from deep `opt-level=0` call chains — split the work across separate WASM calls.
2. Heap-allocated fields on a `#[wasm_bindgen]` struct reached via raw `__wbg_ptr` (HashMap, Vec) — move them to `lazy_static!` and pre-initialize in the constructor, outside the `&self` borrow window.
3. A `lazy_static` initialized lazily: the first method call that hits it initializes while the wasm-bindgen `RcRefMut` borrow is live → `alloc/rc.rs hint::assert_unchecked`. Not OOB; intermittent and input-dependent. Pre-initialize **all** lazy_statics in the constructor.
4. `regex::Regex`'s first `.find()`/`.captures()` inside a struct method allocates a per-thread `Pool<Cache>` via `regex-automata 0.4.x` `Pool::get_slow` — same borrow-window class as (3), but panics at `rt/mod.rs:287:25` "attempt to subtract with overflow" in `Drop for Ref`. Run `.find("")` on every `Regex` in the constructor.
5. JS-side FinalizationRegistry stale callback: nulling a wrapper variable without calling `.__destroy_into_raw()` first leaves the GC callback registered; when dlmalloc reuses the freed Rc address, it fires and decrements the new Rc to 0, so the next method call reads count=0 and trips `alloc/rc.rs hint::assert_unchecked` (line shifts by Rust version — 3743 in 1.84, 3753 in 1.96, same check). The fix is in the JS wrapper, not Rust. See `src/utils/wasm/CLAUDE.md`.

Narrow an OOB location with `web_sys::console::log_1` checkpoints at key statements.

## Toolchain posture

**Warnings are errors locally as well as in CI.** `/.cargo/config.toml` sets `[build] rustflags = ["-D", "warnings"]`, matching what CI's `actions-rust-lang/setup-rust-toolchain@v1` exports by default, so there is no class of failure that only appears after a push. Expect the gap to show up as dead-code and unused-binding lints in **test** code, which normal local runs never surface — both failures found before this was aligned (2026-08-26) were latent for weeks and neither was a real defect. Prefer closing the gap over `#[allow(...)]`: the unconstructed `MatchType::Other` in the old `conflict_resolution_parity_test.rs` marked a genuine parity hole (the else-branch of `WasmConflictResolution.js`'s `packMatches` type ternary, reached by `literal`, `semantic`, `structural_pattern` and `composite` matches). That file was a private re-implementation and is gone; `test-fixtures/conflict-resolution-parity.json` now covers the 'other' tier and runs through production `run_conflict_resolution` (see `conflict_resolution.rs` `mod tests::parity`).

**Scope wasm32-specific linker flags in `.cargo/config.toml`'s `[target.wasm32-unknown-unknown]`**, never inline in a `package.json` script. Inline `RUSTFLAGS=` bleeds into host-target build scripts (`cargo install`), and Apple `ld` rejects GNU-only flags like `-z`. The stack-size flag lives in `/.cargo/config.toml`.

**`cargo fmt` has never been run on this crate — don't treat the drift as your regression, and don't mass-reformat.** `rustfmt --check src/*.rs` (2026-08-17) shows drift in every file, and no `rustfmt.toml` exists anywhere to explain it as intentional; no CI gate or hook enforces it. When `rustfmt --check` flags a file you're editing, confirm the specific lines are ones your diff touched before fixing them. A crate-wide pass is pure mechanical churn with zero architectural value, and it buries `git blame`/`git log -p` under a reformat-only commit spanning nearly every line — exactly the archaeology this file's own entries (the stale-liveness discovery, the wasm32-gate trace) depend on. **Ruled out for mechanization 2026-08-31**: the reasoning is the payload, not the rule, and no formatting conflict has actually occurred. Reverse it if merge conflicts or review friction appear — and then the hook is for new drift only, still not a retroactive reformat. To check one file: `rustfmt --check <path>` from inside `wasm-core/`, because `cargo fmt --manifest-path wasm-core/Cargo.toml -- --check <path>` ignores the path and checks the whole crate.

## Test placement

- `tests/two_phase_test.rs` — two-phase + hierarchical composite tests
- `tests/pattern_matching_test.rs` — `find_best_pattern_match` + `PatternMatcher` unit tests
- `tests/pattern_semantic_type_test.rs` — semantic type propagation Phase A → Phase B

**`pub(crate)` functions (e.g. `tokenize_text_core`) are unreachable from `wasm-core/tests/*.rs`** — integration test files see only the crate's public API, so tests against one must live in that source file's own `#[cfg(test)] mod tests` (nest a submodule if it needs file-like organization — see `text_tokenizer.rs`'s `mod tests::parity`).

**`#[wasm_bindgen]` structs are testable from a native `#[cfg(test)] mod tests`, no `wasm-bindgen-test` needed** — a struct such as `NumberProcessor::new()` constructs and its methods run under plain `cargo test` (`DictionaryEngine` was the worked example until it was deleted 2026-10-04), because `Result<_, JsValue>` only touches JS when a `JsValue` is actually built. That covers happy-path and assertion tests, and stops working the moment a test drives an error branch calling `JsValue::from_str`. Assert through the `#[wasm_bindgen]` getters (for example `get_total_entries`) rather than private fields, and the test doubles as a JS-boundary check.

## Building a new WASM boundary validator? Check `Option<T>` first

A non-`Optional` field on a `#[wasm_bindgen]` struct is guaranteed present and correctly typed by serde, so a `validateWasmDictionaryMatch`-style `typeof` check on it defends against a corruption shape that cannot occur from valid Rust serialization. What serde can't guarantee is a semantically-wrong-but-correctly-typed value — an out-of-range index from a Rust arithmetic bug — and that is the actual recurring bug class here. Check the struct's `Option<T>` usage before choosing a validator shape; `src/utils/wasm/WasmBoundaryValidation.ts`'s `isPatternMatchInBounds`/`areChunksInBounds` are the index-bounds-only pattern this leads to.
