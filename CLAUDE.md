# Chinese-Vietnamese Translation App

React/Tauri desktop app translating Chinese novels to Vietnamese via 5-phase token consumption with WASM acceleration.

---

## Essential Commands

```bash
cargo check --manifest-path src-tauri/Cargo.toml  # NOT cd + cargo — zoxide breaks it
cargo check --manifest-path wasm-core/Cargo.toml   # separate crate — check both when touching Rust
cargo test --manifest-path wasm-core/Cargo.toml -- --test-threads=1
pnpm build-wasm-dev  # after any wasm-core change — binary is gitignored, stays stale otherwise
pnpm tauri:dev
pnpm test -- --run
pnpm type-check  # 0 errors expected
```

## Architecture

### 5-Phase Pipeline (order is immutable)

1. **Pattern** — `translationSource`: `'pattern'`, `'hierarchical_pattern'`, `'hierarchical_patterns'`, `'hierarchical_patterns_composite'`
2. **Proper Noun** — `translationSource` equals `match.dictionary` (e.g. `'properNouns-MyNovel'`)
3. **Number** — `'number_conversion'` (JS), `'number_plus_liang_fix'` (fixup)
4. **Phrase** — `'phrases'`
5. **Character** — `'characters'`

`getSourcePriority()` returns 999 for any unrecognized string — silently corrupts output.

**Consumed token contract:** `*_consumed` → `translated` must be `null`; non-`*_consumed` → `translated` must NOT be `null`. Validated by `validateConsumedTokenContract()`.

### Dual-Path Architecture

- **Character-only**: `src/components/char-only/ClickableTranslationSemantic.tsx` + `ClickableOriginalSemantic.tsx` → `PositionMetadataSegmenter.ts` (sync; `SegmentPrecomputer.ts` is sync JS, named exports)
- **Full Translation**: `src/components/full-translation/ClickableTranslationOptimized.tsx` → `TranslationEngine.js`

Completely separate code paths. Debug the right one. Both subdirectories have an `index.ts` entry point.

## Critical Constraints

**DO NOT extract** from `TranslationEngine.js`:

- `translateSinglePass()` — shared token state across all 5 phases
- `findAllMatchesWithSemanticCache()` — timing-sensitive cache invalidation
- `postProcess()` — position precision requires exact assembly order

**DO NOT modify dictionaries** without permission. Production: `~/Library/Application Support/com.lhak.chinese-translator/dictionaries/`

**Large files are intentional.** `TranslationEngine.js` and `Translator.jsx` coordinate state that can't be extracted. Can extract: pure functions → `src/utils/`; single-concern hooks → `src/hooks/`. Cannot extract: anything using `this.*`, `setState`, refs, or requiring 10+ parameters.

**Intentionally JavaScript (never TypeScript):** `TranslationEngine.js`, `Translator.jsx`, `SemanticPatternProcessor.js`

`src/utils/` has 9 concern-based subdirectories with `index.ts`: `dictionary/` · `text/` · `pattern/` · `highlighting/` · `performance/` · `caching/` · `ui/` · `memory/` — `wasm/` has no barrel, import directly.

## Development

**Environment:** `grep` is aliased to `rg` — flags behave differently. Always use the Grep tool. For **post-edit verification**, use `Read` or `sed -n 'N,Mp' file` — Bash+grep goes through RTK which may return stale file content for recently-written files. RTK also replaces long matched identifiers (and import paths containing them) with `n` in search output — use Read for accurate caller-tracing, not bash rg. In shell scripts, multi-pattern rg requires `-e 'A' -e 'B'`; `'A\\|B'` matches a literal backslash-pipe and silently returns nothing. `--include` is not a valid flag; use `-g '*.js'` glob syntax.

**Existence checks are unreliable via `find`/bash `grep`** in this environment — confirmed false negatives on git-tracked files that were actively being Read the same session (RTK proxy interference). For "does file/test X already exist," use `git ls-files | grep -i <name>` instead — never trust an empty `find`/`grep` result on its own.

**`vi.mock('../X')` resolves relative to the TEST FILE's own path**, not the module under test's — when stubbing a child that the component-under-test imports from elsewhere, match the component's import depth, not the test file's. Wrong relative depth silently renders the REAL child instead of the stub (no error, just confusing downstream test failures).

**Single test file:** `pnpm exec vitest run src/path/to/test.ts` — `pnpm test -- --testPathPattern` does not reliably filter to one file.

**Test file placement in `src/utils/`:** goes flat in `src/utils/__tests__/`, even for modules living in a subdirectory (`dictionary/`, `pattern/`, `highlighting/`, etc.) — NOT in a nested `src/utils/<subdir>/__tests__/`. `src/utils/ui/__tests__/` is the one pre-existing exception. Check `ls src/utils/__tests__/ | grep <ModuleName>` before creating a new test file.

**Test file placement in `src/components/`:** opposite convention from `src/utils/` — nests per component directory (`src/components/dictionary/__tests__/`, `src/components/configuration/__tests__/`, etc.), never a flat top-level dir. Don't apply the utils flat-rule here.

**RTK filters `cargo test` failure output** — full assertion details (panicked at, left/right values) are in `~/Library/Application Support/rtk/tee/<latest>_cargo_test.log`; grep the test name there when a Rust test fails with no detail shown in terminal.

**Large file edits:** Edit tool old_string fails for blocks >~100 lines. Use `python3 -c "with open(p) as f: lines=f.readlines(); open(p,'w').writelines(lines[:N]+lines[M:])"` to remove line range N–M (0-indexed).

**JSX in utils:** `src/utils/` files returning JSX must use `.tsx` extension — TypeScript gives misleading parse errors (`')' expected`, not "JSX not supported") otherwise. Do NOT include `.tsx` in import paths; `allowImportingTsExtensions` is off.

**Dynamic JSON imports:** Never use `import(path, { assert: { type: 'json' } })` — Rolldown silently fails to rewrite the path in production. Use a static `import data from '...json'` at the top of the file.

**Unicode line terminators in regex:** `\u2028` (LINE SEPARATOR) and `\u2029` (PARAGRAPH SEPARATOR) are ECMAScript line terminators — stored as actual Unicode characters in a JS/TS file they break a regex literal. Always use `\u2028\u2029` escape sequences in regex character classes.

**Surrogate pairs in a regex character class strip unconditionally, not just unpaired ones:** `[\uD800-\uDFFF]` matches EVERY UTF-16 surrogate code unit, including both halves of a valid pair (emoji, astral-plane chars) — no way to tell "paired" from "unpaired" without lookahead/lookbehind. A plain char-class sanitizer silently deletes emoji from any string it touches. Use `[\uD800-\uDBFF](?![\uDC00-\uDFFF])|(?<![\uD800-\uDBFF])[\uDC00-\uDFFF]` to strip only genuinely unpaired surrogates. Found in `TextSanitization.ts::sanitizeForJson` (2026-07-17e) — every dictionary entry containing an emoji was silently corrupted on save.

**Testing:** `src/test/setup.ts` must stay — referenced by `vitest.config.ts:10`.

**Report-generating skills** (e.g. `/improve-codebase-architecture`): save output to this repo's `temp/` folder, not the OS temp default — established convention across many sessions.

All write-only/unreachable (no `window.*` global, unlike ADR-021's protected dev tools) — 5th confirmed case of the "nobody reads this metric" pattern. `analyzeContentCharacteristics`/`calculateOptimalChunkSize`/`recordPerformance`/`analyzePerformanceTrend` are real production dependencies of `TranslationEngine.js` and untouched. `BatchProcessingTypes.d.ts`'s `AdaptationStats` interface and the matching fields on its `AdaptiveChunker` interface deleted alongside (100% decorative — no `// @ts-check` file ever imported them as a real type).
- `DictionaryManager.getPrecomputedCacheStats()` — deleted 2026-07-18. Zero direct callers; redundant duplicate of `window.dictionaryTrieLoader.getCacheStats()` (`DictionaryTrieLoader.js`) — both read the same module-level `precomputedTrieStats` singleton, so the two paths were always byte-identical. Also collided in name with the real, unrelated `DictionaryManager.getCacheStats()` (translation-cache stats, not trie-cache stats).
- `WasmRegexUtils.js`, `wasm-core/src/regex_utils.rs`, `OptimizationBenchmarks.benchmarkWasmRegexUtils()` — deleted 2026-07-18. Built 2026-01-31 (commit `4761c3a`); that commit's own "Next Steps" said "run benchmarks to verify 3-8x speedup" and "optional integration with TextChunker" — neither ever happened (`git log -S` on the benchmark's baseline key and on `WasmRegexUtils` in `TextChunker.js` both show zero hits after the creation commit). The wrapper's doc comment ("Benchmark: 0.004ms → 0.0013ms") reads like a measured result but matches the commit's own _projected_ target verbatim — never actually run. `regex`/`lazy_static` Cargo.toml deps kept (shared with `number_processor.rs`).

**Real bug found and fixed in the same sweep:** `useEngineReinitializer.js`'s WASM-sync-validation status check (`'PASS'`/`'FAIL_DIFFERENCES'`/`'FAIL_ERRORS'`) never matched what `DictionaryManager.validateWasmFallback()` actually returns (`'PENDING'`/`'SKIPPED'`/`'PASSED'`/`'FAILED'`) — only `'SKIPPED'` ever matched. In production this meant the success log never fired on a passing sync, and — more importantly — **the user-facing toast warning on a real WASM/JS mismatch never fired either**, since neither `'FAILED'` nor any of the checked strings matched. `useEngineReinitializer.test.js` masked this by mocking `validateWasmFallback` to return the wrong strings the consumer expected, not what the real implementation produces — tests were green while the integration was broken. The mismatch-count toast also read `syncStatus.results.different`, a field that has never existed on the real `results` object (`{tested, passed, failed, wasmErrors, jsErrors}`) — would have printed "undefined mismatches". Fixed: `useEngineReinitializer.js` now checks the real status strings and branches on `results.wasmErrors`/`jsErrors` (not a nonexistent `FAIL_ERRORS` status) to distinguish the two failure toasts; `results.failed` (not `.different`) feeds the mismatch count. `WasmValidationResult.status` and `WasmValidationResults` in `DictionaryManagerTypes.d.ts` were documenting this same wrong contract — fixed to match the real implementation.

**Non-obvious contracts:**

- **Dev `window.*` globals:** all installed via `installDevConsole(engine)` in `src/utils/__devtools__/DevConsole.js` — called from Translator.jsx engine-ready useEffect. Add new debug utilities there, not in App.jsx or Translator.jsx. **These are never automatically tested and can silently rot** — confirmed twice: a polling effect whose guard property (`engine.wasmManager`) stopped existing and nobody noticed (ADR-019), and `window.runPatternParityTests` referencing a property that never existed at all, broken since the commit that created it. After wiring a new command, manually invoke it once to confirm the guard actually passes.
- **Hotkey architecture:** `useHotkeyHandler` has two call sites — `TabbedInterface.tsx` (tab switching + Dictionary-tab shortcuts) and `Translator.jsx` via `<HotkeyHandler>` component (Translator-tab shortcuts). Add Dictionary-tab hotkeys to `TabbedInterface`, Translator-tab hotkeys to `HotkeyHandler` props. Key→action dispatch table lives in `src/utils/ui/HotkeyDispatchTable.ts` (`matchHotkey`) — add/change shortcuts there, not in the hook body.
- **Config reads:** Use `loadAppConfig()` from `utils/appConfig.ts` — caches after first load, returns typed `AppConfig` with defaults applied. In force-reload paths, call `invalidateAppConfig()` first. Never call `window.electronAPI.loadConfiguration()` directly — returns raw unvalidated data with absent/wrong-typed defaults. `saveAppConfig()` is the sole writer to config disk anywhere in `src/` (verified 2026-07-24) — this is what makes the cache safe to trust in-session; before adding any new `window.electronAPI.loadConfiguration`/`saveConfiguration` call site, grep for existing ones first (`DictionaryManager.tsx` was the last direct-call violator, fixed 2026-07-24).
- `src/utils/wasm/WasmBoundaryValidation.ts` — `copyWasmTokens`: param1=JS dest, param2=WASM src
- `types/WasmTypes.ts` (root-level, tests only) — `copyWasmTokens`: param1=WASM src, param2=JS dest (**reversed**)
- `ThrottledStreamingState` canonical home: `src/types/UITypes.d.ts`
- **`SemanticArrayBuilder` validation:** `validateArrays`/`validateAllPositions`/`hasValidPositions` are NOT on the builder — use `semanticArrayValidator.validateArrays(builder.getSnapshot())` from `utils/highlighting/SemanticArrayValidator.ts`. Builder's `validateArrays` is `private` (called only by `addUnit` internally).
- **`this.memoryCoordinator`**: re-constructed each call to `translateWithProgressiveBatches` (not at engine init); shut down in `destroy()`; replaces the former `this.smartMemoryDetector`, `this.backgroundCleanup`, `this.memoryProfiler` trinity
- **`VocabularyWarmup.warmNovelSpecificVocabulary`'s `limits.maxCharacters`/`limits.maxPhrases`** use `??` defaulting (fixed 2026-07-17, was `||`) — `TranslationCache.js:545`'s `remainingCharCapacity = MAX_CHARACTER_PREWARM - charactersWarmed` can legitimately be `0` in production once the common-character pre-warm pass fills its budget; `0 || 50` would silently re-inflate that to the default and over-warm past the intended cache budget. Same failure shape as the earlier `WasmMemoryPoolManager` `initialPoolSize`/`shrinkThreshold` fix — grep for `|| 50` / `|| 30` style defaults on any caller-supplied numeric limit before assuming `0` is impossible.
- **`useDictionaryReloadGuard`**: `consumeReloadTransition()` must be called ONCE at the TOP of `loadAndTranslate` before any early returns — reads prev reload state, updates internal ref, and returns `justFinishedReloading` atomically. Calling it after any early return skips the ref update and breaks reload-skip detection.
- **Ambient `.d.ts` types can encode the wrong contract:** `checkJs: false` means nothing validates `src/types/*.d.ts` against real runtime behavior — found twice drifted to match a _buggy consumer's_ expectation instead of the real producer (a dead getter's return type; a status-string enum matching a hook's wrong check instead of what the method actually returns). Verify a `.d.ts` claim against the real implementation before trusting it, especially before fixing a consumer to match the type instead of the other way around. Third instance (2026-07-28): `ThrottledStreamingState` under-declared 2 real runtime fields (`batchNumber`/`avgTimePerChunk`) and its own doc comment claimed a consumer that didn't exist. Before diagnosing a `.d.ts`-surfaced type error as a live runtime bug, trace the actual data flow (e.g. a passthrough hook) — the type may just be incomplete, not the data.
- **`tsc --noEmit` does NOT catch broken internal `.d.ts` references — confirmed empirically (2026-07-18f).** `skipLibCheck: true` (tsconfig, comment says "node_modules types" but the flag applies to every `.d.ts` file project-wide by TS's own definition) silently suppresses type errors _inside_ any `src/types/*.d.ts` file — including a completely undefined identifier (`extends ThisDoesNotExistAnywhere`), tested directly. Type-check only catches breakage that a REAL `.ts`/`.tsx`/`@ts-check`-annotated `.js` file depends on; same-file and `.d.ts`-to-`.d.ts` references are invisible to it. When pruning declarations from a `.d.ts` file, you MUST manually read the whole file and trace which "orphaned" declarations are actually referenced by declarations you're keeping (same-file, no import needed) — `tsc` will not warn you. Also watch for `export type {...} from '<path>'` barrel re-exports pulling from a `.d.ts` — a 4th reference style (alongside real `import type`, JSDoc `@import {...} from`, and inline `@type {import('...').X}`) that plain import-statement regexes miss because it starts with `export`, not `import`.
- **ADRs drift factually even when their decisions hold — confirmed empirically (2026-07-28, full 34-ADR audit).** File paths, processor/caller counts, and described mechanisms in ADR bodies go stale as code refactors (e.g., "three WASM processors" after one was deleted and two others adopted the pattern; a cache-invalidation mechanism fully replaced by a single `destroy()` call). ~1/3 of ADRs needed a correction; 2 needed "Superseded" status. Verify an ADR's factual claims against current code before citing it — same discipline as the CONTEXT.md/`.d.ts` entries above.

**Dead-code cleanup with fallow:** Has multiple blind spots (dynamic imports, CSS `composes`, class vs singleton, test-only). See [Fallow Protocol](docs/guides/development.md#fallow-dead-code-analysis) before deleting anything.

**Verifying "was this WASM/optimization feature ever benchmarked":** grep the whole git history for the baseline-key string it writes (`git log --all -S "<key>"`), and read the ORIGINAL creation commit's own message. This repo's WASM experiments have baked a "Performance Target" projection into a doc comment worded as if it were a measured "Benchmark:" result at least once (`WasmRegexUtils.js`, confirmed 2026-07-18) — a commit's own "Next Steps: run benchmarks to verify" is a stronger signal than any doc-comment claim.

**Explore subagent verification:** Explore subagents fabricate specific technical details — method names, usage counts, file paths, **exact quoted comment/code text**, and **recency/commit-age claims** (seen: an invented "CODE REVIEW FIX" comment conflated from a different file; a "this was added one commit ago" claim that git blame traced to the initial migration instead). Always verify any specific claim with a direct `Grep` or `Read` before acting on it — especially before deleting or refactoring based on "unused" or "nonexistent" reports, or before repeating a quoted string to the user. This includes claims baked into a saved architecture-review HTML report from a prior run, not just live subagent replies — a report card naming the wrong file or citing a nonexistent test still needs re-verification before you build on it. Also verify "has a test file" separately from "has a production caller" — dead-code sweeps have been fooled by exports whose only caller is their own test. When verifying a "zero callers" dead-code claim, re-check that the caller search didn't exclude the target file's own directory — a sibling file in the same directory is a legitimate caller (caught twice: 2026-07-18, `BackgroundCleanupManager`/`ComponentMemoryProfiler` were "dead" only because the grep excluded `src/utils/memory/` itself, missing `SmartMemoryCoordinator.ts` next door). A "trivial body, therefore dead" conclusion needs the same check even when the trivial-body fact is true — a wrapper can still be a load-bearing named seam. Found: `useTranslationResults.js`'s `setStreamingText` looked like a pure rename with zero behavior, but is a named param threaded across 3 files (`Translator.jsx`, `useAutoTranslateTrigger.ts`, `useReloadRetranslate.js`) via this codebase's `TranslationExecutionContext`/`forceReloadCtx`-style dependency-injection pattern — deleting it would have forced a raw `useState` setter into those contracts instead.

**`catch (_)`/unused catch bindings trigger lint warnings here.** `eslint.config.js` sets no `caughtErrorsIgnorePattern` — `varsIgnorePattern: '^_'`/`argsIgnorePattern: '^_'` cover vars and args, not catch clauses. Use bare `catch {}` (optional catch binding) when the error is unused, not `catch (_) {}`.

**Deleting a `CONTEXT.md`/`CLAUDE.md` glossary-style entry: Read the full entry through to the next `##` heading before building the `Edit` `old_string`.** A partial-window `Read` can miss a trailing paragraph; a partial-match delete leaves it orphaned with no error — only a follow-up grep catches it.

**`CONTEXT.md` glossary entries have no tooling verifying them against real code** — same drift risk as the `.d.ts` warning above. Found 3 stale entries in one pass (2 pre-existing): `SystemPerformanceMonitor` still said "four integration adapters" after `ContentAwarePositionCache` was deleted 2026-07-17 (3 remain); `PerformanceHealth` still documented a `cacheHitRate` param removed earlier than that. Verify an entry against the real module before trusting it, especially one describing code you're about to touch.

**`pnpm lint` suppresses ALL warnings.** `eslint . --quiet` — every rule in `eslint.config.js` except `react-hooks/rules-of-hooks` is severity `warn`, so `--quiet` silently drops `prefer-nullish-coalescing`, `no-unused-vars`, `react-hooks/exhaustive-deps`, and the console-ban rule. `pnpm lint` currently only catches parse errors + hook-rule violations. Run `pnpm exec eslint <file>` (no `--quiet`) to see real findings — `prefer-nullish-coalescing` would have caught the `||`-vs-`??` falsy-default bug class found twice in this codebase's history (`WasmMemoryPoolManager`, `VocabularyWarmup`) before either shipped.
