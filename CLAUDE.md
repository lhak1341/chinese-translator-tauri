# Chinese-Vietnamese Translation App

React/Tauri desktop app translating Chinese novels to Vietnamese via 5-phase token consumption with WASM acceleration.

---

## Essential Commands

```bash
cargo check --manifest-path src-tauri/Cargo.toml  # NOT cd + cargo — zoxide breaks it
cargo check --manifest-path wasm-core/Cargo.toml   # separate crate — check both when touching Rust
cargo test --manifest-path wasm-core/Cargo.toml -- --test-threads=1
cargo test --manifest-path src-tauri/Cargo.toml -- --test-threads=1  # test_reset_with_backup_copies_files_then_wipes_and_recreates is flaky under default parallel threads (pre-existing, unrelated to your change if it's the only one failing)
pnpm build-wasm-dev  # after any wasm-core change — binary is gitignored, stays stale otherwise
pnpm tauri:dev
pnpm test -- --run  # default reporter prints ~nothing when backgrounded/piped — silence ≠ hung; check `ps` CPU or add --reporter=verbose before assuming a stall
pnpm type-check  # 0 errors expected
```

## Architecture

### 5-Phase Pipeline (order is immutable)

1. **Pattern** — `translationSource`: `'pattern'`, `'hierarchical_pattern'`, `'hierarchical_patterns'`, `'hierarchical_patterns_composite'`
2. **Proper Noun** — `translationSource` equals `match.dictionary` (e.g. `'properNouns-MyNovel'`)
3. **Number** — `'number_conversion'` (JS), `'number_plus_liang_fix'` (fixup)
4. **Phrase** — `'phrases'`
5. **Character** — `'characters'`

`getSourcePriority()` returns 999 for any unrecognized string — silently corrupts output.

**Consumed token contract:** `*_consumed` → `translated` must be `null`; non-`*_consumed` → `translated` must NOT be `null`. Validated by `validateConsumedTokenContract()`.

### Dual-Path Architecture

- **Character-only**: `src/components/char-only/ClickableTranslationSemantic.tsx` + `ClickableOriginalSemantic.tsx` → `PositionMetadataSegmenter.ts` (sync; `SegmentPrecomputer.ts` is sync JS, named exports)
- **Full Translation**: `src/components/full-translation/ClickableTranslationOptimized.tsx` → `TranslationEngine.js`

Completely separate code paths. Debug the right one. Both subdirectories have an `index.ts` entry point.

## Critical Constraints

**DO NOT extract** from `TranslationEngine.js`:

- `translateSinglePass()` — shared token state across all 5 phases
- `findAllMatchesWithSemanticCache()` — timing-sensitive cache invalidation
- `postProcess()` — position precision requires exact assembly order

**DO NOT modify dictionaries** without permission. Production: `~/Library/Application Support/com.lhak.chinese-translator/dictionaries/`. When permission is given for a bulk edit: back up the target files to the scratchpad dir first; confirm real formatting (indent width, literal-UTF-8 vs `\u` escapes via `grep -c '\\u'`, trailing-newline via `tail -c`) before `JSON.parse`→mutate→`JSON.stringify(obj,null,2)`, so the rewrite is a surgical diff. `.trie.json` caches don't need manual deletion — checksum staleness detection regenerates them. When bulk-matching entries by key-string suffix/prefix, also verify the matched entries' **field shape** (`allowedVariableTypes`/`semanticType`) matches the expected category before mutating — a string match alone can catch unrelated entries (e.g. `色的X` catching `出色的X` "excellent", not color).

**Bash tool sandbox virtualizes writes outside the repo dir** (e.g. `~/Library/Application Support/...`) — a write can appear to succeed and read back correctly in the same session while the real on-disk file is untouched. Any write to a path outside the repo (dictionaries, `transform-rules.json`, `config.json`, `appearance.json`) needs `dangerouslyDisableSandbox: true` on the Bash call, both for the write AND the verifying read. Separately: after any direct edit to a file the running app owns, the app must be **fully quit and relaunched** (not just window-closed) before trusting the edit — a live process's own next save silently overwrites it with stale in-memory state.

**Large files are intentional.** `TranslationEngine.js` and `Translator.jsx` coordinate state that can't be extracted. Can extract: pure functions → `src/utils/`; single-concern hooks → `src/hooks/`. Cannot extract: anything using `this.*`, `setState`, refs, or requiring 10+ parameters.

**Intentionally JavaScript (never TypeScript):** `TranslationEngine.js`, `Translator.jsx`, `SemanticPatternProcessor.js`

`src/utils/` is organized into concern-based subdirectories, each with an `index.ts` barrel — `wasm/` is the one exception, no barrel, import directly.

## Development

**Environment:** `grep` is aliased to `rg` — flags behave differently. Always use the Grep tool. For **post-edit verification**, use `Read` or `sed -n 'N,Mp' file` — Bash+grep goes through RTK which may return stale file content for recently-written files. RTK also replaces long matched identifiers (and import paths containing them) with `n` in search output — use Read for accurate caller-tracing, not bash rg. In shell scripts, multi-pattern rg requires `-e 'A' -e 'B'`; `'A\\|B'` matches a literal backslash-pipe and silently returns nothing. `--include` is not a valid flag; use `-g '*.js'` glob syntax. `-g` occasionally hits real BSD `grep` (`usage: grep` error) instead of the `rg` alias — if it errors, drop `-g` and rerun plain recursive `grep`.

**RTK tee-log context strips leading whitespace/indentation** — `grep -A/-B` output saved to `~/Library/Application Support/rtk/tee/*.log` shows real content but wrong (stripped) indentation. Never build an `Edit` `old_string` from the log's whitespace — `Read` the actual file first to confirm exact indent/comment spacing.

**RTK silently truncates large grep match sets** — a Bash+grep with many hits returns a partial list with no error, and the rest lands in `~/Library/Application Support/rtk/tee/<n>_grep_*.log`; `cat`/`tail` that log for the remainder rather than assuming the visible output is complete.

**Existence checks are unreliable via `find`/bash `grep`** in this environment — confirmed false negatives on git-tracked files that were actively being Read the same session (RTK proxy interference). For "does file/test X already exist," use `git ls-files | grep -i <name>` instead — never trust an empty `find`/`grep` result on its own. `find` with compound predicates (`-not`, `-exec`) errors outright through the RTK proxy (`rtk find does not support compound predicates or actions`) — drop straight to `/usr/bin/find` for those, not just on a suspected false negative.

**`vi.mock('../X')` resolves relative to the TEST FILE's own path**, not the module under test's — when stubbing a child that the component-under-test imports from elsewhere, match the component's import depth, not the test file's. Wrong relative depth silently renders the REAL child instead of the stub (no error, just confusing downstream test failures).

**Single test file:** `pnpm exec vitest run src/path/to/test.ts` — `pnpm test -- --testPathPattern` does not reliably filter to one file.

**`pnpm test -- --run` (full suite) previously hung — root-caused and fixed 2026-08-08.** Cause: `EnhancedVirtualizedDictionaryTable.tsx`'s `refreshDuplicatesPreservingScroll` depended on the whole `scroll` object from `useVirtualScrollRange` (which returns a new object every render) instead of the one stable field it used (`scroll.getScrollTop`) — infinite render loop, only triggered by `DictionaryManager.composition.test.tsx` mounting the real composition. Full suite now runs clean in ~30s. If it hangs again, suspect the same shape: a `useCallback`/`useEffect` dep on a whole hook-return-object instead of the specific stable field it reads — check `git log -S getScrollTop -- src/components/dictionary/EnhancedVirtualizedDictionaryTable.tsx` for the fix commit.

**No `timeout` command on this machine** (macOS, no GNU coreutils) — use the Bash tool's own `timeout` parameter instead of shell `timeout <cmd>` wrapping.

**`git diff HEAD`/`git diff <ref>` omits untracked new files** — when reviewing or diffing a session that created files, also pass their paths for direct `Read`, don't rely on the diff alone.

**Test file placement in `src/utils/`:** goes flat in `src/utils/__tests__/`, even for modules living in a subdirectory (`dictionary/`, `pattern/`, `highlighting/`, etc.) — NOT in a nested `src/utils/<subdir>/__tests__/`. `src/utils/ui/__tests__/` is the one pre-existing exception. Check `ls src/utils/__tests__/ | grep <ModuleName>` before creating a new test file.

**Test file placement in `src/components/`:** components that live in a subdirectory nest their tests there (`src/components/dictionary/__tests__/`, `src/components/configuration/__tests__/`, etc.). Root-level components with no subdirectory (`ErrorBoundary.tsx`, `TabbedInterface.tsx`, a new cross-cutting primitive like `SearchFilterHeader.tsx`) use the flat `src/components/__tests__/` dir instead — it already holds several. Don't apply the `src/utils/` flat-rule to a component that DOES have a subdirectory, though.

**Edit tool's `replace_all` matches exact whitespace** — near-identical blocks that differ only in indentation (common in this codebase's copy-pasted JSX, e.g. duplicated row/cell markup) will silently skip the non-matching copy with no error. After any `replace_all` across "identical" blocks, grep-verify the replacement count matches how many you expected.

**RTK filters `cargo test` failure output** — full assertion details (panicked at, left/right values) are in `~/Library/Application Support/rtk/tee/<latest>_cargo_test.log`; grep the test name there when a Rust test fails with no detail shown in terminal.

**Large file edits:** Edit tool old_string fails for blocks >~100 lines. Use `python3 -c "with open(p) as f: lines=f.readlines(); open(p,'w').writelines(lines[:N]+lines[M:])"` to remove line range N–M (0-indexed).

**JSX in utils:** `src/utils/` files returning JSX must use `.tsx` extension — TypeScript gives misleading parse errors (`')' expected`, not "JSX not supported") otherwise. Do NOT include `.tsx` in import paths; `allowImportingTsExtensions` is off.

**Dynamic JSON imports:** Never use `import(path, { assert: { type: 'json' } })` — Rolldown silently fails to rewrite the path in production. Use a static `import data from '...json'` at the top of the file.

**Cross-language (wasm-core Rust ↔ src/ TS) shared test fixtures live in `test-fixtures/` at repo root** — read via `include_str!` + `serde_json` on the Rust side, a static JSON import on the TS side (`resolveJsonModule` pulls it in even though it's outside `tsconfig.json`'s `include` globs). Established 2026-07-29 for tokenizer parity (`test-fixtures/tokenizer-parity.json`) — reuse this location for any future cross-language fixture need instead of picking a new one.

**Unicode line terminators in regex:** `\u2028` (LINE SEPARATOR) and `\u2029` (PARAGRAPH SEPARATOR) are ECMAScript line terminators — stored as actual Unicode characters in a JS/TS file they break a regex literal. Always use `\u2028\u2029` escape sequences in regex character classes.

**Surrogate pairs in a regex character class strip unconditionally, not just unpaired ones:** `[\uD800-\uDFFF]` matches EVERY UTF-16 surrogate code unit, including both halves of a valid pair (emoji, astral-plane chars) — no way to tell "paired" from "unpaired" without lookahead/lookbehind. A plain char-class sanitizer silently deletes emoji from any string it touches. Use `[\uD800-\uDBFF](?![\uDC00-\uDFFF])|(?<![\uD800-\uDBFF])[\uDC00-\uDFFF]` to strip only genuinely unpaired surrogates. Found in `TextSanitization.ts::sanitizeForJson` (2026-07-17e) — every dictionary entry containing an emoji was silently corrupted on save.

**Non-obvious contracts:**

- **Dev `window.*` globals:** all installed via `installDevConsole(engine)` in `src/utils/__devtools__/DevConsole.js` — called from Translator.jsx engine-ready useEffect. Add new debug utilities there, not in App.jsx or Translator.jsx. **These are never automatically tested and can silently rot** — confirmed twice: a polling effect whose guard property (`engine.wasmManager`) stopped existing and nobody noticed (ADR-019), and `window.runPatternParityTests` referencing a property that never existed at all, broken since the commit that created it. After wiring a new command, manually invoke it once to confirm the guard actually passes.
- **Hotkey architecture:** `useHotkeyHandler` has two call sites — `TabbedInterface.tsx` (tab switching + Dictionary-tab shortcuts) and `Translator.jsx` via `<HotkeyHandler>` component (Translator-tab shortcuts). Add Dictionary-tab hotkeys to `TabbedInterface`, Translator-tab hotkeys to `HotkeyHandler` props. Key→action dispatch table lives in `src/utils/ui/HotkeyDispatchTable.ts` (`matchHotkey`) — add/change shortcuts there, not in the hook body. **Option/Alt-modified digit hotkeys must match `event.code` (`'Digit1'`...), never `event.key`** — macOS remaps Option+digit to a different character per keyboard layout (Option+1 → `¡` on US layout), so `.key` matching silently breaks for most users; `.code` is the physical key, immune to modifier remapping. **All `TabbedInterface` tabs are always mounted** (visibility toggled via CSS `visibility`, not conditional render) — so a hotkey pressed on one tab can imperatively trigger another always-mounted tab's component via a `forwardRef`/`useImperativeHandle` (see `RulesManagerHandle`, mirrors the older `dictionarySearchRef` precedent), without needing a second instance of that component's own state hooks. Any modal opened this way (target tab not switched to) must render via `createPortal(..., document.body)` — a plain nested overlay inherits `visibility: hidden` from the still-hidden tab-panel ancestor despite `position: fixed`.
- **Config reads:** Use `loadAppConfig()` from `utils/appConfig.ts` — caches after first load, returns typed `AppConfig` with defaults applied. In force-reload paths, call `invalidateAppConfig()` first. Never call `window.electronAPI.loadConfiguration()` directly — returns raw unvalidated data with absent/wrong-typed defaults. `saveAppConfig()` is the sole writer to config disk anywhere in `src/` (verified 2026-07-24) — this is what makes the cache safe to trust in-session; before adding any new `window.electronAPI.loadConfiguration`/`saveConfiguration` call site, grep for existing ones first (`DictionaryManager.tsx` was the last direct-call violator, fixed 2026-07-24).
- **`SegmentPrecomputer.ts`'s two scan loops are not unification candidates.** `precomputeSegments` (Vietnamese panel: punctuation-skip + case/whitespace-normalized matching via `findUnitMatch`, lowercased-char indexing) and `precomputeOriginalSegments` (Chinese panel: raw exact `startsWith`, no punctuation-skip, grapheme-cluster indexing) solve genuinely different matching problems, not the same algorithm with cosmetic differences — confirmed 2026-08-08 (architecture review round, candidate #6 grilling; see ADR-036). A third function, `buildSegmentsFromPositions` (module-private, only reachable from `precomputeOriginalSegments`), bypasses scanning entirely when every semantic-array entry has `originalStart`/`originalEnd` — it had zero test coverage despite firing on every single-chunk (short) translation; now covered in `SegmentPrecomputer.test.ts`.
- `ThrottledStreamingState` canonical home: `src/types/UITypes.d.ts`
- **`SemanticArrayBuilder` validation:** `validateArrays`/`validateAllPositions`/`hasValidPositions` are NOT on the builder — use `semanticArrayValidator.validateArrays(builder.getSnapshot())` from `utils/highlighting/SemanticArrayValidator.ts`. Builder's `validateArrays` is `private` (called only by `addUnit` internally).
- **`this.memoryCoordinator`**: re-constructed each call to `translateWithProgressiveBatches` (not at engine init); shut down in `destroy()`; replaces the former `this.smartMemoryDetector`, `this.backgroundCleanup`, `this.memoryProfiler` trinity
- **`VocabularyWarmup.warmNovelSpecificVocabulary`'s `limits.maxCharacters`/`limits.maxPhrases`** use `??` defaulting (fixed 2026-07-17, was `||`) — `TranslationCache.js:545`'s `remainingCharCapacity = MAX_CHARACTER_PREWARM - charactersWarmed` can legitimately be `0` in production once the common-character pre-warm pass fills its budget; `0 || 50` would silently re-inflate that to the default and over-warm past the intended cache budget. Same failure shape as the earlier `WasmMemoryPoolManager` `initialPoolSize`/`shrinkThreshold` fix — grep for `|| 50` / `|| 30` style defaults on any caller-supplied numeric limit before assuming `0` is impossible.
- **`useDictionaryReloadGuard`**: `consumeReloadTransition()` must be called ONCE at the TOP of `loadAndTranslate` before any early returns — reads prev reload state, updates internal ref, and returns `justFinishedReloading` atomically. Calling it after any early return skips the ref update and breaks reload-skip detection.
- **Ambient `.d.ts` types can encode the wrong contract:** `checkJs: false` means nothing validates `src/types/*.d.ts` against real runtime behavior — found twice drifted to match a _buggy consumer's_ expectation instead of the real producer (a dead getter's return type; a status-string enum matching a hook's wrong check instead of what the method actually returns). Verify a `.d.ts` claim against the real implementation before trusting it, especially before fixing a consumer to match the type instead of the other way around. Third instance (2026-07-28): `ThrottledStreamingState` under-declared 2 real runtime fields (`batchNumber`/`avgTimePerChunk`) and its own doc comment claimed a consumer that didn't exist. Before diagnosing a `.d.ts`-surfaced type error as a live runtime bug, trace the actual data flow (e.g. a passthrough hook) — the type may just be incomplete, not the data.
- **`tsc --noEmit` does NOT catch broken internal `.d.ts` references — confirmed empirically (2026-07-18f).** `skipLibCheck: true` (tsconfig, comment says "node_modules types" but the flag applies to every `.d.ts` file project-wide by TS's own definition) silently suppresses type errors _inside_ any `src/types/*.d.ts` file — including a completely undefined identifier (`extends ThisDoesNotExistAnywhere`), tested directly. Type-check only catches breakage that a REAL `.ts`/`.tsx`/`@ts-check`-annotated `.js` file depends on; same-file and `.d.ts`-to-`.d.ts` references are invisible to it. When pruning declarations from a `.d.ts` file, you MUST manually read the whole file and trace which "orphaned" declarations are actually referenced by declarations you're keeping (same-file, no import needed) — `tsc` will not warn you. Also watch for `export type {...} from '<path>'` barrel re-exports pulling from a `.d.ts` — a 4th reference style (alongside real `import type`, JSDoc `@import {...} from`, and inline `@type {import('...').X}`) that plain import-statement regexes miss because it starts with `export`, not `import`.
- **A typed `.ts` factory called from an untyped `.js`/`.jsx` file only gets the factory's own body checked — the caller's arguments are never checked** (`checkJs: false`). Wrapping untyped-file construction in a typed function guarantees the _returned_ shape is correct; it does not catch the caller passing a wrong-shaped argument. Close that gap with a dev-only runtime guard at the top of the factory, not by assuming the wrapper alone closes it (see `useForceReloadContext.ts`/`useTranslationExecutionContext.ts`).
- **ADRs drift factually even when their decisions hold — confirmed empirically (2026-07-28, full 34-ADR audit).** File paths, processor/caller counts, and described mechanisms in ADR bodies go stale as code refactors (e.g., "three WASM processors" after one was deleted and two others adopted the pattern; a cache-invalidation mechanism fully replaced by a single `destroy()` call). ~1/3 of ADRs needed a correction; 2 needed "Superseded" status. Verify an ADR's factual claims against current code before citing it — same discipline as the CONTEXT.md/`.d.ts` entries above.
- **Deleting code an ADR's Consequence section names as a fallback ("can be wired up later") stales the ADR** — add a dated addendum noting the fallback no longer exists, don't leave it silently wrong. Example: `ADR-034` addendum, 2026-08-06 (the trie-level `validateIntegrity`/`repair`/`getHealthScore` methods it left as a future-wiring fallback were themselves deleted 9 days later as confirmed dead code).

**Dead-code cleanup with fallow:** Has multiple blind spots (dynamic imports, CSS `composes`, class vs singleton, test-only). See [Fallow Protocol](docs/guides/development.md#fallow-dead-code-analysis) before deleting anything.

**Common method names collide across unrelated classes** (`getCacheStats`, `getPerformanceReport`, `clearAll`, etc.) — when grepping to confirm "zero callers," verify each hit actually belongs to the class in question, not a same-named sibling. Caught twice in one session (2026-08-06): `TranslationEngine.getPerformanceReport()` vs `WasmDictionaryManager.getPerformanceReport()`; `DebugObjectPool.getCacheStats()` vs `DictionaryManager.getCacheStats()`.

**Verifying "was this WASM/optimization feature ever benchmarked":** grep the whole git history for the baseline-key string it writes (`git log --all -S "<key>"`), and read the ORIGINAL creation commit's own message. This repo's WASM experiments have baked a "Performance Target" projection into a doc comment worded as if it were a measured "Benchmark:" result at least once (`WasmRegexUtils.js`, confirmed 2026-07-18) — a commit's own "Next Steps: run benchmarks to verify" is a stronger signal than any doc-comment claim.

**Explore subagent verification:** Explore subagents fabricate specific technical details — method names, usage counts, file paths, **exact quoted comment/code text**, and **recency/commit-age claims** (seen: an invented "CODE REVIEW FIX" comment conflated from a different file; a "this was added one commit ago" claim that git blame traced to the initial migration instead). Always verify any specific claim with a direct `Grep` or `Read` before acting on it — especially before deleting or refactoring based on "unused" or "nonexistent" reports, or before repeating a quoted string to the user. This includes claims baked into a saved architecture-review HTML report from a prior run, not just live subagent replies — a report card naming the wrong file or citing a nonexistent test still needs re-verification before you build on it. Also verify "has a test file" separately from "has a production caller" — dead-code sweeps have been fooled by exports whose only caller is their own test. When verifying a "zero callers" dead-code claim, re-check that the caller search didn't exclude the target file's own directory — a sibling file in the same directory is a legitimate caller (caught twice: 2026-07-18, `BackgroundCleanupManager`/`ComponentMemoryProfiler` were "dead" only because the grep excluded `src/utils/memory/` itself, missing `SmartMemoryCoordinator.ts` next door). A "trivial body, therefore dead" conclusion needs the same check even when the trivial-body fact is true — a wrapper can still be a load-bearing named seam. Found: `useTranslationResults.js`'s `setStreamingText` looked like a pure rename with zero behavior, but is a named param threaded across 3 files (`Translator.jsx`, `useAutoTranslateTrigger.ts`, `useReloadRetranslate.js`) via this codebase's `TranslationExecutionContext`/`forceReloadCtx`-style dependency-injection pattern — deleting it would have forced a raw `useState` setter into those contracts instead. **Architecture-review "duplication" scope is unreliable, not just individual facts:** every candidate from a `/improve-codebase-architecture` report needs its described overlap re-diffed against the real files before designing a fix — seen overstated (35 claimed lines → ~10 real) and understated (undersold divergence; "not worth it" reversed) in the same session. Ground-truth the actual files, don't design off the report card's line-count claim. Confirmed twice more in the 2026-07-29 grilling round, but for _behavior_ not line counts: a "DictionaryMatchLookup can't be tested without a live DictionaryManager" claim was false (both extractions already had standalone tests with stub closures) — see ADR-035; a "destroyEngine bypasses destroy()" claim was false (it called destroy() correctly). Re-verify behavioral claims, not just duplication-scope numbers, before designing a fix. 2026-08-07: candidate #4's "breaks true ties" claim (Rust lookup-index `priority` field carrying an array index instead of the real dictionary priority) traced out to zero behavioral impact — Rust's per-position match collection is always in `dictionaryOrder` order regardless of cross-position parallelism, and the shared comparator's stable sort preserves that same order on a real tie. Fixed anyway as interface honesty/future-proofing, not as a behavior fix — but the report card's "breaks true ties" framing overstated it as an active correctness bug.

**Confirmed twice more in the 2026-07-30 grilling round, for the candidate's own _framing_, not just its facts:** candidate #2's "3 tiers" claim was actually 2 orthogonal axes (trie-walk vs WASM-parallel are sub-modes within one axis, not separate tiers); candidate #5's "shared dual-consumer contract" claim overstated fan-out — of `SemanticArrayMetadata`'s 9 fields, only 2 (`tokenIndex`, `source`) are genuinely dual-consumed, 4 are char-only-exclusive, 2 have zero real readers today, and 3 of the original "6 gotchas" cited weren't even about this type (they were Token-level fields on a different data structure). Re-derive the model from real code before writing anything down, not just the individual facts.

**A candidate citing a prior ADR as precedent for deferring/rejecting an idea needs the ADR's actual blocking CONDITION checked, not just its existence.** ADR-033 deferred a pattern-matcher parity test because no trusted oracle existed on either side; a later candidate cited it for a tokenizer parity test where fixture-based oracles already existed on both sides, and the precedent didn't actually transfer (see ADR-033 vs the resolved candidate #6 in CONTEXT.md's TextTokenizer entry).

**`catch (_)`/unused catch bindings trigger lint warnings here.** `eslint.config.js` sets no `caughtErrorsIgnorePattern` — `varsIgnorePattern: '^_'`/`argsIgnorePattern: '^_'` cover vars and args, not catch clauses. Use bare `catch {}` (optional catch binding) when the error is unused, not `catch (_) {}`.

**Deleting a `CONTEXT.md`/`CLAUDE.md` glossary-style entry: Read the full entry through to the next `##` heading before building the `Edit` `old_string`.** A partial-window `Read` can miss a trailing paragraph; a partial-match delete leaves it orphaned with no error — only a follow-up grep catches it.

**`CONTEXT.md` glossary entries have no tooling verifying them against real code** — same drift risk as the `.d.ts` warning above. Found 3 stale entries in one pass (2 pre-existing): `SystemPerformanceMonitor` still said "four integration adapters" after `ContentAwarePositionCache` was deleted 2026-07-17 (3 remain); `PerformanceHealth` still documented a `cacheHitRate` param removed earlier than that. Verify an entry against the real module before trusting it, especially one describing code you're about to touch.

**`pnpm lint` suppresses ALL warnings.** `eslint . --quiet` — every rule in `eslint.config.js` except `react-hooks/rules-of-hooks` is severity `warn`, so `--quiet` silently drops `prefer-nullish-coalescing`, `no-unused-vars`, `react-hooks/exhaustive-deps`, and the console-ban rule. `pnpm lint` currently only catches parse errors + hook-rule violations. Run `pnpm exec eslint <file>` (no `--quiet`) to see real findings — `prefer-nullish-coalescing` would have caught the `||`-vs-`??` falsy-default bug class found twice in this codebase's history (`WasmMemoryPoolManager`, `VocabularyWarmup`) before either shipped. Many `||` warnings are pre-existing and unswept (confirmed repeatedly in `DictionaryManager.js`, `IncrementalDictionarySorter.js`) — after editing a file, check whether _your_ diff touched the flagged line before treating an eslint warning as a regression you introduced. **The RTK proxy summarizes `eslint` output into a "Top rules/Top files" count regardless of flags** — even `--format unix` doesn't return file:line detail through it. To see which line a warning is on, `grep` the source for the pattern directly (e.g. `grep -n '||' file.ts`) and inspect each hit by hand.

**Blind `||`→`??` swap on a `cond && value` expression is unsafe.** `&&` returns the literal falsy left-hand value (e.g. `false`), not `undefined`, when `cond` fails — `??` treats that as non-nullish and stops right there, skipping the real fallback that `||` would have reached. Rewrite `cond && value` → `cond ? value : undefined` first, so the "condition fails" case is genuinely nullish, then swap to `??`. Found `useDictionaryEntryForm.ts` (2026-08-12) — a third variant of the `||`-vs-`??` bug class above.

`pnpm exec eslint <test-file>.test.ts` always prints "File ignored because no matching configuration was supplied" — `eslint.config.js` excludes test files entirely. Not a bug; confirmed against a pre-existing test file too.

- **Known local fix (2026-08-12):** installed `graphify` (`~/.local/share/uv/tools/graphifyy/.../graphify/detect.py`, `_is_ignored()`) had a scoping bug — a bare `*` in ANY nested `.gitignore` (e.g. build-output dirs' standard "ignore everything here" file) matched every path in the whole repo, not just its own subtree, because the non-anchored-pattern branch tested paths relative to repo root instead of the pattern's own anchor directory. Patched locally; if `graphify update` starts silently finding 0 files again (esp. after `uv tool upgrade`), check whether this patch survived before re-diagnosing from scratch.

Never delete it as a troubleshooting step without a copy first; `--force` does not help when the scanner itself finds 0 files (that failure is upstream of what `--force` gates).
